#+TITLE: Where caches belong on a sudo-less, shared-home cluster
#+PROPERTY: header-args :eval never

Written for the LMU CIS servers, but the reasoning is about the /shape/ of the
storage rather than about CIS: one quota'd home shared by every host, one
unquota'd shared filesystem, and a local disk per machine. Any cluster with
that shape wants the same answer.

Everything measured below was run on =beta.cis.lmu.de= (Ubuntu 24.04, 4x
A100-SXM4-80GB) on [2026-08-10].

* The three filesystems

- =$HOME= --- NFS, *quota'd at ~48 GB*, shared by every host in the cluster.
- =/mounts/work= --- NFS, *no quota*, shared by every host. 7 TB free of 145 TB
  at time of writing, so it is shared with everyone else and not infinite.
- =/var/tmp= --- local disk on each machine, on the root filesystem: 858 GB
  with 730 GB free. Not shared, and not the same directory on two hosts.

=/tmp= is local too, but it carries a systemd-tmpfiles rule --- =D /tmp 1777
root root 30d= --- so it is recreated at boot and aged out at 30 days.
=/var/tmp= has no such rule. That is the whole reason the local tier is
=/var/tmp= and not =/tmp=.

* The measurements the policy rests on

Two numbers decide everything. Both compare local disk against the shared NFS
mount, on the same machine, minutes apart.

*Sequential read, 2 GB, =O_DIRECT= so the page cache cannot flatter the result:*

- =/var/tmp= --- 0.60 s, *3395 MB/s*
- =/mounts/work= --- 3.35 s, *610 MB/s*  (5.6x slower)

*File creation, 500 empty files:*

- =/var/tmp= --- 0.03 s, *0.1 ms/file*
- =/mounts/work= --- 0.32 s, *0.6 ms/file*  (6x slower)

@warn Measure sequential reads with =iflag=direct=. Without it, reading a file
you just wrote gives *0.12 s on both* filesystems, because you are timing RAM.
That number is meaningless and it is the easy mistake to make here.

Note also that 6x on metadata is a smaller gap than the "roughly 10x" figure
quoted in the earlier bootstrap notes. 6x is what a controlled run gives.

* The policy

Two questions decide where a cache goes.

*Is it large, immutable, and worth having on every host?* Then it belongs on
=/mounts/work=. Model weights are the case this is built for: downloaded once,
never modified, read by all twelve machines, and far too big for the quota.
The 5.6x read penalty is paid once per host per boot --- after that the page
cache serves it at RAM speed --- while the alternative is downloading 18 GB
again on every machine.

*Is it small, numerous, and regenerable?* Then it belongs on =/var/tmp=. This
is every compiler cache: Triton kernels, TorchInductor output, the CUDA JIT
cache, pip's wheel cache. These are thousands of tiny files, so the 6x
metadata gap is exactly the cost that matters, and they are keyed to the
host's GPU and driver anyway --- sharing them across machines buys nothing and
risks a stale hit.

*Nothing goes in =$HOME=.* It is the only quota'd filesystem, at 48 GB for
everything including your actual work. A single 27B checkpoint is ~54 GB and
would not fit at all. On a shared home there is a second, quieter problem:
=~/.cache= is /one directory/ that every host you are logged into writes
concurrently, so it is a correctness hazard and not merely a slow one.

* What the bootstrap sets

All of this lives in =~/.night-bootstrap.env=, generated by
[[file:../stages/00-dirs.sh][stages/00-dirs.sh]], which every login shell and
every later stage sources. Big store:

#+begin_src sh :eval never
export HF_HOME="${NIGHT_BIG_STORE}/hf"
export HUGGINGFACE_HUB_CACHE="${NIGHT_BIG_STORE}/hf/hub"
export TORCH_HOME="${NIGHT_BIG_STORE}/torch"
#+end_src

Local disk:

#+begin_src sh :eval never
export TRITON_CACHE_DIR="${NIGHT_LOCAL_CACHE}/triton"
export TORCHINDUCTOR_CACHE_DIR="${NIGHT_LOCAL_CACHE}/torchinductor"
export CUDA_CACHE_PATH="${NIGHT_LOCAL_CACHE}/nv"
export PIP_CACHE_DIR="${NIGHT_LOCAL_CACHE}/pip"
export NPM_CONFIG_CACHE="${NIGHT_LOCAL_CACHE}/npm"
export XDG_CACHE_HOME="${NIGHT_LOCAL_CACHE}/xdg"
export TMPDIR="${NIGHT_LOCAL_CACHE}/tmp"
#+end_src

=XDG_CACHE_HOME= is the catch-all: it moves every well-behaved application's
cache off the shared home in one line, instead of naming them individually and
missing the next one.

=TMPDIR= is set for a second reason besides speed. The default =/tmp= is mode
1777, so anything we write there is listable by every other user on the login
node; a private =TMPDIR= under our own mode-700 directory is not.

* Is there a site-wide cache to use instead?

*No.* Checked on [2026-08-10]:

- No =HF_HOME= or =HUGGINGFACE_*= is set system-wide (=/etc/environment=,
  =/etc/profile=, =/etc/profile.d/=).
- No shared model directory exists under =/mounts/work=, =/nfs/gdata=, =/opt=
  or =/srv= --- no =shared/=, =models/= or =hf/= tree.
- Each user has their own directory on the work mount, and each keeps their
  own copy of whatever they downloaded.

So there is duplication across the cluster, but nothing to opt into. If the
admins ever create a shared read-only model tree, the change here is one line:
point =HUGGINGFACE_HUB_CACHE= at it and leave =HF_HOME= private, since the hub
cache is the part that is worth sharing and the rest of =HF_HOME= is per-user
state.

* Consequences worth knowing

- *A wiped =/var/tmp= costs time, never data.* Everything under the local tier
  is regenerable by construction. If a host is reimaged, the first
  =torch.compile= is slow again and nothing else changes.
- *The big store is 95% full cluster-wide.* Unquota'd is not unlimited, and
  the space is shared with every other group. Delete checkpoints you are done
  with rather than assuming 7 TB is yours.
- *Per-host caches are per-host on purpose.* Two machines compiling the same
  kernel both pay for it. That is the correct trade: a shared compile cache
  keyed by a GPU/driver pair you are not actually running on is worse than a
  cache miss.
