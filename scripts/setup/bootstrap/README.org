#+TITLE: bootstrap
#+PROPERTY: header-args :eval never

Bootstrap the dotfiles onto a Linux host, with or without root.

Supersedes [[file:../minimal_proxy/][setup/minimal_proxy/]], which entangled "minimal vs full" with
"proxy vs no proxy". Here the proxy is just one optional stage, and the
storage layout comes from a profile instead of being hardcoded.

The target is *any* Linux host. The LMU CIS cluster is not the subject of
these scripts; it is one profile among others, enabled with a single flag. A
host nobody has configured needs no flag at all.

@note This directory was =bootstrap-sudoless/= until [2026-08-14 Fri]. It was
renamed when the sudo flavour landed, because the old name had become a lie
about half of what lives here.

* One tree, two flavours
There is *one* driver, *one* set of stages and *one* set of profiles. The only
difference between the flavours is a single capability flag, =NIGHT_SUDO=:

#+begin_src zsh :eval never
sh bootstrap-sudo.sh        # we have root; stage 05 installs system packages
sh bootstrap-sudoless.sh    # we do not; everything comes from user space
sh bootstrap.sh             # probe with `sudo -n true` and pick one
#+end_src

The two named entry points are four lines each: set =NIGHT_SUDO=, =exec
bootstrap.sh=. They exist so the choice is *declared at the call site* and
visible in shell history, not buried in whatever the host happened to answer.

Only =stages/05-system-packages.sh= reads the flag, and without root it exits
immediately. So the sudo-less path is byte-for-byte the behaviour it had
before the flavour split existed --- that is the property worth protecting,
and the reason this is one tree rather than two.

** Why the sudo capability is probed when the site profile is not
=profile.sh= is emphatic that the site is *declared, never inferred*, because
every probe for it turned out to be a proxy: a mount point only proves a share
is mounted, a =$HOME= prefix is a naming convention, a DNS search domain
tracks the VPN.

=NIGHT_SUDO= is different, and the difference is the whole justification:
=sudo -n true= is not a proxy for "can this process run root commands", it
*is* that question, executed. There is nothing left to be wrong about.

@warn It must never *prompt*. =sudo -n= throughout, never a bare =sudo=: a
password prompt on a headless host is a hung bootstrap, not a question --- the
same failure mode as =GIT_TERMINAL_PROMPT= in stage 30.

** What may go in stage 05
Only things that (a) some stage hard-requires and (b) genuinely cannot be had
in user space. Today that is =zsh= (stage 30 dies without it and there is no
good user-space build) and a C toolchain.

Anything mise or conda can provide belongs in stage 20 or 40 instead, where it
works on *every* host rather than only the rooted ones. The temptation with a
root flag is to start reaching for it everywhere; resist it, or the sudo-less
path silently rots.

* Run it
#+begin_src zsh :eval never
rsync -az ~/scripts/setup/bootstrap/ host:bootstrap/
ssh host 'cd ~/bootstrap && sh bootstrap-sudo.sh'      # or bootstrap-sudoless.sh
#+end_src

The directory is self-contained on purpose: the wrappers live *beside* the
driver rather than delegating to a shared parent, so a single =rsync= of this
one directory is still all a fresh host needs.

Then, once the dotfiles are in place, the copy inside the repo is the real
one and the rsync'd copy can go:
#+begin_src zsh :eval never
ssh host 'sh ~/scripts/setup/bootstrap/doctor.sh'
#+end_src

Single stage, ignoring the completion stamp:
#+begin_src zsh :eval never
NIGHT_BOOTSTRAP_FORCE=y sh bootstrap.sh 50
#+end_src

List stages: =sh bootstrap.sh --list=.

* A second host at a site you have already bootstrapped
On a cluster with a shared =$HOME= --- =NIGHT_HOME_SHARED=y= --- almost
everything is already there the first time you log into a new machine: the
dotfiles, =~/.night-bootstrap.env=, =~/.night-site=, the binaries in
=~/.local/bin=, and everything on the big store (conda envs, mise, the HF
cache, Doom's package tree). An interactive =zsh= comes up working.

What is *not* there is anything per-host, and there is exactly one command
for it:

#+begin_src zsh :eval never
ssh newhost 'sh ~/scripts/setup/bootstrap/bootstrap.sh 70'
#+end_src

That enables lingering and starts the services. Without it, redis and the
emacs daemon are simply not running on that machine, and every shell you
open greets you with =Could not connect to Redis at 127.0.0.1:6379=.

The per-host things, and why each is per-host:

- *services* --- redis and the emacs daemon are processes, so they exist per
  machine. Lingering is per-host state under =/var/lib/systemd/linger/=.
- *=NIGHT_LOCAL_CACHE=* --- =/var/tmp/$USER=, deliberately not shared. The
  env contract now creates these directories itself when they are missing, so
  this heals on first login rather than needing a stage. It has to: =TMPDIR=
  points there, and a dangling =TMPDIR= stops the emacs daemon from starting.
- *the emacs socket* --- under =$XDG_RUNTIME_DIR=, named per host, so each
  machine gets its own daemon.

Everything else is idempotent, so a full =sh bootstrap.sh= on the new host is
also fine --- just slower, since it re-checks every stage to conclude that the
shared filesystems already have the answer.

* Installing one more package later
Once a host is bootstrapped, =ins= is the front door, and it no longer assumes
anything about root:

#+begin_src zsh :eval never
ins tealdeer            # picks a half for you
ins-sudo tealdeer       # explicitly the system package manager, as root
ins-sudoless tealdeer   # explicitly user space, no root
#+end_src

[agfi:install] branches on [agfi:sudo-usable-p]. With root it goes to
[agfi:ins-sudo], which dispatches over apt-get, dnf, yum, pacman, zypper or apk
--- the same table as =pkg_install= in [[file:lib.sh][lib.sh]], rather than the
=sudo apt install= that used to be hardcoded there. Without root it falls to
[agfi:ins-sudoless]. macOS is untouched: brew needs no root, so the question
never arises.

[agfi:ins-sudoless] walks the first two tiers of the ladder in
[[file:stages/optional/junest.sh][stages/optional/junest.sh]] --- mise, then
conda-forge into the =tools= env stage 45 created --- and stops there. It
installs no package manager of its own: where neither =mise= nor =micromamba=
exists it says to run the bootstrap, rather than curl-piping an installer from
an interactive shell function. When both tiers miss it names the remaining
manual ones instead of failing quietly.

@note The conda tools env is *appended* to =PATH=, so a package the system also
provides stays shadowed by the system copy even after =ins-sudoless= installs
it. That is stage 45's one-owner-per-binary rule, not an accident.

** How root is detected
Two questions, and neither signal answers the other:

- *Are we a sudoer at all?* --- group membership, via =id -nG=: =sudo=,
  =wheel=, =admin=, =root=. Deliberately not the stderr of =sudo -n -v=, whose
  strings are localized and differ across sudo versions, so a check built on
  them is silently wrong under a non-English locale.
- *Can we get root right now without a prompt?* --- =sudo -n true=, the same
  probe =night_sudo_detect= uses.

[agfi:sudo-mode] combines them into one of =root=, =nopass=, =password= or
=none=, memoised per shell. Each covers the other's blind spot: a per-binary
=NOPASSWD:= entry granted with no group membership is caught by the probe, and
a group member whose credential timestamp has expired is caught by the group
check --- and then gets a prompt, rather than a silent degrade to a user-local
install. Where nobody can type that password (=isI= is false), =password= is
treated as unusable, because a prompt with no one watching is a hang.

Force the answer where you know better than the probe does:

#+begin_src zsh :eval never
NIGHT_SUDO=n ins foo                 # the same variable profile.sh reads
sudo_mode_force=password sudo-mode   # root | nopass | password | none
sudo_mode_recheck=y sudo-mode        # bust the per-shell memo
#+end_src

Both overrides are read *before* the memo, so they take effect in a shell that
has already answered the question once.

The answer is deliberately not written into =~/.night-bootstrap.env=. That file
is one file shared by every host in the cluster, and whether we have root here
is per-host --- exactly the kind of value the warning at the top of it forbids.

* Tiers
The point of the split is what each tier is allowed to assume.

- *Tier 0* -- =bootstrap.sh=, the two flavour wrappers, =lib.sh=, =profile.sh=,
  stages =00=, =05= and =10=. POSIX sh. May assume only =sh= + =git= + =curl=,
  because it runs *before* the dotfiles exist. This is the only part that must
  stay dependency-free --- which is also why stage 05 shells out to the system
  package manager directly instead of using anything from zshlang.

- *Tier 1* -- stages =20= and up. The repo is on disk, so these may source
  [[file:../../zshlang/basic/basic.plugin.zsh][zshlang/basic/basic.plugin.zsh]] and use =ec=, =assert=, =reval-ec=, =@RET=
  instead of hand-rolled sh.

- *Tier 2* -- the full environment via =basic-full.zsh= / [[file:../setup.basic][setup.basic]], plus
  optional modules behind feature flags.

* The storage contract
No stage may hardcode a path. Every stage reads these, which =profile.sh=
sets and =stages/00-dirs.sh= writes to
=~/.night-bootstrap.env= (which =~/.privateShell= then sources, so an
interactive shell agrees with the bootstrap):

- =NIGHT_BIN= -- =~/.local/bin=. Small and precious; inside the quota.
- =NIGHT_BIG_STORE= -- conda/pixi envs, package caches, Doom's =straight=
  tree, HF models, datasets. Unquota'd.
- =NIGHT_LOCAL_CACHE= -- per-host local disk. Regenerable content *only*.

Override any of them from the environment:
#+begin_src zsh :eval never
NIGHT_BIG_STORE=/nfs/gdata/$USER sh bootstrap.sh
#+end_src

* Profiles
** The profile is declared, never inferred
=night_profile_detect= consults, in order, and stops at the first hit:

1. =NIGHT_PROFILE=<name>= -- an explicit override, for a one-off run.
2. =BOOTSTRAP_CIS_P=y= -- the CIS special case. Needed *once*: stage 00
   records the result, and CIS shares one home across every host, so that
   one file covers all ~12 of them.
3. =~/.night-site= -- first non-comment line is the profile name.
4. =default=.

There is deliberately *no* probing of hostnames or mount points. Both were
tried and both were wrong: hostname patterns break the moment a host is
renamed or a new one is added, and =/mounts/Users= exists on the laptop too
whenever the VPN is up -- so the laptop would have identified as a CIS
server. A marker we write ourselves cannot be spoofed by someone else's
naming choices.

The same file is the signal Emacs reads (=night/cis-p= in =doom.d/config.el=),
so the shell and the editor cannot disagree.

** Stages branch on capabilities, not on the profile name
A profile sets two flags, and those -- not its name -- are what stages test:

- =NIGHT_HOME_SHARED= -- =$HOME= is one filesystem across several machines.
  Then per-host state (emacs sockets, caches, redis data) must go to local
  disk, and anything written to =$HOME= must *derive* host-specific values
  rather than bake one host's answer in.
- =NIGHT_MULTIUSER= -- other people can log in here. Then: =umask 077=, mode
  700 directories, and any service on loopback needs authentication --
  =127.0.0.1= excludes other *hosts*, not the other *users* of this one.

So no stage tests the profile *name* -- the only mentions of "cis" or
"beta" left under =stages/= are comments recording where a fact was
verified. A stage that asked "is this CIS?" would silently do the wrong
thing on the next cluster; one that asks "can other people read this?"
stays correct, and keeps the hardening off a declared single-user box.

=NIGHT_MULTIUSER= defaults to *y*, which is the fail-safe direction: a
wrong "multiuser" costs a stricter umask on our own files, while a wrong
"private" silently exposes history, tokens and redis to everyone on the
host. You opt out by declaring it, not by forgetting to declare it.

** Adding a host family
Copy =profiles/default.sh=, set =NIGHT_PROFILE_NAME=, the two flags, and the
three storage paths. No stage changes, and no edit to =night_profile_detect=
-- write the name into =~/.night-site= on that host, or pass =NIGHT_PROFILE=.

=profiles/cis-lmu.sh= encodes the LMU CIS cluster: one NFS home shared by
~12 hosts with a 48 GB quota, =/mounts/work= and =/nfs/gdata= shared and
unquota'd, =/var/tmp= local and ~10x faster for small files.
=profiles/default.sh= assumes nothing and keeps everything under =$HOME=.

* Feature flags
- =BOOTSTRAP_WITH_PROXY= -- off on cis-lmu; those hosts have direct
  international access.
- =BOOTSTRAP_WITH_JUNEST= -- off. Junest is a last-resort escape hatch, and
  explicitly not for emacs.

* Services (stage 70)
Per-boot services use *systemd user units*, not cron:

- No root needed, and =systemctl --user= runs on these hosts.
- =~/.config/systemd/user/= is on the shared NFS home, so one unit file
  configures every host, and =systemctl --user enable= writes its symlink into
  the shared =default.target.wants/= too. Crontabs live in
  =/var/spool/cron/crontabs/= on each host's *local* disk, so they would have
  to be copied to ~12 machines and kept in sync by hand.
- You also get restart-on-failure, ordering and =journalctl --user=.

The unit runs =~/.startup..private..zsh=, a plain zsh script (edit it to add
per-boot odds and ends). It starts redis and the emacs daemon, idempotently.

Starting at *boot* rather than at first login additionally needs
=loginctl enable-linger=, which is per-host state under
=/var/lib/systemd/linger/= on local disk. It also keeps =$XDG_RUNTIME_DIR=
alive across logout --- which matters, because the emacs socket lives there
and logind would otherwise delete it out from under a still-running daemon.

* Security on a shared login node
These are multi-user machines --- eight other people were logged into =beta=
while this was written --- so:

- *redis requires a password.* Binding to 127.0.0.1 keeps out other *hosts*,
  not other *users of the same host*; without =requirepass= anyone on the box
  could read the shell history and brishgarden state. The secret is generated
  in stage 45 into =~/.redis-auth= (mode 600); stage 70 starts the server with
  it; the env contract exports =REDISCLI_AUTH=, which =redis-cli= picks up
  automatically, so no calling code changes. A 700 unix socket is exposed too.
  =/proc/PID/environ= is owner-readable only, so exporting the secret does not
  leak it.
- *Our directories are mode 700*: =/mounts/work/$USER=, =/var/tmp/$USER=,
  =~/code=. They default to 755, which would expose models, datasets, fitted
  lenses and logs to everyone on the cluster.
- =~/.night-bootstrap.env= is mode 600, since it carries the redis secret.

* Doom is not set up here
Stage 50 installs a working =emacs= and then *delegates* to
=~/doom.d/bootstrap/install.sh=. Doom setup is not specific to this bootstrap
--- the same config is installed by other methods --- so it lives with the
config, along with its own README covering the version-lockfile policy, why
=straight-thaw-versions= must run after =doom sync=, and the failure modes.

* Things learned the hard way
Documented at the point of use in each stage; collected here because each
one cost real debugging time.

- A sourced zsh file returns its *last command's* status. =crossplatform.zsh=
  ended on =isDarwin=, so on Linux it returned 1, =basic-full.zsh= aborted
  early, and =debug=/=enhancers= never loaded. The symptom was not an error:
  =command_not_found_handler= called the (now undefined) =ectrace=, which
  raised "command not found" again, recursing and forking until the shell
  hung. Fixed in the dotfiles; the handler is now also re-entry guarded.

- conda-forge emacs 29.2 has *no* native compilation (that landed
  [2024-12-05]) and 29.4 predates the =malloc_set_state= fix ([2025-03-06]),
  so it dies instantly on glibc 2.39. 30.2 is the first build that is both
  native-comp-capable and runnable on Ubuntu 24.04.

- The emacs package does not pull in =sysroot_linux-64= / =gcc_linux-64=, but
  its bundled libgccjit cannot link without them: every native compile fails
  with =ld: cannot find crti.o=. =native-comp-available-p= still returns =t=,
  so this only surfaces once something actually compiles.

- Expose conda's emacs with a *wrapper that execs the absolute path*, never a
  symlink. Emacs locates its bundled toolchain relative to its own invocation
  path, so through a symlink native compilation fails while =emacs --version=
  looks perfectly fine.

- Nothing in a stage may read stdin. =doom install= prompts about git hooks
  and dies with =end-of-file=; use =--no-hooks= (and =--no-env=, since a
  shared home would leak one host's env to the other eleven).

- =run_soft= must return 0. Stages run under =set -e=, so a helper that
  returned non-zero would abort the very stage it exists to keep alive.

- Set =GIT_TERMINAL_PROMPT=0=. On a headless host a git credential prompt is
  not a question, it is a hung shell.

- Doom's package tree is only valid for the doom revision that built it.
  Changing the pin *after* a sync leaves =straight/= holding the other
  revision's package set; =doom sync= then tries to move already-built repos
  and stops on straight's interactive "How to proceed? (1,2,3,4,5)" prompt.
  With stdin closed that aborts *before* the generated profile init is written,
  and the next daemon start dies with
  =Symbol's value as variable is void: doom--profile-default=. Stage 50 now
  stamps the built revision and rebuilds when it moves.

- Verify emacs with a *daemon start*, not a batch load. A batch load of
  =early-init.el= succeeds even when the generated profile init is missing,
  because only the interactive path loads it. That is exactly the failure a
  user hits with =emc-gateway=, and the batch check missed it completely.

- =doom.d= reads =DOOMDIR= from the *environment*. We run =doom install
  --no-env= on purpose (a generated envvars file would bake one host's
  environment into a home shared by ~12 machines), so the handful of variables
  the config needs are set explicitly in the env contract instead.

- 134 of the 136 =package!= declarations in =doom.d/packages.el= are unpinned,
  so a fresh sync gets *today's* upstream instead of whatever the laptop has.
  That surfaced as =void-variable marginalia-annotator-registry= (the laptop's
  marginalia still had the obsolete alias; today's dropped it). Fix: read the
  laptop's =straight/repos/*= HEADs and check the same revisions out on the
  server, then =doom sync --rebuild= so the byte-code matches the sources.
  Without =--rebuild= you get stale =.elc= referencing files that no longer
  exist (=file-missing compat-31.el.gz=).

- A unix socket on the shared NFS home cannot work across hosts (AF_UNIX is
  kernel-local; the file is only a rendezvous name) *and* collides between them
  (=server-name= defaults to "server", and =server-start= deletes what it
  judges a stale socket). doom.d now puts it under =$XDG_RUNTIME_DIR= per host;
  the env contract points =EMACS_SOCKET_NAME= at the same path so =emacsclient=
  finds it.

- Beware =pkill -f <pattern>= when the pattern also matches your own command
  line. =pkill -f "doom"= and =pkill -f "emacs --daemon"= each killed the very
  shell that was about to do the work, silently. Cost me two debugging cycles.
