#+TITLE: transit
#+OPTIONS: toc:2

* What this is

A departure-board library with two front ends: a =bun= command-line tool for
the terminal, and a browser bundle for a small phone page. Both are built from
the same modules, so a board looks the same and filters the same way in either
place.

It talks to two public transit APIs. One is the city operator's own service,
which is authoritative for the urban network and is the default. The other is a
national aggregator carrying the same stop identifiers, used as a fallback when
the first one fails, and selectable outright. Neither needs an API key.

It also plans journeys, for the boards that ask it to. A board that opts in
carries, on every row, the journey that departure starts and when it gets you
there. See *Journey planning* below.

* Installing

#+begin_src sh
cd javascript/transit
bun install
#+end_src

The only dependency is the TypeScript compiler, and it is only needed for
=bun run typecheck=. Running the CLI and building the page work from a bare
checkout.

Run the tool as =bun src/cli.ts <command>=. Run the tests with =bun test=, the
type checker with =bun run typecheck=, and the browser bundle with
=bun run build=.

* Configuration

The config is TOML. The CLI looks at =$ADDRESS_CONFIG= first and falls back to
=~/.address-config/address.toml=. A missing file at that conventional location
is not an error: profiles are simply unavailable and raw stop ids still work.
A path you name yourself, through =--config= or the environment variable, must
exist.

Validation collects every problem it finds and reports all of them at once,
each naming the profile, the board index and the field, so a broken config does
not turn into a sequence of one-error-at-a-time runs. Any validation failure
exits with the config status code.

A generic example, with placeholder identifiers throughout. Every key is
optional and the values shown are illustrative rather than the defaults, which
live in the code:

#+begin_src toml
[defaults]
horizon_minutes = 90
backend = "mvg"
fallback = "transitous"
transport_types = ["SBAHN", "UBAHN", "TRAM", "BUS", "BAHN", "REGIONAL_BUS"]
plan_modes = ["SUBURBAN", "SUBWAY", "TRAM", "BUS", "REGIONAL_RAIL"]
target_max_walk_minutes = 20
timezone = "Europe/Berlin"
home = "first"

[places.somewhere]
lat = 0.0
lon = 0.0
emoji = "⭐"

[profiles.first]
title = "First"
emoji = "⭐"
short = "1st"

[[profiles.first.boards]]
title = "Rapid transit, one way"
stops = ["de:00000:1"]
modes = ["SBAHN", "BAHN"]
direction = "H"
walk_minutes = 6

[[profiles.first.boards]]
title = "Two nearby stops merged"
stops = [{ id = "de:00000:1", label = "Near" }, { id = "de:00000:2", label = "Far" }]
lines = ["X1", "X2"]
destinations = ["^Somewhere", "Elsewhere$"]
walk_minutes = 4
walk_minutes_by_stop = { "de:00000:1" = 2, "de:00000:2" = 9 }
#+end_src

Profile keys are arbitrary short words. Nothing in the package assumes any
particular key exists.

=emoji= and =short= are both optional and both are about the sticky bar on a
phone: the glyph in front of the tab and the label it draws when the full title
does not fit. A place may carry a glyph too, for the destination picker, and a
place named after a profile inherits that profile's. The glyph is validated by
length rather than by asking whether it is an emoji, because which code points
count changes with the Unicode version and what actually matters is that it
stays one glyph wide in a tab.

** The home alias

=defaults.home= optionally names one profile key. =board home= then resolves to
that profile, but only when no profile is literally called =home=: an exact key
match always wins. No other name is aliased. If =defaults.home= names a profile
that is not declared, that is a validation error naming the field.

** Per-stop walking times

=walk_minutes= is the walking time to the board's stops and defaults to zero. A
board that merges two stops can override it per stop with
=walk_minutes_by_stop=, because a single board-wide figure is simply wrong when
the two stops are different distances from the same front door: it would dim the
near stop's departures too early, or leave the far stop's looking reachable when
they are not. Every key must be one of that board's stops, values must be
non-negative whole minutes, and reachability is computed per row from the
walking time of the row's own stop.

** Stop labels

A stop may be written either as its bare identifier or as a table with an =id=
and an optional =label=. The label is a short human name, a word or two, and it
is what the multi-stop row tag and the walk summary show. Without one they fall
back to the last field of the identifier, which is a number: readable enough to
tell two platforms apart, useless for telling a reader *which* platform. Labels
are per board, so the same stop can be =Wkz= on one board and something else on
another.

** Onward connections

A board may name one interchange it feeds into:

#+begin_src toml
connection = { stop = "de:00000:9", lines = ["X9"], direction = "H", ride_minutes = 3, transfer_minutes = 5 }
#+end_src

Every row then carries the first departure at that stop which a rider leaving on
that row could still catch, computed as the row's own departure plus the ride and
the transfer. The two figures are static, and that is a deliberate first cut: a
per-departure figure needs a journey lookup for every row, which is a different
order of request volume against a free API, and for a fixed pair of stops the
static pair is right to within a minute or two.

=direction= is optional, for an interchange where the line only runs one way.
An empty slot on a row means the board has an interchange and nothing at it was
catchable from that row, which is information rather than a gap.

** Places

=[places.<name>]= declares somewhere a journey can end, and there are two kinds.

A *coordinate place* carries =lat= and =lon= and is a doorstep: the planner
routes to the point and works out the walk at the end. It is also what the
=nearby= lookup uses. Coordinates are geography, so they are excluded from the
exported config unless you ask for them.

A *stop place* carries =stop= and =label= instead and is a station you are
travelling to rather than through: the journey ends when the vehicle does, the
walk at the end is nothing, and it is offered as a destination from every
profile. It is exported unconditionally, because a stop id is not geography and
the document is already a list of stop ids.

A place declares one or the other, never both. A profile may list
=destinations = [keys…]= to fix the order the picker offers them in; without one
the doorsteps come first and the stations after, which is the order the everyday
answers come in.

A board may also set =destination = "<place key>"=, and then it plans towards
that place whatever the picker says. This is for a profile whose boards are
grouped by where they go rather than by which line they carry: standing in a
main station the question is never "where does this line go", it is "which
platform gets me home", and the answer is a property of the platform. Such a
board says where it is going under its title, and when every planning board of a
profile sets one the picker is not shown at all, because every answer it could
give is already written on a board. Do not confuse it with =destinations= on a
board, which filters the rows by the destination text the operator publishes.

** Which stop the planner is told about

A board may set =plan_stop = "<stop id>"=. It changes nothing about which
departures the board shows, which still come from =stops=; it changes only the
identifier the journey planner is given.

It exists because a large station is several stops and the two services need not
agree on which. The departure feed publishes the main station's S-Bahn under the
identifier of the main-line station; the planner models those platforms as a
station of their own underneath it. Ask the planner about the main-line station
and every journey it offers begins by walking to a stop the board has never
heard of, so the board matches none of them and every row says "no route found"
while the trains run past. That is the whole failure: no error, no empty result
from the planner, just a board that has given up for reasons it cannot state.

The rule that produces it is deliberate and stays: an itinerary whose first ride
is boarded somewhere other than this board's stop is a journey from somewhere
else, and this board cannot put anybody on it. The exception has to be declared
rather than guessed, because "a few minutes' walk away" describes both the
platform downstairs and the stop on the next street.

* Commands

=board <profile|stop...>= renders a profile's boards, or an ad-hoc board for
one or more raw stop ids. An argument that matches no profile key and does not
have the shape of a stop id is rejected with the list of configured profile
keys, rather than being forwarded upstream where it would come back as an
opaque not-found for something you never typed.

=discover <stop>= lists every (line, direction letter) pair seen at a stop over
the horizon, with a few sample destinations for each. This is how you find the
letter a board should filter on.

=search <query>= searches stops by name and prints their identifiers.

=nearby <lat> <lon>= lists stops near a coordinate.

=messages [profile]= prints service messages. Given a profile, it keeps only
messages concerning lines that profile's boards name; a profile whose boards
pin no lines narrows nothing.

=route <profile>= is the commute view: for every departure on that profile's
commute boards, the journey it starts, where you change and when you arrive.
=--to <profile>= names the far end. See *Journey planning*.

=config-export= prints the loaded config as JSON for the browser page.

** Flags

=--json= switches to the machine-readable document. =--cache= turns on the
Redis response cache, which is off by default. =--horizon <minutes>= overrides
how far ahead to look. =--backend <name>= forces the primary backend.
=--watch= clears the screen and re-renders on an interval until interrupted.
=--no-color= suppresses colour, as does an unset terminal or the =NO_COLOR=
environment variable. =--config <path>= reads a different config file.
=--with-places= adds coordinates to =config-export=. =--to <profile>= and
=--early-buffer <minutes>= belong to =route= and are described under *Journey
planning*. =--verbose= logs every outbound request to standard error, which is
how you confirm that a long horizon really did page. =--help= prints the command
list.

Exit status is zero for success, one for a runtime error, and two for a config
problem, which includes an unknown profile name and a commute with no
destination.

* Direction letters

Grouping a board by destination does not work: one direction of one line can
carry several different headsigns, so a destination-shaped grouping splits one
direction in two and merges nothing back together. The primary backend's line
identifier is a colon-joined tuple whose fourth field is a single letter naming
the direction, and that letter is consistent. The package reads it there, and
emits no direction at all rather than guessing when the identifier is malformed.

Use =discover= on a stop to see which letter goes which way, then put that
letter in the board's =direction=.

The aggregator has no such letter. It has an outbound flag, which this package
maps onto the same two letters. That mapping has *not* been verified against the
primary backend on the same stop, and the module says so. If it is ever found
not to hold, flip =TRANSITOUS_DIRECTION_TRUSTED= in
=src/backends/transitous.ts= to false: the aggregator then emits no direction on
any row, a =direction= filter drops all of its rows, and =destinations= filters
have to do the narrowing instead.

* Filters

A board's filters are applied in a fixed order: modes, then lines, then
direction, then destinations. The order is fixed so that a board producing
nothing can be debugged by peeling filters off from the bottom. A board with no
filters shows everything.

Line comparison ignores whitespace and case, so a label written with a space
between the category and the number matches the same label written without one,
in both directions. Destinations are regular expressions matched
case-insensitively against the headsign, and any one of them matching is enough.

The direction rule is blunt on purpose: a board that sets =direction= keeps only
rows carrying exactly that letter, and a row whose direction is unknown is
dropped along with the wrong-way rows. Keeping unknowns would let a backend that
supplies no letter quietly turn a one-way board into a both-ways board, which is
the failure that is hardest to notice.

* Fetching and paging

The primary backend answers with at most =MVG_PAGE_LIMIT= rows, and it applies
that cap /before/ the transport-type filter. The two together mean the size of a
response says nothing at all about the stop: a busy interchange can hand back a
full page of raw rows that narrows to a handful, and a page that arrives short
may be short only because the cap fell somewhere upstream of the filter. A
paging loop that stopped on a short page would therefore truncate exactly the
boards a long horizon was asked for.

So the walk is driven by time and never by counts. Each request names an
=offsetInMinutes=, the newest row in the response sets the next offset, and the
walk ends when that row reaches the horizon, when a page comes back empty, or
when the offset will not move any further. The last of those is what stops a
stop whose paging is stuck from being asked forever, and =MAX_PAGES= caps the
whole walk regardless. The price of not counting rows is one extra request
against a stop that really has run out, which is what its final page costs.

The next offset is rounded /down/ to the minute the newest row falls in, not up
to the one after it. Rounding up starts the next page strictly after that row
and loses whatever the cap had cut off later in the same minute, and no amount
of de-duplication recovers a row the server was never asked for. Rounding down
re-requests that minute instead, and the rows that come back twice are dropped
on a key built from the line identifier, the planned time, the destination and
the label.

The transport-type list is never omitted from a request. With no explicit list
the API silently drops regional rail and regional buses, so a board configured
for them would come back plausibly populated and quietly wrong.

A board that declares =modes= narrows the request to those categories, which is
still an explicit list and merely a shorter one. That keeps the page limit spent
on rows the board can use rather than on five categories it is about to delete.
The narrowing is intersected with the configured transport types and so can only
ever shrink them; a narrowing that intersects to nothing issues no request at
all, since an empty list would read as no list. The board's own mode filter
still runs on the result, because a backend is allowed to ignore the hint and
must not be able to widen a board by doing so.

The aggregator pages by following a cursor instead, and the endpoint used here
carries no category parameter, so a narrowing there changes only what is kept.
Its per-request row count is sized from the length of the window.

** When a direction letter is not a direction

A board can filter by the direction letter its backend puts on a line, and at a
junction that letter does not mean what it looks like it means. It belongs to the
line rather than to the compass: it is the line's primary direction as its
operator publishes it, which is "away from where the line starts". A city that is
where some regional lines start and where others end therefore has one letter
meaning both things at the same station, and a board asking for "towards the
centre" keeps the trains leaving it.

That is not a rare corner. It was observed at one large western junction where
seven regional lines carry the same letter away from the city and five carry it
towards, alongside every rapid-transit line, which carries it towards. The board
showed trains to towns a hundred kilometres the wrong way and the letter was
right about every one of them.

So a board may instead name a place its vehicles have to call at, with the =via=
key, and the check is made against the vehicle's own run. The aggregator
publishes a trip's whole stop sequence against the identifier its stop times
carry, so a row with such an identifier can be asked directly: does this run
still call there after it leaves here. "After" is load bearing. A line that runs
through the centre and out the other side calls at the centre once, and a rider
boarding beyond it wants the call that is still ahead of them.

The key takes several identifiers because one station can be several of them. A
main station with an underground rapid-transit hall publishes that hall as its
own station: the long-distance trains call at one identifier and the local ones
at another, under one name on every sign in the building. Named only the first,
the filter threw away exactly the services the board existed for.

*** One run, seen twice

The primary backend publishes no trip identifier, so a row from there has to be
recognised in the aggregator's own view of the same stop before its run can be
looked up. Two feeds of one railway share no identifier and disagree about
spelling constantly, so this asks several questions in a fixed order and stops at
the first one that answers.

Agreement on the timetabled minute plus agreement on the line is the strong case
and covers almost every row. Agreement on the expected minute comes next and is
worth less, because two runs of one line share an expected minute whenever the
earlier one is late: the real failure was a rapid-transit row timetabled for one
minute and running five late, matched against the following service, which was
timetabled for exactly that later minute. Agreement on the timetable outranks
agreement on the clock, so that pair is no longer a pair.

Then the line is dropped and the headsign used instead, because the two feeds do
not always agree on what a line is called: one wrote a regional service =RE 89=
where the other wrote =RB89=, and published the same train a second time under
another route name at the same minute. Several matches come back there, and the
run is only accepted when every one of them gives the same answer about the place
the board asks for. Two names for one train agree; two genuinely different trains
do not, and then the row is marked unchecked rather than guessed at.

Last, when even the minute disagrees, the line and the platform together, within
the tolerance named in =src/via.ts=, and only while there is exactly one
candidate that close. The disagreement this is for is not rounding: one feed was
running an older working timetable and had a train leaving eight minutes before
the other had it leaving, under a different headsign, because the portion it
carries splits later. A line that comes every few minutes has several candidates
that close, and there the match is refused instead of guessed.

Because the two clocks differ, "still ahead" is measured on the run's own clock,
not on the row's: the floor is the run's departure from this station as the run
itself publishes it. Measured from the row instead, a run matched across a
timetable version can have its next call appear to be in the past.

Trips are fetched once and remembered for the life of the page: a trip identifier
names one vehicle on one day, and a delay moves its times without moving its
sequence, so there is nothing for an expiry to protect against. Without that cache
a board that refreshes every minute would ask about every row every minute.

A row that cannot be checked is kept and marked, never dropped. The letter is
still doing the work for those rows. A board that silently hides what it could
not verify teaches a reader to distrust the whole board, and one that silently
keeps it teaches them to distrust the filter; the mark is the only version of
this that stays truthful when the network is down.

The mark is on the row itself and not only in the sheet that explains it. A
reader glancing down a board is deciding which train to walk to, and a mark that
appears only once they have tapped a row is a mark for a decision they have
already made. The terminal prints the same caveat as a word on the same row.

What is left after all of that, measured on the board this exists for, is about
one row in sixty: a regional service that the aggregator's stop times for the
station do not carry at all, at any minute, on any platform. Nothing identifies
a run that one of the two feeds has never heard of, and pairing it with the
service on the same platform a minute earlier would pair it with a train going
the other way. That row is exactly what the mark is for.

The cost is one request per distinct vehicle, which is why the letter, the modes
and the line list all run first: they are free and they throw away most of it. On
the junction above, a ninety minute window costs about thirty trip lookups on the
first load and none on any refresh after it.

** Asking past the edge

A board is planned further than it shows, by the extension named in
=src/config.ts=. Without it a departure near the end of the horizon has nothing
after it: no later service for its onward connection to point at, and no room
for the journey planner to find the change it would have to make. Neither
absence is real. A rider on the last row of a one hour board still changes
somewhere and still catches something; it was only that nobody had asked. The
symptom was the last several minutes of whichever horizon was picked going blank
in the connection column and in the journey slot, which reads as a board that has
stopped working rather than as a window that has ended.

Two things use the extension, and both of them are about what happens after a
departure rather than about the departure itself. The onward lookup at an
interchange reaches past the horizon, so the last row still has a service to
point at. The journey search is told to cover through that further point rather
than through the last row it was handed, which is the one the planner actually
needs: a search that stops where the last row leaves stops exactly where that
row's change would have to leave from.

The board's own stops are deliberately not fetched past the horizon. Rows from
out there would have to be held back from every view, since "nothing in the
window" has to keep meaning the window the reader picked, so they would be paid
for and never drawn. The measurement below is what settled it: that fetch was
nearly the whole price of the extension and the planning it was supposed to help
does not read it.

How far the search has to reach is recorded on the board as an instant, rather
than read back off whatever the last row happens to be. Those are different
facts. A sparse board can have nothing at all in the stretch past its horizon,
and the row at its edge still needs the planner to search those two hours,
because the change it is going to make is on some other line. Reading the last
row would give up on exactly the boards that need this most.

* Journey planning

A board says when vehicles leave. It does not say which of them gets you to the
other end soonest, and at a stop served by four lines that is the question
actually being asked. =route <profile>= answers it: for every departure on that
profile's commute boards, the journey that starts with that departure, where you
get off, what you catch there, and when you arrive.

A board takes part only if it says =commute = true=. Planning is a much heavier
question than a departure board, one request per board per refresh against a free
service, and most boards are not journeys anybody plans: they are "is there a bus
soon". A profile whose boards all decline says so and exits zero rather than
failing.

The destination is =--to <profile>=, and the place is that profile's entry
under =[places.<name>]=. The name is resolved as a profile first and as a place
key second, because the far end of a commute often has no boards of its own and
therefore no profile, and because a stop place has no profile by construction.
Without =--to= there is one rule and no further guessing:
from the home profile the destination is the =work= key, and from =work= it is
the home profile. Anything else has to say where it is going, and a name that
resolves to no place exits with the config status code, naming what was looked
for.

** What a plan is asked about, and how it is ranked

A plan towards a doorstep is not one search. It is one search for the
coordinate, plus one for every stop of the profile that lives there, each
carrying the walking time the configuration records for that stop, all issued at
once and merged into one set of options.

That is not redundancy, and the reason is the same Pareto set that makes exits
worth recomputing. A journey arriving at a station six minutes from the door is
dominated by one arriving sooner at a station fourteen minutes away: later, no
fewer changes, so it is never returned. Asking about the near station by name is
what makes it exist as an option at all. Measured live: from work towards home,
the recommendation was a fast train to the far station and a quarter of an hour
on foot, and the near station's train was not in the answer to be ranked.

Once the options exist they are ranked by =arrival + (walk_weight - 1) x walked
minutes=, not by arrival. Every option carries the minutes on foot over the whole
journey, the changes and the last stretch together. =walk_weight= defaults to
=DEFAULT_WALK_WEIGHT= and says what a minute on foot is worth in minutes on a
vehicle; one ranks by arrival, the way the planner does on its own. It is a
preference rather than a fact, which is why it is configurable and why the page
lets you move it for one look without saving it. Ties go to fewer changes, then
to the option that is not tight, then to staying on the first vehicle longer.

Walks are legs in the result rather than annotations on the vehicles around
them, because a walk is the thing being chosen between: "off at the far station
and fourteen minutes on foot" and "off at the near one and six" differ in
nothing else, and a list of trains hides exactly that.

** Which stops count as evidence of where a place is

A profile's boards are the reason its stops become targets: a board that leaves
from the doorstep says, by existing, that its stops are within the walk it
declares. Two rules keep that inference honest, and both live in
=src/targets.ts= so the terminal and the page cannot disagree about them.

A board that fixes a =destination= other than its own profile's place is a board
for leaving, not evidence of where the profile is. Such a board is often placed
in a profile purely so its departures show up on the right screen: an
interchange across the city, whose platforms are useful to watch from here, with
a walking time measured at the far end of the journey it describes. Its stops
are never targets for that profile. Without this rule that station becomes "a
few minutes from the door" and the commute view starts recommending that the
reader get off there, which is the fault that produced this rule: a journey home
that alighted at a station on the other side of town and claimed a three minute
walk.

Every target that survives is then checked against the place itself, when both
have coordinates. A stop further from the place than a walk of
=target_max_walk_minutes=, at the package's one walking pace, is dropped with a
warning on the console naming the stop and the distance, and the rest of the
board is planned as usual. The check is a guard against a mistyped walk rather
than a preference: the walks in the configuration are declarations, the planner
is told them rather than asked, so a wrong one is invisible and produces a
journey that is wrong in the most confident way a journey can be. A stop the
primary backend does not carry has no coordinate, and no coordinate means keep
it: a check that cannot see cannot judge. Places configured as a stop rather
than a coordinate skip it for the same reason.

The distance is straight-line, which understates a real walk, and that is
deliberate. This rejects the impossible; it does not judge the plausible.

** Which identifier the planner will accept

The two services carry the same national stop identifiers, so for a long time
the rule here was "prefix it and send it". That rule is wrong, and it fails
silently. The planner is built from the national feed, and that feed does not
always publish the *parent* of a stop area: some stops exist there only as their
platforms. Asking about the parent answers =stop_found=false=, and a board
configured with the obvious identifier could not be planned at all while its
departures worked perfectly.

So the identifier is resolved rather than assumed, in three steps, cheapest
first, and the answer is cached because it is a fact about the data and not
about the moment.

First the parent identifier itself, confirmed with a one-row stop-time request.
That is the cheapest question that distinguishes "this stop exists here" from
"it does not", and it is the right answer most of the time. A 404 to that
request IS that answer, not a failure of it, and reading it as a failure is what
kept the two steps below from ever running for a station that exists here only
as its platforms.

Then the platform identifiers the primary backend has *already handed us* on the
board's own departure rows. They cost no request, they are exactly the platforms
the board's lines depart from, and they are ordered by how many of the board's
rows use them, so the busiest platform leads. A journey plan asks from the first;
a departure fan-out walks them all, because one platform's stop times are not
necessarily the whole stop's.

Last the station's coordinate, which the planner accepts in place of an
identifier. The coordinate comes from the primary backend's per-station lookup,
not from its location search: the search takes a name and answers *nothing at
all* for an identifier. For the departures path, which needs identifiers rather
than a point, the coordinate is turned back into stop identifiers by reverse
geocoding, narrowed to the stop area that was asked about. Without that narrowing
a board would quietly start reporting the stop across the road, which is a worse
answer than reporting none.

The step that answered is published: in the route slot's tooltip on the page, in
the board heading in the terminal, and as =origin_resolution= in =route --json=.
A plan made from one platform or from a coordinate is a slightly weaker claim
than one made from the stop itself, and a reader checking a surprising route
against what they know deserves to see which it was.

Only a 404 settles a step. Every other failure is a bad moment and is raised, so
a network blip cannot be mistaken for a missing stop and then remembered as one.
When no step answers, the board says so once and keeps showing its departures.

This chain replaced a =/geocode?text=<stop id>= lookup that used to resolve a
stop to its platforms. That call now returns nothing at all for an identifier in
either form, though it still works for a name, so the old fallback had been dead
without anyone noticing. That is the argument for probing with a request that
fails loudly rather than one that can answer an empty list.

** Matching an itinerary to a departure

An itinerary belongs to a board row when its first timetabled leg carries the
same line and leaves in the same minute, at the same platform. Not the trip
identifier: the departure board and the planner do not share one. The board's
rows come from whichever backend answered and carry that backend's identifiers,
and even on the aggregator a board row is a stop time while an itinerary leg is a
trip, with nothing in either response linking the two.

Which minute is the whole difficulty. The *timetabled* minute is the one both
sides agree on, because it is the same timetable. The expected minute is not: the
board and the planner carry separate live feeds, and they disagree by a minute or
more whenever anything runs late. Matching on the expected minute alone silently
emptied every delayed row while the punctual ones planned fine, which is the kind
of failure that looks like a coverage gap rather than a bug. The expected minute
now only backs the timetabled one up, for a row whose backend publishes no
scheduled time.

Something has to separate two trains that share a line and a minute, because
that happens and it is the case that matters most. A stop whose two directions
hang off one parent identifier can run the same line at the same minute each way,
and one S-Bahn line was observed doing exactly that, leaving for the city and
leaving for the country in the same minute. Handed the wrong one of those, a row
gets the worst answer this package can give: plausible, and pointing at a train
going the other way.

The platform was that separator and it is not good enough on its own. At a large
station the two feeds do not spell a platform the same way. The departure board
says platform 6 and the planner says track 86 for the same piece of concrete, and
then says 6 for it on the next train through. That is not a disagreement about
facts, it is two identifier schemes for one edge, and holding rows to it cost the
busiest board on the page most of its journeys: measured on one afternoon, every
regional departure towards the city and half the rapid-transit ones had an
itinerary waiting and were refused it.

So the platform is believed when it agrees, and where it does not the question
falls back to where the vehicle says it is going. A headsign is exactly what
separates the two directions of a line at one minute, which is the collision the
platform was brought in to settle, and both feeds publish one. They spell a
terminus differently often enough that the comparison folds punctuation, case and
the bracketed district a long-distance feed likes to add.

A row that ends up with no journey now carries the reason, and the sheet shows
it. The two reasons are genuinely different and used to look identical on the
board: nobody offered a journey starting with that departure, which on a board
with several lines is usually the honest answer that this train is not the way to
go, and a journey was offered and refused here, which is this package's fault
every time. The command line prints the same sentence, so the question can be
asked without a browser.

An itinerary whose first timetabled leg starts at some other stop is not this
board's journey and is dropped. A leading walking leg is normal, though, and is
skipped over to find that first leg: the planner will walk you onto a platform
inside the station you named.

** What counts as an alternative

A row's alternatives are deduplicated by where the rider gets off and which
lines carry them on from there. Within a group only one ride survives, so a later
run of the very same route never appears as a choice: that is the next row on the
board, and offering it here says nothing the board does not already say. The
reported symptom was a row whose three alternatives were the same line from the
same interchange twenty minutes apart.

Which ride represents the group is not simply the earliest arrival, though it
nearly was. A tight option is never recommended, by design, because it is offered
so a rider can choose to gamble and not so the tool can gamble for them. A group
whose earliest ride was tight would therefore have elected a representative that
could never be recommended, and the row would have come back with no journey at
all while a perfectly good ride of the same route two minutes later sat unshown.
So a comfortable ride represents its route however much earlier the tight one
lands, and the earliest arrival decides between equals.

** Which vehicles a journey may use

The journey planner routes over the whole national timetable, so left alone it
will put an inter-city or high-speed train in the middle of a commute: a real
journey, quicker than the alternative, and not one a local ticket covers. So the
request names the modes it will accept rather than the ones it will not, because
that is the shape the planner's parameter takes, and long-distance rail, night
trains and long-distance coaches are simply not in the list. =defaults.plan_modes=
replaces it for a reader who does hold a ticket that covers them.

The names are the planner's own vocabulary, not this package's, and they are not
checked against a list here: that vocabulary grows upstream without asking, and a
validator would eventually reject a mode that works. A name the planner does not
recognise is ignored there, which is the failure such a check would be guarding
against anyway.

The mode list is part of the plan cache key, because two searches over different
modes are two different searches.

** Exits, walks and the early buffer

The interesting part of a matched itinerary is where the rider can get off and
what leaves from there. Every stop the first leg *calls at* is a candidate exit,
not only the one the planner's own itinerary alighted at, and this matters more
than it sounds. The planner returns a Pareto set over arrival, changes and
departure time, so "leave at 22:21 and change at the near interchange" is
dominated by "leave at 22:41 and change at the same interchange onto the same
onward train": later, no worse, so the earlier one is never returned. The only
itinerary left beginning with the 22:21 vehicle was a much worse one changing far
away, and that is what the row was told to do, while the row twenty minutes later
was given sensible advice. Reading the calling points fixes it, because the tails
observed from the later departure are exactly what the earlier row needs.

A candidate exit only reaches an onward service whose boarding platform has a
*measured* walk from that exact platform. Treating an unmeasured interchange as
instant would manufacture changes nobody can make, which is the same plausible
and wrong failure as handing a row the journey going the other way.

The first leg is truncated at the chosen exit, so it ends where the rider leaves
the vehicle. The same onward journey reached from two different exits is one
journey: it appears once, from the later exit, which means less walking and more
time on a vehicle already boarded. Every itinerary the planner returns ends at the
destination, so any tail of any itinerary also ends there, and a tail observed
after one first leg can be spliced onto another that alights at the same place.
That recombination is the point: the planner returns only changes it considers
feasible, so taking its itineraries as they came would never surface a change it
had already ruled out.

It rules them out with a transfer time that is not a walk. Measured on the live
service, the street legs at the two ends of a journey come back at a steady pace,
but the walks *between* two transit legs do not: the same service billed one
interchange at under two minutes for a hundred and eighty metres and another at
five minutes for a hundred and fifty. The difference is the minimum transfer time
the timetable carries for that station, which is a property of the station rather
than of the rider, and it is what makes a change look impossible when it is
merely inconvenient. So the transfer walk is derived from the leg's own
=distance= at =WALK_METRES_PER_MINUTE=, the single place this package turns a
distance into a time, and the planner's walking =duration= is never read.

The feasible change is then the first leg's arrival plus that walk. Onward
departures up to =DEFAULT_EARLY_BUFFER_MINUTES= *before* it are offered as well,
marked *tight*: they come off only if the first vehicle runs a little early or
the change is quicker than the pace assumes. A tight option is never the
recommended one. It is shown so a rider can decide to run for it, not so the tool
can gamble on their behalf, and the recommendation is always the soonest arrival
among the options that are not tight. =--early-buffer <minutes>= moves the line;
at zero the tight options disappear entirely. In the terminal the marker carries
the verdict without colour, so the distinction survives a terminal that has none.

=MAX_OPTIONS_PER_ROW= caps what a row carries and =ROUTE_OPTIONS_SHOWN= caps what
the terminal prints of it, both in =src/plan.ts= and =src/format/terminal.ts=
respectively. Everything past the first few arrives later than something already
on screen.

** Paging, caching and gaps

One request, as wide as the board. The planner takes =searchWindow= in seconds,
and asking for the span the board actually covers, bounded by
=PLAN_SEARCH_WINDOW_MIN_SECONDS= and =PLAN_SEARCH_WINDOW_MAX_SECONDS=, answers in
one round trip what the cursor walk needed two or more for. Measured against the
live service: =searchWindow=10800= answered in 357 ms with itineraries spanning
184 minutes of departures, where the same request without it needed two pages and
620 ms to cover less.

The cursor walk survives as the safety net for a board whose horizon outruns the
widest window worth asking a free service for. =numItineraries= is honoured too
and widens the window on its own, so it stays as a floor on how many itineraries
come back, which is what the onward-chain index feeds on. The walk ends when the
itineraries reach the last row being planned, when a page comes back empty, when
the cursor stops moving, or at =PLAN_MAX_PAGES=. The cap is there for the same reason the departure backends
have one: a free service with no rate-limit signal gets a bounded walk rather than
an unbounded one. Coverage is measured only on itineraries that actually start at
the board's stop, so one that walks off to a neighbouring stop cannot declare the
board covered.

A plan is reused for =PLAN_CACHE_MS=, keyed on the origin, the destination and
the minute it started from. A page refreshing twice a minute must not re-plan
every time, and within a minute nothing about the itineraries changes but the
delays. The early buffer is deliberately not part of that key: it only changes
how itineraries already in hand are recombined.

Rows that show no journey are common and usually mean what they say. The planner
returns optimal journeys rather than every journey, so a departure that nothing
else beats is returned and one that something else beats is not. The early part
of a window is sparser than the rest for the same reason. A board whose stop no step of the
resolution chain can name is not planned at all; its departures are still shown
and the reason is reported once per stop. The aggregator is also *asked* only
once per origin: a 404 is remembered without an expiry, because it says the
identifier does not exist rather than that this moment was a bad one, and a
board that re-asked an unanswerable question twice a minute for as long as a tab
stayed open would be a rude thing to point at a free service. That memory is
keyed on the *resolved* origin rather than on the configured stop, so a stop
that failed as a parent identifier and then resolved to a platform is asked
again under the identifier that might work. Every other failure stays
retryable.

A 404 names one of the two ends and does not say which, so it is only blamed on
the origin when *every* destination has failed, which is the one case where the
origin is what they had in common. One destination the planner cannot place is
dropped and the rest answer.

** The route document

=route --json= emits =schema_version=, =profile=, =requested_profile=,
=destination=, =early_buffer_minutes=, =generated_at= and =boards=, in the same
snake_case and ISO instants as the rest of the JSON contract. =destination= names
the far end by key and by name and carries no coordinates: the coordinate was the
input, and this package keeps geography out of what it prints.

Each board carries its title, its stops, its walking times, its labels, its
backend, and =rows=. A row carries the departure, in exactly the shape =board
--json= gives it, then =best= and =options=. =best= is the recommended journey or
null; =options= is every journey found for that row, tight ones included, sorted
by arrival, so a consumer that disagrees about what to recommend has the material
to decide for itself. Each journey names its exit stop by identifier and by name,
its arrival, how many changes it involves, whether it is tight, and its legs.

* The JSON contract

=board --json= emits a document carrying =schema_version=, =profile=,
=requested_profile=, =generated_at= and =boards=. =profile= is the key actually
rendered and =requested_profile= is what was typed, so a consumer can tell when
the home alias was followed; both are null for an ad-hoc board built from raw
stop ids.

Each board carries its title, its stops, its walking time and any per-stop
overrides, the backend that answered, and its departures. The board-level
backend is a single name when every stop on that board was answered by the same
one and the string =mixed= otherwise; every departure also carries its own
backend, so the mixed case is still readable.

Each departure carries the line label, the mode, the destination, the scheduled
and expected times as ISO instants, the delay in minutes, the cancelled and
replacement-service flags, the platform, the direction letter, whether it is
catchable, the walking time used to decide that, its backend, its stop, and a
short stop tag. The tag is non-null only on a board with more than one stop,
where it is the only thing distinguishing two otherwise identical rows. Each
board also carries =stop_labels=, the label map, or null when the board declares
none.

=config-export= emits =schema_version=, =defaults=, =backends= and =profiles=.
It carries *no* timestamp. The page repository refreshes this file by re-running
the exporter and committing the result, and a timestamp would make every run
produce different bytes, turning an unchanged config into a commit. Coordinates
are omitted unless =--with-places= is passed.

* The browser page

=bun run build= bundles =src/page.ts= into =page/app.js= and =src/route.ts= into
=page/route.js=. The bundles import only the model, the filters, the backends,
the colours and the HTTP helper; they never touch the cache module or anything
else that needs the bun runtime, and the build is deterministic.

=page/index.html= is a generic shell: a title, a stylesheet link, what CSS only
that page needs, an empty mount point and a script tag. =page/route.html= is the
same for the expanded view of one journey, and =page/theme.css= is what they
share. None of them contains a stop identifier, a coordinate or a hostname,
because a separate private repository copies them in alongside its own
=data/config.json= produced by =config-export=. The page fetches that file
relative to itself on load.

The page renders one tab per configured profile, in config order, titled from
each profile's title, and remembers the selection in local storage inside a
try/catch so a browser that refuses storage still works. It refreshes only while
the document is visible, ticks its countdowns locally in between, and on a failed
refresh keeps the last good data and says so.

** Three states per board

A board is *integrated*, *full* or *collapsed*, and integrated is the default.
Integrated is a strip of times, one line per (stop, line, direction), which
answers "when is the next one and how often" in a glance. Full is one row per
departure, for when the platform, the delay and the onward connection matter.
Collapsed is for a board that is not relevant today but would be annoying to
delete from the configuration. Clicking a board's title cycles the three, and the
choice is remembered per profile and per board title.

There is no separate "later" section any more. One board is one state, and the
integrated view covers the whole horizon.

** The row grid

A row is a grid of fixed slots: minutes, line badge, destination with its times,
the onward connection, the journey to the destination, a reminder marker, and
the stop label. The platform and whether the time is live are on the row too,
and are deliberately not slots.

Both were, and both overflowed on the reader's phone. A grid track is a promise
about width, and a cell whose text is wider than its track does not overflow
anything a browser will report: it paints across its neighbours. The word
"planned" fitted its track exactly in the font of the machine this was written on
and lay across the bell in the font a phone renders =system-ui= as. Replacing the
word with a disc fixed the word and not the mechanism, because the disc still
needed a track and the track still had to be budgeted against a font nobody here
can see. The platform's own track was cheaper but no better spent: two characters
were costing the destination a quarter of its width.

So they are one badge in the row's top right corner, positioned out of the flow,
where they cost the row no width at all. The badge holds the platform number and
is painted by the state: green when the operator is reporting this trip, grey
when the time comes off the timetable, red and struck through when the departure
is cancelled. A row with no platform gets the same badge with nothing in it, so
the colour still reads and the corner still looks like one thing rather than like
something missing. It is flush into the corner rather than floating near it: no
margin, and the two corners that lie along the row's own edges stay square so the
badge fuses with them, leaving only the corner that faces into the row rounded.
Its digit is centred by a line height equal to its height rather than by flex
alignment, because a flex box inside a baseline-aligned row inherits a baseline
it should not have and the digit then sits a pixel low in some fonts and not in
others. The words for all of this are in the sheet, on the line that says where
the time came from.

**** A platform three feeds might know

The primary feed publishes a track for most services and, at some stations, none
at all for a whole category: rapid transit is the usual one, and those rows'
corner badges were empty while the aggregator's row for the very same train at
the very same stop carried the track all along.

So a missing platform is borrowed, in order of how much each source knows about
this row. The row's own feed first, because it is the feed the row came from.
Then the aggregator's row for the same run at the same stop, matched by the same
cascade that identifies a run for its onward calls, and borrowed once per stop
in the data layer rather than per row on the screen. Last the run's own record,
which names the track it uses at each call, and which is only available once
something has asked where the run goes.

A borrowed figure is kept in its own field rather than written into the
published one, because the two are not the same claim and everything that
decides whether two rows are the same run compares the published one. Good
enough to print on a badge is not good enough to identify a train with. A
platform nothing publishes stays unpublished: the badge shows nothing rather
than a guess.

In the strip the platform belongs to the group rather than to the time. A group
is one line in one direction from one stop and almost always leaves from one
platform, so the group carries the platform most of its times use, once, in the
same corner badge a row uses, and only the times that differ from it are marked.
Almost always: a diversion or a single late-evening run can move one departure,
and that one departure is exactly what a reader standing on the usual platform
needs to be told about. A group no feed publishes a platform for gets no badge.

The countdown is minutes up to an hour, hours and minutes past it, and whole
hours past ten of them: a row two hours out reads "2:14" and one twenty hours out
reads "20h". At that range the question is how long, and four digits of minutes
is a number the reader has to divide. The column is right-aligned, so a "9", a
"45" and a "1:23" end under each other down the board.

*** A column budgeted for the common case, not the widest one

Five characters was the widest the headline could be, at the far end of the
longest horizon on offer, and the column was budgeted for exactly that. It was
the wrong budget. Almost every row is one or two digits, so two thirds of the column was
blank on almost every row, and because the column is the first one and its text
is right-aligned, all of that blank pooled on the left: a gutter down the side of
every board, on every screen, for the sake of a form that appears a few times a
day. Measured in the stress font, thirty six pixels a row.

So the column is two digits wide now, and anything longer is drawn smaller to fit
it. There is one step, and its ratio is the widest form the headline can emit,
four characters, over two digits in a font wider than this machine's. The thirty
six pixels went to the destination, which is the column that yields first and the
one the reader is actually reading.

There were two steps at first, the second one for a five character form, and that
is the part worth writing down because it was the wrong answer. Two digits of
width make "23:59" fit only at about seven pixels, and seven pixels is not a
small number, it is a smudge. The fix was not a deeper step but a shorter string:
past ten hours the headline drops the minutes and reads "23h". Nothing is lost by
that. A departure half a day out is not one anybody times to the minute, the row
already carries the clock time it means, and the sheet and the tooltip spell the
countdown out in full whenever the headline has rounded it, so the exact figure
is one tap from the row that rounded it.

Whether a countdown needs the step is a question about the length of the string
and not about its punctuation. A colon is what makes the long forms long today,
and a rule written about the colon would quietly stop covering the next long form
that appears, which is exactly what "23h" would have been. The rule is in
=src/page/dom.ts= beside the formatter, so the two can be checked against each
other: one test walks every minute the longest horizon can reach and insists that
everything the formatter emits which is wider than the column takes the step, and
another insists that nothing it emits is wider than the step can hold.

The tick has to set the class as well as the text: a countdown crossing the hour
changes length as well as value, and a class set once at render is the wrong
class a minute later. It still patches the text node rather than replacing it.

The rest of the left edge was measured and left alone, because it turned out not
to be waste. On a phone at 390 pixels the card starts at zero, its padding is
eight pixels, the row adds none of its own, and the countdown's cell begins
exactly there. The mark on the first catchable row is an inset shadow rather than
a track or a border, so it costs no width at all; it was moved out of the grid
for that reason and the comment beside it says so. Eight pixels is the page's
text gutter, not a gutter to reclaim, and taking it would put the largest number
on the page against the edge of the screen.

What is left inside the column is the space a one-digit countdown leaves to the
left of itself, which is what right-alignment is for: the units line up down the
board, so the eye compares lengths of time rather than hunting for where each
number starts.

On a phone the row's second line has to earn its place. A clock time that is
exactly the countdown added to now says nothing the countdown has not already
said, and saying it costs a whole line on every row. So the second line is drawn
when there is something on it that the countdown does not carry: a delay, where
the expected time and the promised one are two different facts, a replacement
service, or a cancellation. An on-time departure with none of those is one line
tall, and its clock time is in the sheet with everything else. On a wider screen
the line is free and is always drawn, so the rows there stay the same height as
each other.

In the slots too narrow to hold a full place name (the strip's legend, the board
chips) names are abbreviated by one shared map before they are cut, so what
survives distinguishes one place from another rather than spelling out the word
"station". The full name is always still in the tooltip.

The journey slot goes further, because it is the narrowest of them and an
ellipsis there was leaving two letters and a dot, which names no station at all.
Its exit name goes through the same rule the destination badges use: the words
that only say what kind of thing a place is are dropped, a place with two names
keeps the first, and a name still too long ends in a period rather than an
ellipsis. A period is a word that has been shortened; an ellipsis is a row that
has run out of room.

Both the destination and the journey carry a minimum width, and the journey's is
the one that holds. When a row runs out of space the destination yields first:
it is abbreviated already, the same word is on every row of its group, and the
tooltip repeats it, whereas a journey squeezed below its floor stops naming a
station. The interchange and the journey also carry a maximum they may fall
below. On a phone a board that has *both* an interchange and a journey still
does not fit, and there the journey wins and the interchange is not drawn: it
answers the same question with more in it, chosen per row rather than configured
once. On a wider screen both fit and both are shown, because a configured
interchange is something somebody asked for by name. This is the one layout
decision the render makes rather than the stylesheet, so the page re-renders
when the breakpoint is crossed. A slot is empty when the value is absent and
nothing shifts, so the eye can run down one column.

The numbers this has to add up to are not the ones the screen reports. A row is
narrower than the page by the page's gutter, the card's border and the card's
own padding, and a grid whose fixed tracks exceed the row it is in neither wraps
nor ellipsises: it runs the last column off the side of the card, where the card
clips it and the page reports no overflow at all, because at the page level
there is none. The touch harness asserts every row child stays inside its row
for exactly this reason. It found the case above, where the columns had been
budgeted against the page's width rather than a row's.

On a phone the cards are full bleed: no page gutter, no side borders, square
corners, and one card separated from the next by the page colour showing
through. A card inset from the edge spends the same margin twice, once outside
it and once inside, and on a phone that margin comes out of the row rather than
out of the screen. What it bought went to the destination.

Which of the two wide cells absorbs a screen's spare width depends on the
screen. On a phone there is none to absorb, so the destination takes what there
is and the journey slot is pinned to its floor. On a wide screen there is a
great deal, and giving it to the destination put a few hundred pixels of nothing
between a departure and the journey that belongs to it, which makes a row take
two glances instead of one. There the destination is capped at a width a station
name fits in and the journey takes the rest.

Past that, on a screen wide enough that the column itself is still most of the
window with blank margins either side, the column grows again. Boards keep
their rows exactly as above: no side-by-side grid of boards, and the row's own
grid template is unchanged, so what actually gets wider is the fraction the
journey slot already claims and the strip view's own row, which can now lay
more of a group's times on one line before it wraps. The floor this kicks in
above and the width it grows to are both in the page's shared stylesheet, next
to the narrow column's own rule; see =#app= in =page/theme.css=. The
anchored journey popover (see *The journey tooltip and the expanded page*
below) grew its own width cap to match, so it reads as an explanation rather
than a column of fragments; that cap is the =.tip= rule in the same file, next
to =SHEET_MAX_WIDTH_PX= in =src/page/tip.ts=, which still decides the
floor below which it is the phone's bottom sheet instead.

What the destination ends up with is the whole point of the arithmetic, so the
harness measures that rather than trusting it: on a board with a journey slot at
a phone's width, the destination must hold twelve characters of a long station
name, measured against a sample rendered in the cell's own font and measured
again with a deliberately wider font forced on the page. Twelve characters is
about where a shortened name still says which station it is.

Which *optional* slots exist is decided per board rather than globally: the
connection column only when the board declares an interchange, the journey column
only when that board is being planned, and the stop column only when the board
merges stops.

The expected time is the headline and the planned time follows it in parentheses
when the two differ, because a departure eleven minutes late is a different thing
from one always scheduled for then. Delay and cancellation are carried by weight
and by a struck line as well as by colour, so they survive a monochrome screen.

** The bar

Sticky, and it carries the profile tabs, one jump chip per board with that
board's next departure, the horizon picker with the resulting end time, the start
time, the destination the commute view plans towards, the refresh control with
its age and progress ring, and the name of whichever backends answered. The chip
row and the control row both scroll sideways rather than wrapping or shrinking,
because on a phone they do not fit and a control that cannot be reached at all is
worse than one that has to be scrolled to. The chips count only the rows a board is actually
showing, so a chip never promises a departure the board's own filter is hiding.

Their scrollbars are hidden, so they read as bars rather than as panes, and that
leaves nothing to say there is another control just past the edge. The control
row fades out on whichever side is still holding something, and drops the fade at
the end it has reached: a last control that stays dimmed reads as disabled rather
than as reachable. The harness enforces the pair. Every other element on the page
has to fit the viewport; this one may scroll, and must show the fade when it
does.

*** A glyph and a short name per tab

A profile may declare a glyph and a short label, and on a phone the tab draws
both instead of the title. The glyph is a landmark rather than a label: it is
there so a thumb can find the right tab without reading, and the word stays
beside it so a reader who does not recognise the picture is not guessing. The
full title remains the tab's accessible name and its tooltip, and a screen wide
enough for it draws it in full, still with the glyph in front. With no short
label declared the key stands in, uppercased, which is right for a key that is
already an abbreviation and wrong for a word, so a word declares its own.

The places do not repeat themselves: a place named after a profile borrows that
profile's glyph in the destination picker, and only the stations a reader
travels to declare their own.

None of this is decoration, and the test for it is not whether it looks nice.
The bar is sticky, so every pixel it grows is a pixel of departures gone from
every board, and a second row of tabs would be worse than no glyph at all. So
the assertions are that the bar is exactly as tall with the glyphs as without
them, that the tabs sit on one line, and that the last of them is fully on
screen.

That last one failed the moment it was written, with four profiles on a real
phone: the fourth tab was drawn off the edge of the strip. What the smoke check
made obvious is that the right of the bar takes its width first and the tabs get
what is left, so everything reserved on the right is a tab that might not be
reachable. Three things came off it. The tabs and their padding are tighter at
phone width, where a thumb is no less accurate for a few pixels either side. The
freshness reads as a number rather than as a word while a refresh is running,
because the ring beside it is already spinning and "updating" was three times
the width of the age it replaced. And the feed's name leaves the bar entirely on
a phone: it is provenance rather than a control, every board's filter now names
the feed that answered it, and a board that disagrees with the others still says
so on its own header. The check prints how much room is left, so the next
profile added can be budgeted rather than discovered.

The start time is either *now*, which moves with the clock, or a moment the
reader picked. With a picked moment every row is labelled *planned*, because
there is no live data for a train that has not been dispatched yet.

A row is marked =live= or =planned=, and =planned= explains itself differently
either side of an hour: inside it the operator has not started reporting that
trip yet, beyond it the row is simply too far ahead for reporting to have begun.
The two are genuinely different questions, and saying "no live data" for both
invites a reader to worry about the second, which is only how a timetable
works.

On the desktop: the number keys switch profiles, =r= refreshes, =[= and =]= step
the horizon, and =f= toggles the board under the top of the viewport between full
and integrated. All of them are ignored while typing in a field.

** The commute view on the page

The same planner the =route= command uses runs in the page, for the boards that
say =commute = true=. The bar gains a destination picker listing the configured
places, remembered per profile, and each planned row gains a journey slot: where
to get off the first leg, the short chain after it, and the arrival time.

The slot is worth a column only because of the comparison it makes possible. The
exit stop a line usually uses is computed from the board's own rows rather than
configured, and a row whose best exit differs from that usual one is marked, so
the signal is "this one is better off somewhere else" rather than the same advice
on every row. An optional sort orders a planned board by arrival instead of
departure, which is the order the question is actually asked in.

A cancelled row is never given a journey, at any layer. The planner works from
the timetable and does not always know a vehicle has been withdrawn, and a
recommendation to board a train that is not running is worse than no
recommendation.

The board's own filter carries the tight-connection window and the walking
weight, because both change what one board shows and mean nothing on the others.
Both are held in memory and deliberately not persisted: they are "show me what I
would have to run for" and "what if I would rather sit down" questions about one
look at one board, and a persisted one would quietly change every plan for weeks
after the reader forgot they had touched it. Moving either re-plans without
re-fetching, which is nearly free, because neither is part of the plan cache key.

The boards of a profile are planned all at once, and the profile the reader is
looking at is planned before the others: a background tab must not put four
journey searches in front of the one on screen. While a run is going a planned
board says so, and the refresh ring counts planning as work in flight, because a
ring that stopped while the journeys were still being worked out said the page
was idle when it was not.

Plans *are* mirrored to IndexedDB, and what comes back is never presented as
current. A stale departure is obvious, since its countdown is wrong and the row
says how old the data is; a stale arrival time is not, because it looks exactly
like a fresh one and it is the number a reader acts on. So a restored plan is
drawn dimmed and italic with its age on the board, and swapped out the moment a
fresh one lands. Without the mirror a cold start shows every row with an empty
journey slot for a second or two, which reads as "no journey" rather than "not
yet asked".

*** The journey tooltip and the expanded page

A journey slot is two centimetres wide and the answer is a paragraph, so the
slot is a summary with two ways out of it.

Hovering it opens the page's tooltip: the recommended journey with every leg
listed, walks included, then the other options as one-liners that expand where
they stand. The same tooltip carries the times in the rows and the strip, and
the jump chips in the bar. It replaced the native =title= attribute, which takes
plain text only and never appears at all on a phone, which is where this page is
read and where the slot is narrowest. A control with its own primary action,
like a jump chip, keeps its tap and opens the tooltip on hover or a long press
instead.

The other way out is the expanded view: one journey, every leg, the alternatives
in full. In a browser tab that is a second document, opened in a new tab so the
board stays exactly where it was, with its own address so it can be shared,
bookmarked and reloaded. See *The route document*.

Installed to a home screen there are no tabs. The page runs standalone, and a
link to a second document then has nowhere to go: it either does nothing or it
replaces the only window there is, and either way the board is gone. So in
standalone the same view is drawn over the board instead, as a full screen
overlay, by the same module the page itself calls. The view is a render function
over a container for exactly this reason: two ways in, one thing to maintain,
and no chance of the overlay and the page disagreeing about what a journey looks
like.

It is shielded from the sheet underneath. A sheet closes on a pointer landing
anywhere it does not own, which is right for a page and wrong for a view the
sheet itself put on top: a reader tapping a control in there is still inside the
answer they opened. Anything drawn over a sheet and opened from it says so with
one class, so the rule stays in the sheet's own code rather than the sheet
learning the names of the things that may cover it.

Opening it pushes a history entry. That is what makes it feel like part of the
system rather than a pane somebody bolted on: the Android back gesture pops the
entry, the overlay's own back control does nothing except pop the same entry,
and the close happens on =popstate= in both cases, so there is one path out and
no way for the history to end up holding an entry for an overlay that is no
longer there. Nothing underneath is torn down, so the board is still scrolled
where it was and the sheet is still open when it closes. The overlay carries a
control that copies the address the view would have as a page, because the one
thing a tab gave the reader that an overlay does not is something to share.

The trailing link in the sheet says where it goes, and where it goes depends on
whether there is anywhere to go: "a new tab" is a promise the installed app
cannot keep.

*** One tap target per row

On a touch screen the row is the tap target, not the cells inside it, and a tap
anywhere on it opens that departure as a sheet: a dimmed backdrop, the departure
at the top with its planned and expected times, delay, platform, stop and where
the times came from, then the journey below when there is one. Tapping the
backdrop, the close button, Escape or the row again dismisses it.

The cells were the tap targets before and every one of them was wrong in its own
way. The destination answered a tap by starting a text selection, the line badge
by doing nothing, and the journey slot by opening a new tab that the browser
then refused. That last one is worth writing down, because it looked like
nothing happening at all: the tap handler was on the =click= event, filtered to
touch by testing whether the event was a =PointerEvent=, which is a browser
detail rather than a guarantee. Where the click arrives as a plain mouse event
the filter rejected it, the handler returned without preventing the default, the
slot followed its own link, and a new tab from a gesture the browser had not
classified as one is silently blocked. Everything now hangs off pointer events
from end to end, which say what kind of pointer they are by definition: a press
under four hundred milliseconds that has not travelled more than ten pixels is a
tap, a longer one belongs to the reminder popup, and the press is acknowledged
the moment a finger lands rather than when the gesture is decided.

Rows take =user-select: none= and =touch-action: manipulation= on coarse
pointers only, so a tap cannot start a selection or a double-tap zoom, while a
mouse can still select a destination or a time to copy. Links inside the sheet
are ordinary anchors with nothing between the tap and the navigation, and the
handler that closes the sheet on an outside pointer ignores any pointer that
started inside it: it used to run first and take the anchor out of the document
before the browser got as far as following it.

A sheet is bound to the departure rather than to the element it was opened from,
so a refresh no longer closes it. The board is rebuilt from scratch several times
a minute and the element the sheet came from does not survive its own
explanation; the replacement claims the open sheet by the same key, and the
content is rebuilt in place only when the journey actually changed. An
explanation with a thirty second life expectancy through no fault of the reader's
was the single worst thing about the page on a phone.

Clicking the slot on a desktop, or an "open" link in the sheet on a phone, opens
=route.html= in a new tab: one row's journeys in full,
as vertical timelines. It takes its whole state from the URL fragment, as
base64url of a small JSON object, which is why it opens instantly, opens
underground, and cannot disagree with the board it came from. A fragment rather
than a query string because a fragment never leaves the browser. The cost is
that a link is a snapshot, so the page says when it was planned and carries a
button that plans that one row again and rewrites the fragment.

*** Where the train goes after it leaves

A row names a line and a terminus, and at a junction neither answers the
question a rider actually has, which is whether it stops at the place they are
going to. The sheet therefore carries the run's remaining calls with the time it
reaches each of them, the first few and then a control that unfolds the rest.
Times as well as names, because "does it stop there" is almost always followed
by "and when would I be there", and the pair also says how long the ride is,
which nothing else on the page does.

It is the last thing in the sheet, under the journey, and it is short. The
reader opened the sheet to choose a train and the journey is that choice; where
the train calls afterwards is what confirms it. Put above the journey, as it
first was, and long enough to be useful, the list pushed the journey past the
bottom of a sheet that is capped at a fraction of the screen. The journey was
still there and still drawn, one scroll down inside the sheet, which reads
exactly like it having been taken away. The count it collapses to is named in
=src/page/board.ts=.

Asked only when something asks. That is one request per vehicle and a board is
two hundred rows, so nothing is fetched until a sheet opens on a particular
departure or a pointer rests on its time. The answer is remembered for the life
of the page under the row's key, and so is a failure to find one: a run that
nothing could identify at half past four is still unidentifiable at half past
four, and re-asking on every render would be a request loop with a spinner on
top. The signature the board computes for every row to decide whether an open
sheet is still current therefore peeks at what is known rather than asking,
because asking there would start a lookup for every row on the board, which is
the one thing this arrangement exists to prevent.

A regional service also carries the first calls beside its times on the row
itself. Only a regional one: a rapid-transit line calls everywhere and its next
two stops tell a reader nothing they did not know, while a regional service
calls only at the places worth naming, so its next two calls are the difference
between the train that runs through the centre and the one that turns off before
it. Where the board already filters by a place the vehicle must call at, those
runs have been fetched and the hint costs nothing further.

Rows whose backend publishes no trip identifier are recognised in the
aggregator's own view of the same stop, by the cascade described under "One run,
seen twice". The filter there is stricter about an ambiguous match than this is,
and for a good reason: it is deciding whether to hide a departure, while this is
deciding what to print on one that is staying either way.

**** Four reasons a sheet has no calls, and one sentence each

"Where this run goes after here is not published for it" used to be the answer
to every one of these, which made a real fault indistinguishable from an
ordinary gap in the data, and it hid one for months. So each cause now says what
it is, because the reader holding the phone is the only person who can tell
which one they are looking at.

The aggregator lists no stop times at this stop at all. The aggregator lists
them and none of them is this departure. The run was identified and no stop
sequence is published for it. Or a request did not arrive, which says nothing
about the run: that one is retried once before it is believed, kept only for an
interval named in =src/page/calls.ts= rather than for the life of the page, and
asked again after it rather than on every render.

The fault the fourth sentence uncovered was none of those. A station whose
parent identifier the aggregator does not carry answers 404 for it, and the
departures path threw on that 404 before it reached the fan-out over the
station's platforms that exists precisely for this case: the fan-out sat behind
a check for an EMPTY list, and a stop that 404s never produces one. Every row of
every board at such a station therefore had no onward calls, no aggregator rows
to filter a via clause against, and no timetable half beyond the live horizon,
while the journey planner at the same station worked perfectly, because it asks
the resolution chain directly and hands it the platforms the rows came from.
Measured on the live configuration: thirty five of fifty two rows on one profile
had no onward calls, and none do now.

A 404 on the parent is therefore an answer rather than a failure, and the
platforms the primary feed already named on this stop's rows are passed to the
chain as hints, so the fan-out covers the platforms the board actually uses
rather than whichever single one a reverse geocode happens to return. Anything
that is not a 404 still fails, because a rate limit quietly turned into an empty
board is a board that lies about the service.

*** Nothing moves that did not change

Skeleton rows are a promise that something is coming, and they are the right
answer exactly once: the first time a board is drawn with nothing in it. After
that the board has real rows, and replacing them with grey bars on every refresh
takes information away in order to show that work is happening, which the
progress line already says without moving anything. "Nothing in the window" is a
claim about a completed answer and is never made while a fetch is in flight; a
board that is merely slow used to look like a board that was over for the night.

A board also keeps the DOM it has when nothing it draws has changed. The page is
built around rendering the whole thing from state, which is what makes it
impossible for two parts of it to disagree, and the cost was a visible flash
twice a minute for no new information at all. So every board is drawn to a
signature of everything it reads: its departures down to the minute and the
delay, its status, its journeys, its view, its filters, and the clock at minute
granularity, because whether a row is still catchable is decided per render
rather than by the tick. Equal signature, same DOM, and the open sheet and any
selection inside it survive.

*** What the reader is holding onto

A refresh lands every half minute whether or not anything on screen changed, and
it used to take four things with it: the sideways scroll of the bar's control
strip, the page's own scroll, the focus in a field, and the field's popover. The
strip was the one that was noticed, because the start-time controls sit at its
far end and reaching them is a deliberate act that was undone before it could be
used. All four have one cause, and the cause is in none of the four: rendering
the whole page from state ended in =replaceChildren= on the root, and taking an
element out of the document, even for the instant it takes to put it back,
resets its scroll offsets and blurs whatever inside it had focus. None of that is
state the model holds, so nothing put any of it back.

The rule now is that a data update never re-creates a control the reader can be
in the middle of using. It has four parts, and they are separate because the
four things were lost in four different places.

The root's children are reconciled rather than replaced. A node already in the
right position is not touched at all, which is the ordinary case: the bar, and
every board whose signature has not moved.

The bar is built once and patched from then on. It was the one part of the page
that really was rebuilt on every render, so no amount of care further down could
have saved the strip's scroll: the strip was a different element each time.
Patching means text nodes, classes and disabled states; a list is replaced only
when what it lists changes, which for the tabs is the configured profiles and
for the jump chips is the set of boards. Two controls are left alone while they
have focus, the destination menu and the start-time field, because writing a
value into a control somebody is using is the same bug in miniature.

The filter popover is built once per open session. It is the only part of this
page made of controls that are operated in place rather than tapped once, and it
is attached to a board, which is the thing that redraws. It is rebuilt only when
what it lists changes shape, meaning a new line appeared at a stop or the board
gained its journeys. Which lines are hidden is deliberately not part of that,
because the box the reader just clicked is exactly the one a rebuild would take
away from them; those are patched instead.

Focus is restored across the whole sync, and it is read before anything is
built. That ordering is the whole trick: the popover is moved into the freshly
built board while the new nodes are being assembled, so the blur happens well
before anything reaches the screen, and code that reads =activeElement= just
before swapping the nodes in finds the body and concludes nothing was focused.
The restore passes =preventScroll=, because scrolling to reach the element it is
refocusing would take away the other thing the reader owns.

A sheet keeps its scroll too, in the one case where its content is genuinely
rebuilt under it. The rebuild happens because the journey it describes changed,
which is real, but the new text is usually the same sentence with one number
different, and starting it again from the top loses the reader's place for a
reason they cannot see.

The harness scrolls the strip to its end, scrolls the page, opens a popover,
puts focus in a field inside it, then changes what the fixture says and asks for
a refresh, and insists that all four are where they were. It insists on the
refresh as well: the rows must actually have changed, or the assertions would
pass against a page that had done nothing.

*** A journey slot that had an answer never goes blank

The report was that journey slots empty out when a refresh starts and stay empty
until the new plan lands, and the obvious reading of that is a race: the page
refreshes every half minute, a search takes seconds, so a second search overlaps
the first and the two fight over the same slots. Watching the real page for two
and a half minutes said something else. Row identities were stable across
refreshes, plans came back in well under a second from the planner's own cache,
and one row in fifty lost its journey for forty-one seconds while everything
around it kept one. Forty-one seconds is the remainder of a minute plus the next
search, which is the signature of the planner's cache expiring and the next
search answering differently, not of two searches at once.

So there are two problems, and they need separate fixes.

The first is that a journey search is a search rather than a lookup. The
aggregator answers for the itineraries it found in the window it looked at, and
a row at the edge of that window drops out of one answer and returns in the
next. A run used to build its map of journeys from scratch, so a row the newest
search did not answer for had its journey removed, and the slot went blank as if
there were no way to get there from that train. Now every run is merged onto the
one before it, per row: a row the new search answered for takes the new answer,
a row it left out keeps the one it had, and, the case the harness caught, a row
the search did answer for by saying it found nothing also keeps the one it had.
That last case is the same blank slot arriving by a different route, because the
row was in the answer, just empty. What the fresh run always contributes is the
departure itself, so a carried journey is drawn against a train whose delay is
current.

A carried answer is dated with when it was found rather than when it was last
asked about, which is what lets it age: past =ROUTE_AGEING_MS= the row is dimmed,
and its sheet says the journey was found some minutes ago and that the last
search did not offer one. Nothing is carried across a change of destination,
because those journeys answer a different question, and a stale truth may be
shown where an answer about somewhere else may not.

The second is the race, which was not the cause but is real. There is now one
search per profile at a time. A refresh that lands mid-search is remembered
rather than started, however many land, and one follow-up runs when the search
finishes. A search whose question has been replaced, by the reader choosing a
different destination for instance, is cancelled outright with an =AbortSignal=
that reaches the fetches inside it, and what it had already put on screen stays
there until the new run replaces it row by row.

Testing this needed one thing that is easy to get wrong. Three refreshes in a
row against a fixture prove nothing, because the planner keys its own cache on
the minute a search starts and the minute its horizon ends, so three refreshes
inside one minute are one question asked three times and answered twice from
memory, at memory speed and with the answers it gave the first time. No search
runs long enough to be overlapped and no answer ever differs. The harness moves
the reader's start time on by a minute per round instead, which is a question
the planner has not been asked, while leaving the departures alone so the rows
keep their identity. Against a planner made slow and made to answer nothing, it
samples every row ten times a second and insists that no row that had a journey
is ever seen without one, and it reads the page's own search accounting to
insist that no two searches for one profile ever overlapped and that the
refreshes which landed mid-search were folded rather than run. The accounting is
read from the page rather than counted at the network for the same reason the
start time has to move: a search answered from memory makes no request, so
counting requests cannot see a search at all.

*** Destination badges in the strip

A strip is one line per line and direction and one cell per departure, which is
what makes it a glance. Branching services broke that: a run terminating short
of the others had its destination spelled out after every time, the row wrapped,
and the rhythm was gone.

Where a group's runs all end in the same place the header says so and nothing is
repeated. Where they do not, every time carries a two or three letter badge and
the header itself is the legend: it names each destination with that
destination's badge in front of it, so the group costs one line rather than two
and the reader never has to look below the times to find out what a letter meant.
The letters are the initials of up to
three significant words of the destination, filler words dropped, and collisions
are resolved by lengthening the first word rather than by adding a digit,
because the extra letters still name a place. The colour comes from the
destination's alphabetical rank within the board, so it is stable across
refreshes; how saturated and how light it is belongs to the stylesheet, which is
the only thing that knows the colour scheme. A badge never borrows the line's own
colour, because the line badge beside it already carries that.

*** Which platform a strip group leaves from

A platform is a property of the group far more often than it is a property of a
departure. Ten trains on one line in one direction almost always leave from the
same piece of concrete, and printing that number against every one of them is
ten times the ink for one fact, on the row whose whole purpose is to be read at a
glance.

So the group carries it once, in the same corner badge a row uses, drawn neutral
rather than by state because a group has no single state. The number is the most
common platform among the group's times, and only a time that leaves from
somewhere else is marked, beside its own time. A group whose feed publishes no
platform at all gets no badge, which is the honest answer and not an empty box:
the empty box belongs to a row, where the badge also carries the colour, and a
group's badge carries nothing but the number.

*** A platform the departure feed does not publish

The primary backend leaves the platform blank for whole categories of service at
some stations, most of them the surface ones, and the corner badge was then empty
for every one of them. The aggregator had the number all along, on its own stop
times row for the same run.

So a row with no platform of its own borrows one: the aggregator's row matched to
the same departure, and failing that the run's own record of this station. The
borrowed number is kept apart from the feed's own, in its own field, because the
two are not the same claim and only one of them is what the operator is saying
right now. The page draws either, since a reader asking which platform does not
care which service answered, but nothing downstream may mistake a borrowed number
for a published one.

** Freshness, caching and installing

The last good result for every profile is mirrored into IndexedDB and rendered
immediately on load with its age, then refreshed. Switching tabs shows the cache
at once and refreshes only when it is older than a glance. While a fetch is in
flight a board shows skeleton rows and a progress line naming the backend and the
page number.

A board that has answered cannot go back to loading. That sounds like a detail
and it was a bug a reader lived with: the first board on the screen showed a full
list of departures with a progress line under it claiming it was still on page
one, for the whole visit. Two boards on that profile share a stop, and progress
was attributed to whichever board mentioned the stop first, so the second board's
fetch of the shared stop reported under the first board's name minutes after the
first board was done. Nothing takes a progress line back off the screen except
the board's own answer, and that answer had already been given. Progress for a
stop no board asked for is now dropped rather than charged to the first board,
the stop a board changes at counts as that board's, and a board that has answered
ignores anything that arrives afterwards.

The shell is two pages now, the board and the expanded journey view, and they
share =theme.css=: the palette, the type, the line badge and everything a
journey is drawn with. Two copies of a palette drift, and these two are on the
same screen a tap apart.

The page ships a web manifest and a service worker, so it installs as a
standalone app. The worker caches the shell and deliberately not the departures:
a worker that served stale departures would do it silently, with no age and no
way for the page to know, which is the one failure this page exists to avoid. The
departures come back from IndexedDB instead, with their age on screen.

*** A shell change that does not change the worker is invisible

A browser decides whether to install a new service worker by comparing that
worker's own bytes. Nothing else is consulted. So a deploy that rebuilds the page
and leaves the worker file identical is a deploy an installed client never
notices: it keeps the cache it has, keeps answering from it, and shows a version
that no longer exists anywhere on the server. There is no error, no warning and
nothing on screen that differs from a page that is simply up to date, and
checking that the server is serving the new bytes says nothing at all, because it
is.

That happened here, twice in a row. Two rounds of fixes were published, both
verified on the server, and the phone kept showing the bugs they had fixed.

So the worker's cache name carries a hash of every shell file, written in when
the page is published. A changed shell then cannot leave the worker unchanged,
which turns the failure from silent into impossible. The same hash is stamped
into both pages as a build id, readable from the filter popover and from the
tooltip on the bar's backend label, and exposed as =window.__BUILD__= so a test
can assert which build is running. An unpublished checkout carries the
placeholder instead and reports no build id, which is true: it was never
published.

The page also asks the browser to check for a new worker on every load rather
than waiting for its own schedule, which is measured in hours, and when one
arrives it offers the reader a reload instead of taking it. Reloading underneath
somebody reading a departure time is worse than being one version behind for a
few more seconds.

The touch harness has a test for exactly this: it publishes one build, installs
the worker, publishes a second build that differs only in the stamp, and asserts
that the reader is offered the reload and lands on the second build. Removing the
hash from the worker makes that test fail, which is the only evidence worth
having that it is testing anything.

*** What may be cached, and who is allowed to write it

Only responses that are =ok=, of type =basic=, and whose final URL is on this
origin. The first condition alone is not enough on a site behind an access gate:
an expired session answers a request for the shell with a redirect to a login
page, and following that redirect produces a perfectly successful response that
is not this page. Cached, it would replace the app with a login screen that
outlives the session it belonged to, and would keep being served offline.

Those three conditions used to be checked at fetch time, because the worker
answered from the cache and then refreshed the entry behind the reader, one file
at a time. One file at a time is the whole bug, and it is worth stating plainly
because it cost a reader two days of a broken page.

*** Half a shell is worse than an old one

A browser holds the page, the stylesheet and the script as three separate cache
entries. A worker that refreshes them independently can therefore end up holding
one of each from two different deploys, in one cache, under a cache name that
still claims to be a single shell. That is what happened: a phone opened the page
during a deploy, kept its old worker, and that worker replaced whichever files
that visit happened to touch. What came out was a board drawn by one build and
laid out by another.

That does not degrade politely. The rows ran off the side of the screen so the
whole page panned sideways, the sticky bar was cut off, the state word spilled
out of a badge the older stylesheet had nowhere to put, and the destinations were
squeezed to four characters. Nothing on the server was wrong for a moment of it,
which is why every check against the server passed while the reader was looking
at it.

Three things now stand between a reader and that.

The worker's cache is written by exactly one thing: the install step, which
writes every shell file together or writes none of them. Nothing is revalidated
at fetch time, and a shell file that is missing from the cache is fetched without
being written back. A new version therefore arrives only as a new worker, and a
worker either has a whole shell or it has nothing. Being one open behind is the
price of never being half a build, and it is a much better trade than it sounds:
the page already asks for a new worker on every load and offers the reader the
reload.

The two pages link their script and their stylesheet with the shell version in
the URL. Two builds then do not share a URL for those files, so no cache
anywhere, the worker's or the browser's own, can serve one where the other was
asked for. It is not cache busting in the usual sense, which is about freshness;
it is about making a mismatched pair unnameable.

The page and the script each carry a build id, stamped separately at publish
time, and the page compares them before it draws anything. If they disagree, it
asks the worker to update and reloads once, which is the repair for a mixture
that got into a cache before either of the defences above existed. If the
disagreement survives that reload it is the server's and not a cache's, so the
page says so in the console and carries on rather than reloading for ever. The
flag that makes it once rather than for ever is per tab and remembers which pair
it reloaded for.

The harness proves both halves: one mixed shell that the server can repair, where
the page must come back reloaded and on one build, and one the server cannot,
where the page must reload once, give up and draw itself. A marker set after the
rows appear is the loop detector, because a second reload would wipe it.

** Reminders and disruptions

A long press on a row opens a reminder popup: an optional "keep walk time"
allowance, a set of lead times, and a set button. Reminders are re-pointed at the
updated expected departure on every refresh, which is the point of them, and they
are best effort while the page is open. That is said on the popup rather than
implied.

Disruption notices are collapsed by default, filtered to the lines that are
relevant to the visible profile, and can be narrowed further by chips or
acknowledged until their text changes. Relevant means both the lines the profile
pins and the lines its boards are actually showing. Pinned labels alone are not
enough: a board that filters by category rather than by line pins nothing, so a
profile made of rapid-transit boards matched no notice at all, which is exactly
the profile where a notice matters most. They can be copied out in one go with a translation
instruction in front, or translated in place.

Translation runs by itself when the browser has an on-device translator and the
reader's own interface is not already in the notices' language, and the
translation then becomes the body of the notice with the operator's own words one
tap away, per notice rather than per panel. Automatic only for the on-device
translator: it is free and nothing leaves the machine, so doing it unasked costs
the reader nothing. The paid provider stays a button, because it spends the
reader's money and sends the text to a third party, and neither is a thing to do
on somebody's behalf. Its key lives in local storage on that device and nowhere
else.

*** One translation, shared between the browsers reading the page

Every reader's browser used to translate the same dozen notices, and the ones
using the paid provider paid for it each time. They are pooled now, through the
planning server, which stores what any client produced and hands it to the next.
The server never translates on the page's behalf from a key of the page's: the
reader's own key stays in the reader's own browser, which is the rule that has
never had an exception here. A server may hold a translation credential of its
own, placed on that machine by hand, and then it translates a notice once for
everybody; a server without one relays and nothing more. Either way the page
behaves the same, and a page with no server at all, which is what the tailnet
copy is, behaves exactly as it did before any of this existed.

The identity of a notice is =src/message-hash.ts=: its text trimmed, every run
of whitespace collapsed to one space, SHA-256, lowercase hex. Both ends import
that one module, which is the point of it. Two implementations of the same rule,
one of them in another process, agree until somebody edits one of them, and the
symptom would be a cache that silently stops hitting. Normalising first is not
cosmetic either: the two upstreams wrap a notice at different widths and disagree
about the non-breaking space, and without it a feed that gained a trailing
newline overnight would invalidate every translation anybody had paid for.

The flow on the page is in =src/page/messages.ts=. When the notices arrive, every
hash the panel is about to render is asked of the server in one request, and
whatever comes back is written into the same IndexedDB cache the page's own
translations live in and rendered before any local translation is attempted. What
this client then produces, by the browser's translator or by the Gemini button,
is offered back once per hash. What it received is never offered back: a received
translation carries the kind of client that made it, and re-asserting somebody
else's work under this page's name is exactly what the server's precedence rule
exists to prevent. The lookup and the offer both go through the data source in
=src/page/source.ts=, where the direct source implements them as finding nothing
and offering nowhere, and they are deliberately not routed through the fallback
that demotes the page off the server: a rate-limited translation offer says
nothing about whether the server can still plan a journey, and losing the boards
over one would be a poor trade.

The line under a translation says where it came from: translated on this device,
translated by another client with the kind of client after it, or translated by
server. The reader's judgement of a translation depends on which: an on-device
translator is a small model doing a hard job on a phone, and a notice full of
line names and platform numbers is where it comes apart.

** Selections

The countdowns are patched once a second by rewriting single text nodes, not by
re-rendering, and the tick skips its work entirely while a selection is live
inside a board. A full render every second would destroy a selection in progress,
and copying a time or a destination off the page is a thing people do.

* Line colours

A badge is coloured from =data/line-colors.json=, a table of the operator's own
per-line artwork. It is generated by =scripts/colors-refresh.ts=, which
=bun run colors:refresh= runs, and the result is committed rather than fetched
at boot: the browser page has no business downloading a timetable archive to
draw a badge, and a committed table makes a colour change a reviewable diff.

The generator downloads the transit association's network-wide GTFS archive,
reads only =routes.txt= and =feed_info.txt= out of it, and writes the table
sorted by line label and carrying no retrieval timestamp, so a regeneration
that finds an unchanged feed produces byte-identical output. The feed version
identifies the release instead. The archive URL is in the script, which is the
only place to look it up.

The feed is published under Creative Commons Attribution, so anything that
redistributes this table has to carry the credit. The generator writes the
publisher's required credit line and the feed version into the generated file
itself, where they travel with the data instead of sitting in a readme that a
copy of the file might not bring along.

That feed encodes one colour per operator rather than per line, so every rapid
transit line in it arrives as a single network green and every underground line
arrives as a filler colour its operator prints on nothing. The generator drops
the filler and reapplies a small hand-checked table of the two rail networks'
real per-line colours, which is the last hand-maintained colour data in the
package. It reports every line where the two disagree, so a feed that starts
carrying genuine per-line artwork shows up instead of being silently
overridden.

Resolution order for a badge background is the generated table first, then the
colour the backend supplied for that departure, then the category fallback in
=src/colors.ts=. The table goes first because it is the operator's own artwork
and changes only when the operator changes it, whereas a backend's colour
varies from feed to feed and has been seen to disagree with the printed colour
for the same line. The printed one is what a rider reads off a platform sign.
Where the table also names a foreground it wins over the contrast computation;
where it does not, black or white is picked against the background.

Only the category fallbacks are emitted as CSS custom properties. The table
holds too many lines for one property each to be worth building and parsing on
every load, and nothing reads them anyway: both renderers ask =src/colors.ts=
directly.

* Icons

Every icon on the page is an inline SVG symbol, defined once in a sprite and
referenced with =use=, sized in em and painted with =currentColor=.

They used to be characters, and that failed in the worst way a thing can fail:
silently, and only on somebody else's device. The walking figure that says "and
then you walk" is in a Unicode block Android's system font does not carry, so on
the phone this page exists for it rendered as an empty box, while looking
perfect on the machine it was written on. No test that runs here could have
caught it, because the font is not here.

A glyph is a request that some font, somewhere, happens to have a picture. An
SVG is the picture. The live and planned discs were in the sprite for one round and are gone: the
state is a colour on the corner badge now, and a colour needs no picture.

Text punctuation is deliberately not in the sprite: an arrow
between two stop names, a middle dot between two facts, an ellipsis on a
shortened name. Those are words, not icons, and they live in blocks every system
font covers.

* Timing

A refresh records where its time went, and the record is shown in the filter
popover and logged to the console: time until there were rows, time until the
journey slots filled, the planner's share, the last render, and per board how
long its departures took and how many upstream pages they cost.

It is on the page rather than in a profiler because the device the question is
about is a phone, and a phone has no profiler. Numbers measured on a laptop on a
wired connection answer a different question from the one a reader is asking
when they say it feels slow.

** What asking past the edge costs

The extension is not free and the harness measures the price rather than
estimating it. The three things that could have used it were priced separately,
under four times CPU throttling and a slow mobile connection, on the same
fixtures.

Telling the journey search to cover through a later instant is a number in a
request and costs nothing measurable. Reaching past the horizon at an interchange
costs one stop's extra pages, and only on the boards that declare one: time until
the journey slots are filled goes from about 2.75 s to about 2.82 s. Fetching the
board's own stops past the horizon was the expensive one, and it was almost the
entire bill: a board's departures fetch went from about 650 ms to about 1260 ms
and the journey slots to about 3.39 s. The primary backend pages at roughly forty
minutes of departures per request, so the shape is no surprise: a one hour picker
was asking for a little over an hour and started asking for several.

That third fetch is gone, which is why the numbers above are the ones the page
runs at now. It was paying to page a board three times over so that rows could
arrive and never be drawn, and the planning it was meant to support turned out
not to read them: the planner is told how far to reach, and the interchange
lookup asks for itself. Time to the first rows does not appear in any of this,
because that is one round trip on a slow link and no amount of later fetching
changes how long the first answer takes to arrive.

** Asking once, and asking together

A profile's boards are fetched all at once rather than one after another. They
are independent questions and the reader is waiting for the slowest one either
way, so asking them in turn only added the others' time to it.

Requests are shared by promise rather than by result. A cache stops a second
request only if the first has already finished, and on this page the common case
is not "asked again later" but "asked twice in the same instant": two boards at
the same stop, two boards planning to the same place, a prefetch overlapping the
profile on screen. The first caller starts the work and everyone who arrives
before it finishes waits on the same promise. Each one gets its own copy of the
rows, because boards annotate what they receive and two boards sharing objects
would show each other's annotations.

The same applies one layer down, to the journey searches and to the probe that
works out which identifier the planner will accept for a stop.

Everything is capped: so many departure requests in flight, so many timetable
requests, so many journey searches. Uncapped, a long horizon across several
profiles turns one refresh into dozens of simultaneous requests against free
public services, and a rate-limited board looks to a reader exactly like a
broken one.

* The touch harness

=bun run e2e= drives the built page in a headless browser at a phone's size,
with device metrics and touch emulation on, and every network answer served from
fixtures committed beside it. It uses real touch events rather than calling
=click()=, because the bug it exists to catch was precisely that the page
listened for the wrong kind of event: a synthetic click proves nothing about
what a finger does. It skips itself with a message where no browser is
installed, and it serves the built directory over a local server rather than
reaching for a deployed copy, so it is offline and repeatable.

Run it before every deploy. The layout pass that preceded it measured pixels and
never tapped anything, and everything it missed was a bug that only exists under
a finger.

** The same work, done once, near the page

A phone opening this page asks the two public APIs about every stop on every
board, and then asks the journey planner about every commute board, and pays
for a fresh connection each time because the phone is the slowest link in the
chain. Every one of those questions has the same answer for everybody who asks
it in the same minute. So the page can also be answered by a small server
running beside it, doing exactly that work once and keeping the answers warm,
and then one request replaces all of them.

The page does not choose between the two at build time, because the same bytes
are served from a host that has such a server and from one that does not, and
an installed copy on a phone may be either. So there are two implementations of
one interface, in =src/page/source.ts=. The DIRECT source is this package doing
the work in the browser, which is what the page has always done and what it
still does everywhere else. The SERVER source turns the same three questions
into requests to an API mounted beside the page.

At startup the page probes the server's health endpoint with a short deadline,
alongside the fetch of its own configuration rather than before it, so the
probe costs nothing on a host where there is no server to find: the two are one
round trip to the same place and the slower of them is the configuration. A
request that then fails, for any reason, moves the page back to doing the work
itself, at once, and it tries the probe again some minutes later. Falling back
is not an error state and the reader is never shown one: a page that has fallen
back is the page as it has always been, and the only thing that changes is the
provenance line in the timing note, which says either "via server, N s old" or
"worked out here".

Two details are less obvious than they look.

A =Map= does not survive =JSON.stringify=. It becomes ={}=, with no error
anywhere, and the journeys are held in maps two levels deep. So there is a wire
format, in =src/page/wire.ts=, which is the same data with its maps written as
pairs, and both ends import it from there rather than each parsing what the
other writes. A server and a page that agree about a format by coincidence stop
agreeing the first time a field is added.

Carrying a journey forward happens on the phone, not on the server. The server
has no idea what is on this reader's screen, so what it sends is what it found
this time, plus a list of which boards it set out to plan. That list is what
lets the page apply the same rule to a server's answer that it applies to its
own searches: a board the run could not answer for keeps what it had. Both
paths go through one function for that, because two implementations of a rule
like this would drift apart within a week.

The server itself is not in this package, and deliberately: it needs the
configuration with the places in it, which is private, and it is deployed as
part of a page rather than as part of a library. What is here is the client
half, the wire format, and the pieces it composes, which are the very functions
the page calls. The server calls =fetchProfile= and =planProfile= exactly as
the page does, so the answer it hands back is the answer the phone would have
computed.

*** Measuring what it is worth

=test/e2e/server.ts= starts both halves itself, a planning server on one
loopback port and a static server on another that proxies the mount to it the
way the deployment does, then loads the page under a throttled phone profile
and measures the time to a journey on screen with the server and without it. It
needs the directory the page and its server live in, from the environment,
because this package is public and the address of somebody's page is not.

Two things it found, both of which looked exactly like the page refusing to use
the server:

The intercept pattern =*/api/*= matches the upstream transit APIs as well.
Both of them have =/api/= in their own paths, so a check that meant to pause
the page's requests to its own server paused all hundred and thirty requests to
theirs, and turned a two second page load into a twenty second one. Every
number in that run was wrong and none of them looked wrong.

bun's =fetch= decodes a compressed answer by default and leaves the
=content-encoding= header on it. A proxy written the obvious way therefore
hands the browser decoded bytes labelled as gzip, and every request through it
dies with =ERR_CONTENT_DECODING_FAILED=, which the page sees as a network
failure and responds to by falling back. The fix is one option; the lesson is
that the check's own scaffolding is code too, and it had no tests.

*** Checking that a translation is only paid for once

=test/e2e/share.ts= is the other harness that needs a real planning server. It
runs the page twice against one, with the browser storage cleared in between so
the second run is a different reader rather than the same one looking at its own
cache again, and it replaces the browser's Translator with one that counts its
calls. The assertion is that the second reader's counter never moved and that
the text on its screen is the first reader's. Counting rather than timing, on
purpose: a page that translated the notice quickly and a page that was handed
the translation look identical on screen, so a timing assertion here would pass
for the wrong reason forever.

A third pass points the page at a second planning server that has a translation
credential, and asserts that no reader translates anything at all and that the
credential was spent once rather than once per reader. Its translation endpoint
is overridden to a loopback stand-in this harness serves itself. Nothing in this
package may call a paid API from a test, and the alternative to a stand-in was
leaving the tier that spends money as the one tier with no end-to-end check.

It builds its own page directory into scratch space from the working tree,
writes a fixture configuration into it, and serves the notices from a stand-in
for the departure backend. The notices go through the stand-in rather than being
injected into the browser because the server can only translate a notice it
fetched itself: a fixture that exists only inside the page is a fixture the
server has never seen.

** bun runs code it has not checked

Every harness entry point type-checks before it runs, and so must anything
written for a single run. That is not tidiness. bun executes TypeScript by
stripping the types, so a call with the wrong number of arguments is not an
error, it is a parameter bound to =undefined= and another bound to whatever was
passed in its place.

What that cost, once: a throwaway reproduction script called the harness's
Chrome cleanup with one argument instead of two, so the parameter holding the
profile *directory* received a process object, which becomes =[object Object]=
as a string. It went to =pgrep -f= as a pattern, matched every process whose
command line contained any of those letters or a space, and the loop sent
=kill -9= to each in turn. It killed the ssh agent, the window manager, a
database, a terminal multiplexer serving other sessions, and the Finder, and it
killed its own shell as well, which looked like a crash and was retried twice.
Three sweeps for one missing argument.

The cleanup is now built so that the same mistake cannot reach a process list:
the directory is checked before anything is killed and must be an absolute path
under the harness's own scratch root, the listing is matched against that
literal string with =includes= rather than handed to a tool that would read it
as a pattern, and the sweep refuses to return its own process or its parent.
=test/sweep.test.ts= passes it the exact wrong argument that caused this and
insists it throws. But the check in front of every run is what would have caught
it in the first place, so it is the first step of every one of them.

It builds the bundles itself, as the first thing it does. The directory it
publishes contains a build artefact that is not in version control, so a fresh
checkout has none of it and a working tree has whatever the last build left
behind. Both are silent: the run goes green against the previous bundle, which
is a harness reporting on code that is no longer in the tree. That happened
here, and it cost a round of assertions that proved nothing about the change
they were written for.

It measures the layout twice, the second time in a font deliberately wider than
this machine's. A phone renders =system-ui= as Roboto, which is wider than what
runs here, so any width budget derived from a measurement taken here is a budget
for the wrong font. That is not a hypothetical either: a row measured as fitting
exactly, to the pixel, on this machine overflowed on the phone. Verdana is wider
than Roboto, so a layout that survives it survives the phone, and forcing it is
better than guessing a margin.

The consequence for the page is that no column's width may be a measurement of
text. The fixed tracks are all in rem, which is a constant; a slot whose width
could only ever be a measurement of somebody else's font was taken out of the
grid instead, which is what happened to the live mark and to the platform. Every
fixed text cell is also clipped, so that a cell whose text is wider than its
track cannot paint across its neighbours, which is a kind of overflow no browser
reports.

Where a cell does have to hold text, the harness measures it against a sample
rendered in that cell's own font rather than against a character count, in both
passes: the destination must hold twelve characters of a long station name, the
countdown column must be as wide as two digits and no wider, and both of the
countdown's long shapes, the widest hours-and-minutes form and the hours-only
one, must fit that column at the size the step-down class gives them.
A character count would be a different number of pixels in every font, which is
the mistake this whole section exists to stop making.

The countdown's probe clones the real cell and adds the class, rather than
building a span and copying font properties onto it. The sizes under test are
the stylesheet's own, so the probe has to inherit the same cascade the cell has;
a probe assembled from =getComputedStyle= measures what the harness believes
instead of what the page draws, which is exactly how the previous version of
this assertion passed while the column was seventeen pixels too narrow.

It also asserts what is deliberately not in the grid: the corner badge must be
out of the flow, flush to the row's top and right edges, with its text centred in
it, and every row's track count must equal the number of children the grid
actually places. That last one is how a slot that quietly came back would be
found.

It loads the route page too, rather than only reading the href of the links that
point at it. That view became a render function that two callers share and its
styles moved into the shared stylesheet, and both of those are refactors that
break a page in a way nothing else here would notice.

Where a control has to be reachable, it is tapped rather than driven. The
overlay's back control is a case in point: closing it through the history passed
while tapping it did not, because the sheet underneath dismisses itself on any
pointer it does not own, so the reader came back to a board instead of to where
they were. A test that calls the function the button would have called proves
the function and not the button.

It also measures a refresh with the processor slowed to a quarter and the
network held to a slow mobile connection, and prints what it found. Two limits
are worth stating: the fixtures are fulfilled through the debugging protocol, so
the emulated bandwidth does not apply to them the way it would to a real
response, and the processor throttle is a multiplier on this machine rather than
a model of any particular phone. What it does measure honestly is whether the
page waits for its requests one after another or all at once.

It also runs the page once as the installed app, by overriding the standalone
media query before the document loads, which is the only way to get there: no
protocol call puts a page in standalone, and the page asks the question once, on
the tap. That pass checks that the expanded view opens over the board, that it
pushes exactly one history entry, that nothing was opened in a tab, and that
going back closes the overlay and leaves the sheet where it was.

Four things it is worth knowing about writing assertions here. Service workers
must be bypassed or the run measures the previous deploy rather than the build
in front of it. A regular expression inside an evaluated template literal needs
its backslash doubled, because a template literal eats the first one and =\s=
silently becomes the letter =s=, which is a passing test that measures nothing.
A probe that copies a cell's font must copy the longhands one at a time and
never the =font= shorthand: that shorthand serialises to the empty string
whenever a longhand it does not cover is at a non-initial value, and the
countdown cell sets =font-variant-numeric=, so the assignment did nothing, the
probe measured at the page's own size, and the assertion passed while the
countdown was clipping its leading digit on a wider font. An assertion that
measures the wrong thing is worse than no assertion, because it is also a
claim that somebody checked.
And a tap that opens a second tab must close that tab again before the run
continues: a browser that has moved its foreground elsewhere can
leave the next evaluation waiting for a reply that never comes, which looks
exactly like a slow test rather than a hang.

** The smoke check, which is the only thing that looks at the live page

=test/e2e/smoke.ts= loads the page that was actually deployed, at a phone's
width, with real upstream data and no fixtures, and it is the last step of a
deploy rather than a thing anybody remembers to run. The URL comes from the
environment, because this package is public and the address of somebody's page
is not.

It exists because the harness and the server checks between them still missed a
page the reader could not use. The harness asks whether the code behaves, against
fixtures it ships with; the server checks ask whether the bytes arrived. Neither
can see a browser holding two builds at once, an upstream that changed shape, or
a proxy in front of the site. So this one asks the only question left: does the
thing at the end of the URL still look like a departure board.

It checks that the shell reports a build id, that nothing overflows a 390 pixel
viewport, that every row keeps its children inside itself, that the state badge
is in each row's corner, that no row draws a state word outside the cancellation
flag, that no progress line is still on screen once the boards have loaded, and
that a destination can show twelve characters of a real station name. It saves a
full-length screenshot named after the build, which is what a report should
carry instead of an assurance.

The progress-line check waits rather than reading once, and it matches the class
those lines carry rather than their words. The wording changes with the backend
and the page number, and a check written against one phrasing quietly stops
covering the other one.

* Knobs

Every tunable value lives in exactly one place in the code, which is the only
place to look it up. The horizon, the default backend and fallback, the
transport types, the time zone and the default walking time are in
=src/config.ts=. The request timeout and the user agent are in =src/http.ts=. How many trip
lookups a via filter may have in the air at once is in =src/trip.ts=, and how far
apart two feeds may time one run and still be recognised as one run is in
=src/via.ts=.
The page cap that stops a pathological stop from being walked forever is in
=src/backends/types.ts=, the primary backend's rows-per-page limit is in
=src/backends/mvg.ts=, and the per-request row counts for the aggregator are
in =src/backends/transitous.ts=. The aggregator's address and the shape of its
stop identifiers are in =src/aggregator.ts=, which exists as its own module so
the origin resolver and the backend that uses it are not an import cycle. Both
cache lifetimes are in =src/cache.ts=.
The boundary between the near window and the strip view is in
=src/format/terminal.ts=, along with how many journeys a row prints. The walking
pace, the early buffer, the plan cache lifetime, the itineraries asked for per
request, the bounds on the search window, the page cap and the options kept per
row are all in =src/plan.ts=, and the transit modes a journey may use and what a
walked minute costs are in =src/config.ts= with the other defaults, as is how
far a target stop may be from the place it is offered as a way of reaching. The
abbreviations used in slots too narrow for a full place name are a single
constant in =src/page/dom.ts=, and the filler words a destination badge drops
are one in =src/page/badges.ts=. How many of a run's onward calls a sheet names
before it offers the rest, and how many a regional row's own hint names, are in
=src/page/board.ts=. How long a pointer rests before a tooltip opens,
how long a press may last and how far it may travel and still be a tap, and the
width below which the tooltip becomes a sheet, are all in =src/page/tip.ts=; the
length of the long press that opens the reminder popup instead is in
=src/page/notify.ts=. The
watch interval, the discovery sample count and the key the commute view pairs
with the home profile are in =src/cli.ts=, and the page's refresh and tick
intervals are in =src/page.ts=.

The cache connects using =REDIS_URL= when it is set. Failing that, a local
server that wants a password is reached with the credential in =REDISCLI_AUTH=,
the variable the standard Redis client already uses, so no password ever needs a
home in this package or its config. Any cache failure degrades to a miss and is
reported once; it never fails a command.

The backend base URLs can be overridden with =MVG_BASE_URL= and
=TRANSITOUS_BASE_URL=, which is also how the fallback path is exercised.

* Etiquette

Both APIs are free, undocumented and offered for private, non-commercial use at
moderate request rates. Neither sends a rate-limit signal, so nothing will warn
you before you become a problem for them; there is no back-pressure to react to
and no quota header to watch.

Design for few, on-demand requests. The defaults here already do: the page only
refreshes while someone is looking at it, the paging loop stops as soon as it
has covered the horizon and is capped besides, the cache is there for when you
poll, and there are no retries anywhere. A failing primary backend is asked
once and then the fallback is asked once. If you add a feature that fetches on a
timer, ask first whether it can fetch on demand instead.
