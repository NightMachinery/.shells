#+TITLE: transit
#+OPTIONS: toc:2

* What this is

A departure-board library with two front ends: a =bun= command-line tool for
the terminal, and a browser bundle for a small phone page. Both are built from
the same modules, so a board looks the same and filters the same way in either
place.

It talks to two public transit APIs. One is the city operator's own service,
which is authoritative for the urban network and is the default. The other is a
national aggregator carrying the same stop identifiers, used as a fallback when
the first one fails, and selectable outright. Neither needs an API key.

It also plans journeys, for the boards that ask it to. A board that opts in
carries, on every row, the journey that departure starts and when it gets you
there. See *Journey planning* below.

* Installing

#+begin_src sh
cd javascript/transit
bun install
#+end_src

The only dependency is the TypeScript compiler, and it is only needed for
=bun run typecheck=. Running the CLI and building the page work from a bare
checkout.

Run the tool as =bun src/cli.ts <command>=. Run the tests with =bun test=, the
type checker with =bun run typecheck=, and the browser bundle with
=bun run build=.

* Configuration

The config is TOML. The CLI looks at =$ADDRESS_CONFIG= first and falls back to
=~/.address-config/address.toml=. A missing file at that conventional location
is not an error: profiles are simply unavailable and raw stop ids still work.
A path you name yourself, through =--config= or the environment variable, must
exist.

Validation collects every problem it finds and reports all of them at once,
each naming the profile, the board index and the field, so a broken config does
not turn into a sequence of one-error-at-a-time runs. Any validation failure
exits with the config status code.

A generic example, with placeholder identifiers throughout. Every key is
optional and the values shown are illustrative rather than the defaults, which
live in the code:

#+begin_src toml
[defaults]
horizon_minutes = 90
backend = "mvg"
fallback = "transitous"
transport_types = ["SBAHN", "UBAHN", "TRAM", "BUS", "BAHN", "REGIONAL_BUS"]
timezone = "Europe/Berlin"
home = "first"

[places.somewhere]
lat = 0.0
lon = 0.0

[profiles.first]
title = "First"

[[profiles.first.boards]]
title = "Rapid transit, one way"
stops = ["de:00000:1"]
modes = ["SBAHN", "BAHN"]
direction = "H"
walk_minutes = 6

[[profiles.first.boards]]
title = "Two nearby stops merged"
stops = [{ id = "de:00000:1", label = "Near" }, { id = "de:00000:2", label = "Far" }]
lines = ["X1", "X2"]
destinations = ["^Somewhere", "Elsewhere$"]
walk_minutes = 4
walk_minutes_by_stop = { "de:00000:1" = 2, "de:00000:2" = 9 }
#+end_src

Profile keys are arbitrary short words. Nothing in the package assumes any
particular key exists.

** The home alias

=defaults.home= optionally names one profile key. =board home= then resolves to
that profile, but only when no profile is literally called =home=: an exact key
match always wins. No other name is aliased. If =defaults.home= names a profile
that is not declared, that is a validation error naming the field.

** Per-stop walking times

=walk_minutes= is the walking time to the board's stops and defaults to zero. A
board that merges two stops can override it per stop with
=walk_minutes_by_stop=, because a single board-wide figure is simply wrong when
the two stops are different distances from the same front door: it would dim the
near stop's departures too early, or leave the far stop's looking reachable when
they are not. Every key must be one of that board's stops, values must be
non-negative whole minutes, and reachability is computed per row from the
walking time of the row's own stop.

** Stop labels

A stop may be written either as its bare identifier or as a table with an =id=
and an optional =label=. The label is a short human name, a word or two, and it
is what the multi-stop row tag and the walk summary show. Without one they fall
back to the last field of the identifier, which is a number: readable enough to
tell two platforms apart, useless for telling a reader *which* platform. Labels
are per board, so the same stop can be =Wkz= on one board and something else on
another.

** Onward connections

A board may name one interchange it feeds into:

#+begin_src toml
connection = { stop = "de:00000:9", lines = ["X9"], direction = "H", ride_minutes = 3, transfer_minutes = 5 }
#+end_src

Every row then carries the first departure at that stop which a rider leaving on
that row could still catch, computed as the row's own departure plus the ride and
the transfer. The two figures are static, and that is a deliberate first cut: a
per-departure figure needs a journey lookup for every row, which is a different
order of request volume against a free API, and for a fixed pair of stops the
static pair is right to within a minute or two.

=direction= is optional, for an interchange where the line only runs one way.
An empty slot on a row means the board has an interchange and nothing at it was
catchable from that row, which is information rather than a gap.

** Places

=[places.<name>]= holds coordinates for the =nearby= lookup. They are not part
of any board and they are deliberately excluded from the exported config unless
you ask for them.

* Commands

=board <profile|stop...>= renders a profile's boards, or an ad-hoc board for
one or more raw stop ids. An argument that matches no profile key and does not
have the shape of a stop id is rejected with the list of configured profile
keys, rather than being forwarded upstream where it would come back as an
opaque not-found for something you never typed.

=discover <stop>= lists every (line, direction letter) pair seen at a stop over
the horizon, with a few sample destinations for each. This is how you find the
letter a board should filter on.

=search <query>= searches stops by name and prints their identifiers.

=nearby <lat> <lon>= lists stops near a coordinate.

=messages [profile]= prints service messages. Given a profile, it keeps only
messages concerning lines that profile's boards name; a profile whose boards
pin no lines narrows nothing.

=route <profile>= is the commute view: for every departure on that profile's
commute boards, the journey it starts, where you change and when you arrive.
=--to <profile>= names the far end. See *Journey planning*.

=config-export= prints the loaded config as JSON for the browser page.

** Flags

=--json= switches to the machine-readable document. =--cache= turns on the
Redis response cache, which is off by default. =--horizon <minutes>= overrides
how far ahead to look. =--backend <name>= forces the primary backend.
=--watch= clears the screen and re-renders on an interval until interrupted.
=--no-color= suppresses colour, as does an unset terminal or the =NO_COLOR=
environment variable. =--config <path>= reads a different config file.
=--with-places= adds coordinates to =config-export=. =--to <profile>= and
=--early-buffer <minutes>= belong to =route= and are described under *Journey
planning*. =--verbose= logs every outbound request to standard error, which is
how you confirm that a long horizon really did page. =--help= prints the command
list.

Exit status is zero for success, one for a runtime error, and two for a config
problem, which includes an unknown profile name and a commute with no
destination.

* Direction letters

Grouping a board by destination does not work: one direction of one line can
carry several different headsigns, so a destination-shaped grouping splits one
direction in two and merges nothing back together. The primary backend's line
identifier is a colon-joined tuple whose fourth field is a single letter naming
the direction, and that letter is consistent. The package reads it there, and
emits no direction at all rather than guessing when the identifier is malformed.

Use =discover= on a stop to see which letter goes which way, then put that
letter in the board's =direction=.

The aggregator has no such letter. It has an outbound flag, which this package
maps onto the same two letters. That mapping has *not* been verified against the
primary backend on the same stop, and the module says so. If it is ever found
not to hold, flip =TRANSITOUS_DIRECTION_TRUSTED= in
=src/backends/transitous.ts= to false: the aggregator then emits no direction on
any row, a =direction= filter drops all of its rows, and =destinations= filters
have to do the narrowing instead.

* Filters

A board's filters are applied in a fixed order: modes, then lines, then
direction, then destinations. The order is fixed so that a board producing
nothing can be debugged by peeling filters off from the bottom. A board with no
filters shows everything.

Line comparison ignores whitespace and case, so a label written with a space
between the category and the number matches the same label written without one,
in both directions. Destinations are regular expressions matched
case-insensitively against the headsign, and any one of them matching is enough.

The direction rule is blunt on purpose: a board that sets =direction= keeps only
rows carrying exactly that letter, and a row whose direction is unknown is
dropped along with the wrong-way rows. Keeping unknowns would let a backend that
supplies no letter quietly turn a one-way board into a both-ways board, which is
the failure that is hardest to notice.

* Fetching and paging

The primary backend answers with at most =MVG_PAGE_LIMIT= rows, and it applies
that cap /before/ the transport-type filter. The two together mean the size of a
response says nothing at all about the stop: a busy interchange can hand back a
full page of raw rows that narrows to a handful, and a page that arrives short
may be short only because the cap fell somewhere upstream of the filter. A
paging loop that stopped on a short page would therefore truncate exactly the
boards a long horizon was asked for.

So the walk is driven by time and never by counts. Each request names an
=offsetInMinutes=, the newest row in the response sets the next offset, and the
walk ends when that row reaches the horizon, when a page comes back empty, or
when the offset will not move any further. The last of those is what stops a
stop whose paging is stuck from being asked forever, and =MAX_PAGES= caps the
whole walk regardless. The price of not counting rows is one extra request
against a stop that really has run out, which is what its final page costs.

The next offset is rounded /down/ to the minute the newest row falls in, not up
to the one after it. Rounding up starts the next page strictly after that row
and loses whatever the cap had cut off later in the same minute, and no amount
of de-duplication recovers a row the server was never asked for. Rounding down
re-requests that minute instead, and the rows that come back twice are dropped
on a key built from the line identifier, the planned time, the destination and
the label.

The transport-type list is never omitted from a request. With no explicit list
the API silently drops regional rail and regional buses, so a board configured
for them would come back plausibly populated and quietly wrong.

A board that declares =modes= narrows the request to those categories, which is
still an explicit list and merely a shorter one. That keeps the page limit spent
on rows the board can use rather than on five categories it is about to delete.
The narrowing is intersected with the configured transport types and so can only
ever shrink them; a narrowing that intersects to nothing issues no request at
all, since an empty list would read as no list. The board's own mode filter
still runs on the result, because a backend is allowed to ignore the hint and
must not be able to widen a board by doing so.

The aggregator pages by following a cursor instead, and the endpoint used here
carries no category parameter, so a narrowing there changes only what is kept.
Its per-request row count is sized from the length of the window.

* Journey planning

A board says when vehicles leave. It does not say which of them gets you to the
other end soonest, and at a stop served by four lines that is the question
actually being asked. =route <profile>= answers it: for every departure on that
profile's commute boards, the journey that starts with that departure, where you
get off, what you catch there, and when you arrive.

A board takes part only if it says =commute = true=. Planning is a much heavier
question than a departure board, one request per board per refresh against a free
service, and most boards are not journeys anybody plans: they are "is there a bus
soon". A profile whose boards all decline says so and exits zero rather than
failing.

The destination is =--to <profile>=, and the coordinate is that profile's entry
under =[places.<name>]=. The name is resolved as a profile first and as a place
key second, because the far end of a commute often has no boards of its own and
therefore no profile. Without =--to= there is one rule and no further guessing:
from the home profile the destination is the =work= key, and from =work= it is
the home profile. Anything else has to say where it is going, and a name that
resolves to no place exits with the config status code, naming what was looked
for.

** Matching an itinerary to a departure

An itinerary belongs to a board row when its first timetabled leg carries the
same line and leaves in the same minute, at the same platform. Not the trip
identifier: the departure board and the planner do not share one. The board's
rows come from whichever backend answered and carry that backend's identifiers,
and even on the aggregator a board row is a stop time while an itinerary leg is a
trip, with nothing in either response linking the two.

Which minute is the whole difficulty. The *timetabled* minute is the one both
sides agree on, because it is the same timetable. The expected minute is not: the
board and the planner carry separate live feeds, and they disagree by a minute or
more whenever anything runs late. Matching on the expected minute alone silently
emptied every delayed row while the punctual ones planned fine, which is the kind
of failure that looks like a coverage gap rather than a bug. The expected minute
now only backs the timetabled one up, for a row whose backend publishes no
scheduled time.

The platform is there because line and minute are not unique, and the exception
is the case that matters most. A stop whose two directions hang off one parent
identifier can run the same line at the same minute each way, and one S-Bahn line
was observed doing exactly that, leaving for the city and leaving for the country
in the same minute. Without the platform check the outbound row was handed the
inbound journey, which is the worst answer this package can give: plausible, and
pointing at a train going the other way. A row or a leg that names no platform is
not held against it, since a stop with no platforms has one direction per
identifier and cannot collide.

An itinerary whose first timetabled leg starts at some other stop is not this
board's journey and is dropped. A leading walking leg is normal, though, and is
skipped over to find that first leg: the planner will walk you onto a platform
inside the station you named.

** Exits, walks and the early buffer

The interesting part of a matched itinerary is where its first leg puts you down
and what leaves from there. Every itinerary the planner returns ends at the
destination, so any tail of any itinerary also ends there, and a tail observed
after one first leg can be spliced onto another that alights at the same place.
That recombination is the point: the planner returns only changes it considers
feasible, so taking its itineraries as they came would never surface a change it
had already ruled out.

It rules them out with a transfer time that is not a walk. Measured on the live
service, the street legs at the two ends of a journey come back at a steady pace,
but the walks *between* two transit legs do not: the same service billed one
interchange at under two minutes for a hundred and eighty metres and another at
five minutes for a hundred and fifty. The difference is the minimum transfer time
the timetable carries for that station, which is a property of the station rather
than of the rider, and it is what makes a change look impossible when it is
merely inconvenient. So the transfer walk is derived from the leg's own
=distance= at =WALK_METRES_PER_MINUTE=, the single place this package turns a
distance into a time, and the planner's walking =duration= is never read.

The feasible change is then the first leg's arrival plus that walk. Onward
departures up to =DEFAULT_EARLY_BUFFER_MINUTES= *before* it are offered as well,
marked *tight*: they come off only if the first vehicle runs a little early or
the change is quicker than the pace assumes. A tight option is never the
recommended one. It is shown so a rider can decide to run for it, not so the tool
can gamble on their behalf, and the recommendation is always the soonest arrival
among the options that are not tight. =--early-buffer <minutes>= moves the line;
at zero the tight options disappear entirely. In the terminal the marker carries
the verdict without colour, so the distinction survives a terminal that has none.

=MAX_OPTIONS_PER_ROW= caps what a row carries and =ROUTE_OPTIONS_SHOWN= caps what
the terminal prints of it, both in =src/plan.ts= and =src/format/terminal.ts=
respectively. Everything past the first few arrives later than something already
on screen.

** Paging, caching and gaps

The planner pages by cursor, like the aggregator's departures. =numItineraries=
is honoured and widens the search window rather than truncating a fixed one, so
=ITINERARIES_PER_REQUEST= usually covers a whole board in one request and the
cursor walk is the exception. The walk ends when the itineraries reach the last
row being planned, when a page comes back empty, when the cursor stops moving, or
at =PLAN_MAX_PAGES=. The cap is there for the same reason the departure backends
have one: a free service with no rate-limit signal gets a bounded walk rather than
an unbounded one. Coverage is measured only on itineraries that actually start at
the board's stop, so one that walks off to a neighbouring stop cannot declare the
board covered.

A plan is reused for =PLAN_CACHE_MS=, keyed on the origin, the destination and
the minute it started from. A page refreshing twice a minute must not re-plan
every time, and within a minute nothing about the itineraries changes but the
delays. The early buffer is deliberately not part of that key: it only changes
how itineraries already in hand are recombined.

Rows that show no journey are common and usually mean what they say. The planner
returns optimal journeys rather than every journey, so a departure that nothing
else beats is returned and one that something else beats is not. The early part
of a window is sparser than the rest for the same reason. A board configured with
a stop identifier only the primary backend carries cannot be planned at all,
since the planner is the aggregator; that board's departures are still shown and
the reason is reported once per stop. The aggregator is also *asked* only once
per origin: a 404 on the origin is remembered without an expiry, because it says
the identifier does not exist rather than that this moment was a bad one, and a
board that re-asked an unanswerable question twice a minute for as long as a tab
stayed open would be a rude thing to point at a free service. Every other
failure stays retryable.

** The route document

=route --json= emits =schema_version=, =profile=, =requested_profile=,
=destination=, =early_buffer_minutes=, =generated_at= and =boards=, in the same
snake_case and ISO instants as the rest of the JSON contract. =destination= names
the far end by key and by name and carries no coordinates: the coordinate was the
input, and this package keeps geography out of what it prints.

Each board carries its title, its stops, its walking times, its labels, its
backend, and =rows=. A row carries the departure, in exactly the shape =board
--json= gives it, then =best= and =options=. =best= is the recommended journey or
null; =options= is every journey found for that row, tight ones included, sorted
by arrival, so a consumer that disagrees about what to recommend has the material
to decide for itself. Each journey names its exit stop by identifier and by name,
its arrival, how many changes it involves, whether it is tight, and its legs.

* The JSON contract

=board --json= emits a document carrying =schema_version=, =profile=,
=requested_profile=, =generated_at= and =boards=. =profile= is the key actually
rendered and =requested_profile= is what was typed, so a consumer can tell when
the home alias was followed; both are null for an ad-hoc board built from raw
stop ids.

Each board carries its title, its stops, its walking time and any per-stop
overrides, the backend that answered, and its departures. The board-level
backend is a single name when every stop on that board was answered by the same
one and the string =mixed= otherwise; every departure also carries its own
backend, so the mixed case is still readable.

Each departure carries the line label, the mode, the destination, the scheduled
and expected times as ISO instants, the delay in minutes, the cancelled and
replacement-service flags, the platform, the direction letter, whether it is
catchable, the walking time used to decide that, its backend, its stop, and a
short stop tag. The tag is non-null only on a board with more than one stop,
where it is the only thing distinguishing two otherwise identical rows. Each
board also carries =stop_labels=, the label map, or null when the board declares
none.

=config-export= emits =schema_version=, =defaults=, =backends= and =profiles=.
It carries *no* timestamp. The page repository refreshes this file by re-running
the exporter and committing the result, and a timestamp would make every run
produce different bytes, turning an unchanged config into a commit. Coordinates
are omitted unless =--with-places= is passed.

* The browser page

=bun run build= bundles =src/page.ts= into =page/app.js=. The bundle imports
only the model, the filters, the backends, the colours and the HTTP helper; it
never touches the cache module or anything else that needs the bun runtime, and
the build is deterministic.

=page/index.html= is a generic shell: a title, the whole stylesheet, an empty
mount point and a script tag. It contains no stop identifiers, no coordinates
and no hostnames, because a separate private repository copies it in alongside
its own =data/config.json= produced by =config-export=. The page fetches that
file relative to itself on load.

The page renders one tab per configured profile, in config order, titled from
each profile's title, and remembers the selection in local storage inside a
try/catch so a browser that refuses storage still works. It refreshes only while
the document is visible, ticks its countdowns locally in between, and on a failed
refresh keeps the last good data and says so.

** Three states per board

A board is *integrated*, *full* or *collapsed*, and integrated is the default.
Integrated is a strip of times, one line per (stop, line, direction), which
answers "when is the next one and how often" in a glance. Full is one row per
departure, for when the platform, the delay and the onward connection matter.
Collapsed is for a board that is not relevant today but would be annoying to
delete from the configuration. Clicking a board's title cycles the three, and the
choice is remembered per profile and per board title.

There is no separate "later" section any more. One board is one state, and the
integrated view covers the whole horizon.

** The row grid

A row is a grid of fixed slots: minutes, line badge, destination with its times,
the onward connection, the journey to the destination, the platform, whether the
time is live or a plan, a reminder marker, and the stop label. A slot is empty when the value is absent and
nothing shifts, so the eye can run down one column.

Which *optional* slots exist is decided per board rather than globally: the
platform column appears only when that board's rows actually carry platforms, the
connection column only when the board declares an interchange, the journey
column only when that board is being planned, and the stop column only when the
board merges stops. The upstream feed reports a platform for
rail and never for surface transport, so a globally fixed platform column would be
dead space on most boards.

The expected time is the headline and the planned time follows it in parentheses
when the two differ, because a departure eleven minutes late is a different thing
from one always scheduled for then. Delay and cancellation are carried by weight
and by a struck line as well as by colour, so they survive a monochrome screen.

** The bar

Sticky, and it carries the profile tabs, one jump chip per board with that
board's next departure, the horizon picker with the resulting end time, the start
time, the refresh control with its age and progress ring, and the name of
whichever backends answered. The chips count only the rows a board is actually
showing, so a chip never promises a departure the board's own filter is hiding.

The start time is either *now*, which moves with the clock, or a moment the
reader picked. With a picked moment every row is labelled a plan, because there
is no live data for a train that has not been dispatched yet.

On the desktop: the number keys switch profiles, =r= refreshes, =[= and =]= step
the horizon, and =f= toggles the board under the top of the viewport between full
and integrated. All of them are ignored while typing in a field.

** The commute view on the page

The same planner the =route= command uses runs in the page, for the boards that
say =commute = true=. The bar gains a destination picker listing the configured
places, remembered per profile, and each planned row gains a journey slot: where
to get off the first leg, the short chain after it, and the arrival time.

The slot is worth a column only because of the comparison it makes possible. The
exit stop a line usually uses is computed from the board's own rows rather than
configured, and a row whose best exit differs from that usual one is marked, so
the signal is "this one is better off somewhere else" rather than the same advice
on every row. An optional sort orders a planned board by arrival instead of
departure, which is the order the question is actually asked in.

A cancelled row is never given a journey, at any layer. The planner works from
the timetable and does not always know a vehicle has been withdrawn, and a
recommendation to board a train that is not running is worse than no
recommendation.

The board's own filter carries the tight-connection window, because it changes
what one board shows and means nothing on the others. It is held in memory and
deliberately not persisted: it is a "show me what I would have to run for"
question about one look at one board, and a persisted one would quietly widen
every plan for weeks after the reader forgot they had touched it. Moving it
re-plans without re-fetching, which is nearly free, because the window is not
part of the plan cache key.

Plans are never written to the offline cache, unlike the departures. A stale
departure is obvious, since its countdown is wrong and the row says how old the
data is. A stale arrival time is not: it looks exactly like a fresh one, and it
is the number a reader acts on.

** Freshness, caching and installing

The last good result for every profile is mirrored into IndexedDB and rendered
immediately on load with its age, then refreshed. Switching tabs shows the cache
at once and refreshes only when it is older than a glance. While a fetch is in
flight a board shows skeleton rows and a progress line naming the backend and the
page number.

The page ships a web manifest and a service worker, so it installs as a
standalone app. The worker caches the shell and deliberately not the departures:
a worker that served stale departures would do it silently, with no age and no
way for the page to know, which is the one failure this page exists to avoid. The
departures come back from IndexedDB instead, with their age on screen.

** Reminders and disruptions

A long press on a row opens a reminder popup: an optional "keep walk time"
allowance, a set of lead times, and a set button. Reminders are re-pointed at the
updated expected departure on every refresh, which is the point of them, and they
are best effort while the page is open. That is said on the popup rather than
implied.

Disruption notices are collapsed by default, filtered to the lines that are
relevant to the visible profile, and can be narrowed further by chips or
acknowledged until their text changes. Relevant means both the lines the profile
pins and the lines its boards are actually showing. Pinned labels alone are not
enough: a board that filters by category rather than by line pins nothing, so a
profile made of rapid-transit boards matched no notice at all, which is exactly
the profile where a notice matters most. They can be copied out in one go with a translation
instruction in front, or translated in place by the browser's own translator when
it has one and by a paid provider when the reader supplies a key. The key lives in
local storage on that device and nowhere else.

** Selections

The countdowns are patched once a second by rewriting single text nodes, not by
re-rendering, and the tick skips its work entirely while a selection is live
inside a board. A full render every second would destroy a selection in progress,
and copying a time or a destination off the page is a thing people do.

* Line colours

A badge is coloured from =data/line-colors.json=, a table of the operator's own
per-line artwork. It is generated by =scripts/colors-refresh.ts=, which
=bun run colors:refresh= runs, and the result is committed rather than fetched
at boot: the browser page has no business downloading a timetable archive to
draw a badge, and a committed table makes a colour change a reviewable diff.

The generator downloads the transit association's network-wide GTFS archive,
reads only =routes.txt= and =feed_info.txt= out of it, and writes the table
sorted by line label and carrying no retrieval timestamp, so a regeneration
that finds an unchanged feed produces byte-identical output. The feed version
identifies the release instead. The archive URL is in the script, which is the
only place to look it up.

The feed is published under Creative Commons Attribution, so anything that
redistributes this table has to carry the credit. The generator writes the
publisher's required credit line and the feed version into the generated file
itself, where they travel with the data instead of sitting in a readme that a
copy of the file might not bring along.

That feed encodes one colour per operator rather than per line, so every rapid
transit line in it arrives as a single network green and every underground line
arrives as a filler colour its operator prints on nothing. The generator drops
the filler and reapplies a small hand-checked table of the two rail networks'
real per-line colours, which is the last hand-maintained colour data in the
package. It reports every line where the two disagree, so a feed that starts
carrying genuine per-line artwork shows up instead of being silently
overridden.

Resolution order for a badge background is the generated table first, then the
colour the backend supplied for that departure, then the category fallback in
=src/colors.ts=. The table goes first because it is the operator's own artwork
and changes only when the operator changes it, whereas a backend's colour
varies from feed to feed and has been seen to disagree with the printed colour
for the same line. The printed one is what a rider reads off a platform sign.
Where the table also names a foreground it wins over the contrast computation;
where it does not, black or white is picked against the background.

Only the category fallbacks are emitted as CSS custom properties. The table
holds too many lines for one property each to be worth building and parsing on
every load, and nothing reads them anyway: both renderers ask =src/colors.ts=
directly.

* Knobs

Every tunable value lives in exactly one place in the code, which is the only
place to look it up. The horizon, the default backend and fallback, the
transport types, the time zone and the default walking time are in
=src/config.ts=. The request timeout and the user agent are in =src/http.ts=.
The page cap that stops a pathological stop from being walked forever is in
=src/backends/types.ts=, the primary backend's rows-per-page limit is in
=src/backends/mvg.ts=, and the per-request row counts for the aggregator are
in =src/backends/transitous.ts=. Both cache lifetimes are in =src/cache.ts=.
The boundary between the near window and the strip view is in
=src/format/terminal.ts=, along with how many journeys a row prints. The walking
pace, the early buffer, the plan cache lifetime, the itineraries asked for per
request, the page cap and the options kept per row are all in =src/plan.ts=. The
watch interval, the discovery sample count and the key the commute view pairs
with the home profile are in =src/cli.ts=, and the page's refresh and tick
intervals are in =src/page.ts=.

The cache connects using =REDIS_URL= when it is set. Failing that, a local
server that wants a password is reached with the credential in =REDISCLI_AUTH=,
the variable the standard Redis client already uses, so no password ever needs a
home in this package or its config. Any cache failure degrades to a miss and is
reported once; it never fails a command.

The backend base URLs can be overridden with =MVG_BASE_URL= and
=TRANSITOUS_BASE_URL=, which is also how the fallback path is exercised.

* Etiquette

Both APIs are free, undocumented and offered for private, non-commercial use at
moderate request rates. Neither sends a rate-limit signal, so nothing will warn
you before you become a problem for them; there is no back-pressure to react to
and no quota header to watch.

Design for few, on-demand requests. The defaults here already do: the page only
refreshes while someone is looking at it, the paging loop stops as soon as it
has covered the horizon and is capped besides, the cache is there for when you
poll, and there are no retries anywhere. A failing primary backend is asked
once and then the fallback is asked once. If you add a feature that fetches on a
timer, ask first whether it can fetch on demand instead.
