#+TITLE: claude_session

Renders Claude Code session transcripts (=~/.claude/projects/**/*.jsonl=) into
org-mode or markdown, and scans a directory of them for the fuzzy session
picker. The zsh wrappers live in =zshlang/auto-load/others/claude-session.zsh=.

Standard library only, so =go build= needs no network and no module cache. It
works on a freshly bootstrapped, sudoless host.

* Install
#+begin_src zsh :eval never
go-install-local "${NIGHTDIR}/golang/claude_session"
#+end_src

Registered in =setup/setup_go=, so a full setup run installs it. The zsh
wrappers also install it on first use via [[agfi:ensure-dep1]], so a fresh clone
works without a separate step as long as Go is present.

* Test
#+begin_src zsh :eval never
claude-session-selftest
#+end_src

That runs =go test= plus the parity check below. The Go tests alone:
#+begin_src zsh :eval never
cd "${NIGHTDIR}/golang/claude_session" && go test ./...
#+end_src

The parity test needs real transcripts and pandoc, so it is skipped unless
pointed at a corpus:
#+begin_src zsh :eval never
CLAUDE_SESSION_CORPUS=~/.claude/projects go test -run Parity ./...
#+end_src

* Commands

=claude_session render [flags] <session.jsonl>= writes the transcript to
stdout. Flags:

- =-format md|org|org-pandoc= --- output syntax. =md= (the default) is meant to
  be piped through pandoc; =org-pandoc= does that internally and in parallel,
  and is what the zsh wrapper uses; =org= emits org directly without pandoc and
  is only a fallback, since message bodies stay markdown.
- =-max-block-lines N= --- elide code blocks longer than N lines, leaving a
  =… [N lines elided]= marker. =0=, the default, never elides.
- =-diff= --- render =Edit= tool calls as a unified diff. On by default.
- =-subagents= --- inline the transcripts of spawned subagents. On by default.
- =-jobs N= --- worker count, defaulting to the CPU count.
- =-pandoc PATH= --- the pandoc binary to use for =org-pandoc=.

=claude_session name <session.jsonl>= prints the session's name, or nothing if
it has none. Claude Code names a session several ways, in increasing order of
authority: a generated slug like =sharded-bouncing-clarke=, an =ai-title=
summarising the work (=fix-org-store-link-title=), a =custom-title= the user
set (=Neru=), and =agent-name=, which is the name Claude Code itself resolved
from those. Names can be revised during a session, so the last wins; a slug
never changes. 39 of 52 local sessions have a slug and 28 have a title; the
rest predate the features and fall back to their uuid.

=agent-name= is preferred when present, so a future title source is picked up
without changing this code. It cannot replace the explicit precedence, though:
only 19 of the 28 named sessions carry one. Where both exist they agree, on all
19 --- and adding it changed no name anywhere in the local corpus.

That precedence lives in one place, the =nameParts= accumulator in =list.go=,
and is reached two ways. =name= reads the whole file forwards and feeds every
record to it. =list= feeds it the records its tail scan is already decoding for
the timestamp, reading backwards. Both end in the same =resolve=, so the name in
the picker's column and the name a viewer writes into a filename cannot drift
apart. The direction only decides which occurrence to keep: the last one written
is the last met reading forwards and the first met reading backwards, which is
what the =keepFirst= flag of =observe= selects.

The two differ in reach. =list= widens its tail window in search of a title only
up to =nameWindow=, one MiB (the Performance section says why); the slug does not
count as having found one, since it rides on nearly every message record and so
proves nothing about how far back the scan has looked. A title written more than
a megabyte before the end of the transcript is therefore beyond the column,
which shows the slug instead. Measured over all 119 local sessions across both
profile roots, including the 26MB ones, the column and the full =name= scan agree
on every single one. The cap is a theoretical limit here, not an observed one.

The org header uses it, and so does the filename the viewers write, so a
session opens in emacs as =Neru.org= rather than a uuid:

#+begin_example
,#+TITLE: Neru
,#+SUBTITLE: Claude Code session 3e500e15-2d94-44c6-bac4-4d6634c743f6
#+end_example

=claude_session list [flags] <sessions-dir>...= walks the directories for
=.jsonl= files and writes one TSV line per session, newest first: =epoch=,
absolute path, local time, the session's name, path relative to the scanned
directory, and the first user message as a snippet.

The name sits before the relative path on purpose. The relative path runs to
about fifty characters (=.claude-work/-Users-evar-scripts/87e1476d-….jsonl=),
which would push a name placed after it off the right edge of an ordinary
terminal, and seeing the name without scrolling is the whole point of the
column. A session with no name leaves the field empty; its uuid is in the
relative path either way.

More than one directory may be given, and they are merged and sorted together
rather than listed one after another. Claude Code keeps a projects directory
per config home, and [[agfi:claude-work]] runs a second one, so a single root
would leave every work session invisible.

With several roots the relative path is prefixed by a label, because it is
otherwise ambiguous --- every profile holds a =-Users-evar-scripts/=. The label
is the first path component in which the roots *differ*: =.claude= and
=.claude-work= for the profile roots, and still those two when the caller
scopes each root down to a single project, where the last component is the same
for both and the parent is =projects= for both. A single root is listed exactly
as before, with no label.

- =-snippet-len N= --- snippet width cap, default 120.
- =-name-len N= --- name width cap, default 40.
- =-subagents= --- also list subagent transcripts. Off by default: =render=
  inlines them into their parent, and they were a third of the list.
- =-jobs N= --- worker count.

* Document structure

A transcript is not rendered record by record. Claude Code writes one JSONL
record per content block, so a single assistant turn arrives as a run of
records that would otherwise become a run of near-identical headings.
Consecutive records sharing a role are merged into one turn heading, which
carries the first timestamp. Sub-headings inside the turn show their own
timestamp only when it falls in a different minute, and show the full date as
well when the turn crosses midnight.

Tool results are nested under the call they answer, matching =tool_use.id=
against =tool_result.tool_use_id=. This matters because results are not really
user messages: the wire format sends them back to the model as user turns, so
rendering them literally produced a =* User= heading nobody wrote, sitting next
to --- but not under --- its call. Records containing nothing but results now
produce no heading at all. A result whose call is missing from the transcript
still renders where it sits, and a user record mixing results with typed text
keeps its heading for the text.

Together these collapse a 4.5MB session from 1182 top-level headings to 34, one
per conversational turn:

#+begin_example
,* User [2026-08-10 Mon 10:22]
,* Assistant [2026-08-10 Mon 10:22]
,** Thinking
,** Tool Use: Bash · Verify LaTeX delimiters
,*** Result: ok
,** Tool Use: Edit · ~/x.zsh [10:24]
,*** Result (error): Exit code 1
#+end_example

A result that is a single line of 72 characters or fewer goes on its heading
rather than into a block; an empty one reads =Result: (no output)=.

Assistant turns carry the model that produced them, shortened for repetition:
=opus-5=, =fable-5=, =haiku-4.5=, and =synthetic= for the messages Claude Code
writes itself, such as interruption notices. Merging stops at a model change,
so a switch mid-answer starts a new heading instead of hiding inside one --- 8
of 52 local sessions use more than one model, and 3 of 297 merged turns would
otherwise have spanned two. Annotating sub-headings instead was the
alternative, but a plain text block has no heading to annotate, so a switch
landing there would go unrecorded.

* Events

A transcript is not only messages. These record types are rendered too, each
attaching to the turn it interrupts:

- *Recap* --- the summary Claude Code writes when you step away
  (=system/away_summary=). 83 locally.
- *Notice* and *Model fallback* --- =system/informational= and
  =system/model_consent_fallback=, the latter explaining a model switch
  ("Switched to Sonnet 5 for this session · Fable 5 requires usage credits").
- *Command* --- a slash command you ran (=system/local_command=). The payload is
  the same =<command-name>= scaffolding the picker strips, so it reduces to
  =** Command: /model=.
- *Pull request* --- =pr-link=, with the number, repository and URL.
- *Edited outside the session* --- =attachment/edited_text_file=, a file you
  changed in your editor mid-conversation, with the snippet Claude was shown.
  77 locally, and they explain changes Claude did not make.
- *Context compacted* --- =system/compact_boundary=. This one stands alone
  rather than attaching to a turn, since it separates two phases of the
  conversation: =* Context compacted [2026-08-06 Thu 16:25] · manual · 476980 →
  11820 tokens=.
- =system/turn_duration= is not a section. It measures the turn before it, so it
  lands in that turn's heading as =· 4m2s=.

- *Task reminder* --- =attachment/task_reminder=, the outstanding task list.
  Rendered only when it has items. All 485 locally are empty (identical
  56-byte records with =content: []=), because the task tools go unused here,
  but a populated one is worth reading rather than dropping.

Deliberately left out, all of it bookkeeping: =mode=, =permission-mode=,
=agent-color=/=agent-setting=, =bridge-session=, =file-history-snapshot= and
=-delta=, and =last-prompt=, which only repeats the message beside it.
=system/stop_hook_summary= is dropped because it never carries content --- 0 of
225 locally. The remaining =attachment= payloads are harness internals
(=skill_listing=, =deferred_tools_delta=, =output_style=, =plan_mode=).

=agent-name= is not a section either, but it is not discarded: it feeds the
session name, above.

=queue-operation= is left out for a subtler reason. Half of what gets enqueued
is delivered and therefore already appears as an ordinary user message, so
rendering it would duplicate; the other half was withdrawn before it was ever
sent. 49 of 96 local enqueues fall in the first group.

* Subagents

Claude Code stores a subagent's transcript beside its parent, at
=<session-uuid>/subagents/agent-<id>.jsonl=, with a =.meta.json= sidecar giving
the agent type, the description it was launched with, and the id of the tool
call that spawned it. Those transcripts are inlined into a =* Subagents=
section at the top of the document, ordered by where their spawning call
appears in the parent.

The section itself stays unfolded so the roster of agents is visible at a
glance; each agent's own heading carries =:VISIBILITY: folded= so its
transcript stays out of the way until wanted.

* How tool calls are rendered

The original jq renderer dumped every non-=Bash= tool input as compact JSON, so
a =Write= call arrived as one enormous line with every newline escaped as
=\n=. Now each input is taken apart:

- Scalars and short strings become bullets (=- **replace_all**: false=). Paths
  are abbreviated to =~=.
- =command=, =content=, =old_string=, =new_string=, =plan= and =prompt= are
  always blocks, however short. Beyond a command belonging in a source block
  anyway, org's ==verbatim== markup has no escape mechanism, so a one-line
  command inlined that way breaks apart the moment it contains an ===, which
  =echo "=== section ==="= does.
- Other multi-line or long strings become their own fenced block, tagged with a
  language guessed from the input's =file_path= extension.
- Nested arrays and objects become indented JSON.
- Anything already shown in the heading is not repeated as a bullet.

Tool-use headings carry a short summary so a folded outline stays scannable:
the path for =Read=/=Write=/=Edit= (with the line range for =Read=), the
description for =Bash= and =Agent=, the pattern for =Glob=/=Grep=, the URL for
=WebFetch=.

=Edit= calls render as a unified diff with three lines of context, produced by
a line-based LCS in the program itself --- no =diff(1)= fork, no temporary
files. The output matches =diff -U3= byte for byte. Inputs large enough to make
the quadratic LCS table wasteful fall back to printing =old_string= and
=new_string= as two separate blocks.

* Prose fields and heading levels

Message text, and the =plan= and =prompt= tool fields, are markdown rather than
code, so pandoc turns them into real org markup --- headings included. A
message's own =## Foo= must not escape the transcript's outline, so its headings
are renumbered to sit two levels under the turn they belong to, keeping their
relative depths. Two rather than one: the sub-headings a turn is made of
(=Tool Use=, =Thinking=, =Recap= …) sit one level under it, and message content
that landed on the same level would be indistinguishable from the transcript's
own structure.

The renumbering happens on the *org* side, after pandoc, not on the markdown
going in. It has to: /pandoc/ decides what a heading is, and the markdown side
cannot see everything it will call one. That was not a hypothetical. A subagent
wrote banner rules around its section titles,

#+begin_example
====================================================================
SECTION 1. Hernandez et al., …
====================================================================
#+end_example

which CommonMark reads as one lazily-continued paragraph closed by a setext
underline --- a level-1 heading, with no =#= anywhere for the markdown side to
find. Seven of them came out as =* = at column zero, siblings of the =* User=
and =* Assistant= turn headings, and re-parented the rest of the document.

So each heading this program emits carries a tag instead: two private-use runes
around a kind letter (=T= for a turn, =S= for everything else) and the heading's
true level. Markdown ignores them, pandoc passes them through untouched, and
=normalizeOrgLevels= strips them again while restoring the level each one
declares. Anything else that is a heading by then came out of a message, and is
demoted as a unit. Two things fall out of doing it this way:

- A =*= at the start of a line in pandoc's org output is /always/ a heading. The
  writer zero-width-space-escapes prose org would misread (=#+TITLE:=, a literal
  =* = line) and comma-escapes block interiors, so there are no false positives
  to sort out.
- Heading levels are no longer capped at six. Markdown stops there; org does
  not, and the tag carries the unclamped level, which matters inside a subagent
  where the transcript already starts at level three.

Three smaller rules the markdown side still enforces, all about fences:

- Headings inside fenced code blocks are skipped, because a shell snippet's
  =# comment= lines are not headings.
- A message that opens a fence and never closes it gets one appended. Otherwise
  it swallows everything after it --- the next turn's headings included --- into
  a single code block, and a chunk seam landing inside that block converts
  differently from no seam at all.
- A fence opened mid-sentence is re-cut around what was meant. A fence has to
  start its own line, so ~I want to print ```~ is not one: CommonMark reads the
  run as an inline code span, keeps the paragraph going, and then takes the
  /closing/ run --- which does start its own line --- as the opening fence. Code
  and prose come out swapped, with the rest of the sentence sealed into the
  block by the rule above.

Only a bare run closes a fence: ~```sh~ inside a ~```~ block is content, not the
end of it. Reading it as the end walks the rest of the message one block out of
step, which is how the fence-closing rule above first went wrong.

The mid-sentence shape is common because =pasteBlockified= (hyper+=,=) wraps the
clipboard in ~```~ with no leading newline, so any paste not landing at column
zero produces it --- 28 times across 18 of the local transcripts. Re-cutting is
safe because CommonMark was already going to read that text as a code block;
only the boundaries move, so a message that would otherwise have rendered
correctly cannot be broken by it. A run with no matching closer later in the
message is left alone rather than guessed at.

A body of one line was a quotation inside a sentence, and becomes an inline code
span so the sentence survives. The line after the closer is pulled up with it
unless it starts a block of its own, because a soft break there leaves pandoc a
space to strand before a leading comma. Anything longer becomes the block it
looks like. What that costs is nesting: an opener inside a list item puts the
fence at column zero, so the block and the text after it trail the list instead
of sitting in the item. Measuring list markers to keep it was not worth it.

[[agfi:org-header-rm-shared-level]] followed by [[agfi:org-header-indent]] is the
same idea, on a document that is already org.

* Performance

pandoc dominates the conversion --- on a 4.5MB session it was 89% of the
runtime --- so =org-pandoc= splits the rendered markdown into byte-balanced
chunks and runs one pandoc per chunk concurrently. The seams always fall on
record boundaries, never inside a code block and never just after a heading, so
every chunk is a self-contained markdown document; the result is byte-identical
to converting the whole thing in one pandoc, which =TestPandocPathParity= checks
against the whole local corpus by comparing the path against itself run with
=-jobs=1=. Its reference used to be =-format=md | pandoc=, which no longer
works as one: the org-pandoc path tags its headings and rewrites their levels
afterwards, and a bare pandoc pipeline can do neither. The test exists for the chunk seams, and
still covers them. Documents below a few hundred KB use a single process,
because pandoc's ~70ms startup would eat the gain. Records also render
concurrently, since each is independent.

The no-heading rule is the newer half, and the parity test failed on one
transcript for a long time without it: the parallel output carried one blank
line a single pandoc did not. An org headline is a container, so pandoc's org
writer emits whatever follows a headline with no blank line between the two,
while the chunk join always puts one there. Probed against every block type the
renderer emits, that is the whole of the difference --- a chunk ending on a
heading, followed by a heading, paragraph, list, code block or table, all
diverge, and nothing else does. So when the byte target is reached at a part
whose markdown ends with an ATX heading, the seam moves on to the next part
instead; =endsWithMarkdownHeading= is the test, and it only has to know our own
markdown. Deciding the separator at the seam instead would mean knowing pandoc's
spacing rules, which is the trade the next paragraph refuses. The cost is
nothing measurable: only a part ending in a bodyless heading (a =### Result:=
with no content under it) can push a seam, those are rare, and in the worst case
the chunks merely come out less balanced. Parity now holds over the whole
corpus --- 112 transcripts under =~/.claude-work/projects= and 376 under
=~/.claude/projects=, 488 in all --- and the single-pandoc output is
byte-identical to what it was before the fix.

A tempting further step is to keep code blocks away from pandoc entirely ---
they are 84% of a transcript's bytes and pandoc only copies them through, and
skipping them measured ~40% less pandoc CPU. Do not. Matching pandoc's output
then means reimplementing its reader's quirks: tab expansion to 4-column stops,
CRLF folding, outright deletion of lone CRs, comma-escaping after indentation,
trailing-newline trimming. Each is a silent corruption if it drifts from
whatever pandoc does next release, and that is a bad trade for CPU on a
conversion that runs once per session view.

=list= reads only the two ends of each file: forward from the start until the
first user message, and backwards from the end over a 64KiB tail window. Both
windows widen if they come up empty. That keeps the picker's cost proportional
to the number of sessions rather than to total transcript volume --- across 52
sessions and 48MB it reads well under 1% of the bytes and runs in about 30ms,
matching a full scan exactly on every session.

The name column costs =list= nothing. The backwards walk already decodes every
line in its window, so noticing the =slug=, =aiTitle=, =customTitle= and
=agentName= fields on the records it passes is free. =scanTail= returns both the
newest timestamp and the name parts from the one buffer, decoding into a narrow
=tailRecord= that carries the type, the timestamp and those four fields and
nothing else, so no message body is copied on the way. Measured over the real
corpus --- 119 sessions across both profile roots, warm cache --- the walk took
0.03s before the column and 0.03s after.

What did change is how far the walk goes and when it stops widening. The
timestamp is settled after =tailRecords= (25) messages, since records are
written in order and the newest is always among the first few met; the name
search wants the rest of the window, so the walk now carries on past that point
and only skips the timestamp work. The two searches also widen differently. The
timestamp search is unbounded: missing it means dating the session by mtime,
which is wrong in a way worth reading a whole file to avoid. The title search
stops at =nameWindow= (1MiB): missing it only means falling back to the slug,
and a session with no title anywhere would otherwise pull a 26MB transcript
through the scan just to establish that.

* Why the session time is not the file mtime

The picker used to show each file's mtime, which drifts from the conversation:
Claude Code appends bookkeeping records (for instance
={"type":"bridge-session"}=, which carries no timestamp) long after the last
message. In practice that put entries hours, and in one case two days, past the
last thing actually said. =list= therefore reports the newest timestamp among
the session's =user= and =assistant= records, and sorts by it. Files with no
timestamped message at all --- empty or truncated ones --- fall back to mtime
so they still appear in the picker rather than vanishing.

* pandoc

The org conversion runs =pandoc --from=gfm-gfm_auto_identifiers --to=org=.
Without =-gfm_auto_identifiers=, pandoc attaches a three-line
=:PROPERTIES:/:CUSTOM_ID:/:END:= drawer to every heading, which nothing in
these exports links to.

Avoid the em dash in generated headings: pandoc's org writer rewrites it as
=---=. The tool-use headings use a middle dot, which survives. Property drawers
cannot be expressed through pandoc at all --- a =:PROPERTIES:= paragraph is
collapsed onto one line, and =header_attributes= is not supported for gfm ---
which is why the Subagents skeleton is emitted directly as org and only the
message bodies are handed to pandoc. Its two headings still carry the level tags
described above, so that =normalizeOrgLevels= sees one uniform document rather
than mistaking =* Subagents= for something a message wrote.

* zsh entry points

- =claude-code-view-session-fz= --- pick a session, convert to org, open in
  emacs.
- =claude-code-view-session-md-fz= --- same, as markdown.
- =claude-code-view-session-raw-fz= --- open the original =.jsonl=.
- =claude-code-view-session= --- the same as the first, for a session path you
  already have. No picker.
- =claude-code-view-session-focused= --- open the session running in the
  focused kitty window. See below.
- =claude-code-session-live-fz= --- pick among the sessions currently live in
  a kitty window. See below.
- =claude-code-session-resume-fz= --- pick a session of this project from any
  profile and resume it, forking it into another profile first when asked.
  =claude-resume-fz=, =claude-resume-personal-fz= and =claude-resume-work-fz=
  fix the target profile. The family is documented in
  =docs/claude_code_usage.md=.
- =claude-session-selftest= --- run the Go tests and the corpus parity check.

Each viewer and each resume picker has a =-all-fz= variant that selects from
every project's sessions instead of the current directory's:
=claude-code-view-session-all-fz=, =claude-code-session-resume-all-fz=,
=claude-resume-all-fz=, =claude-resume-personal-all-fz=,
=claude-resume-work-all-fz=, and so on. The viewers set the picker's
=claude_code_view_session_fz_scope= directly; the resume family sets its own
=claude_code_session_resume_scope=, which =claude-code-session-resume-fz=
forwards into the picker's knob. It used to declare the picker's variable
=local= and hardcode it, which silently shadowed whatever an =aliasfn= wrapper
had set --- the reason the resume family went without =-all-fz= variants for as
long as it did.

All of them pick through =h-claude-code-session-select-fz=, which shows the
=list= columns from the local time onwards --- time, name, profile-labelled
relative path, first-prompt snippet --- and previews the highlighted row with
=h-claude-code-session-preview=, the same tail-scan body the live picker and the
kitty overlay use (see the section on sessions live in a kitty window). It used
to pass no =--preview= at all, so it fell back to =fz='s generic
=FZF_SIMPLE_PREVIEW=, which just echoes the row back. There is no separate knob
for turning the preview off: =claude_code_view_session_fz_fz_opts= is appended
after the preview options, so a =--preview-window hidden= there wins.

Variables:

- =claude_code_view_session_fz_scope= --- =project= (default) or =all=.
- =claude_code_session_resume_scope= --- the same choice for the resume family,
  =project= (default) or =all=, forwarded into the picker's knob so the two
  cannot disagree. Replaces =claude_code_session_resume_all_p=, a boolean that
  was set by nothing and documented nowhere.
- =claude_code_session_projects_dirs= --- an array of projects directories to
  search. Defaults to every profile's, found by globbing
  =~/.claude*/projects=, so a new config home needs no wiring.
- =claude_code_session_projects_dirs_glob= --- overrides that glob.
- =claude_code_view_session_fz_projects_dir= --- the older singular name, still
  honoured as a single-directory override.
- =claude_code_view_session_fz_fz_opts= --- extra options for =fz=.
- =claude_code_view_session_fz_subagents_p= --- =y= to also list subagent
  transcripts in the picker.
- =claude_code_session_preview_bytes= --- how much of the transcript's tail the
  fzf preview scans, in bytes. Default 400000.
- =claude_code_session_preview_color_p= --- =n= turns off the ANSI colour in the
  preview. The callers still pass =--ansi=, which is harmless on plain text.
- =claude_code_session_max_block_lines= --- passed to =-max-block-lines=.
- =claude_code_session_diff_p= --- =n= disables diff rendering for =Edit=.
- =claude_code_session_subagents_p= --- =n= stops inlining subagent transcripts.

* Reading the session you are in

Picking from a list is the wrong tool when you are already inside the session
you want to read: several sessions routinely share a project directory, so
"newest for this cwd" is not reliably the right one. =cmd+shift+o= in kitty
opens the session running in the focused window.

Claude Code cannot do this by itself. Its =~/.claude/keybindings.json= takes
only a fixed action enum --- =chat:submit=, =app:toggleTranscript= and the
like --- with no action that runs a shell command and no way to bind a slash
command. So the keypress lives in kitty.

** What the window can say for itself

The hotkey is =claude-code-view-session-focused=, bound in
=configFiles/kitty/kitty.conf=. It asks =kitty @ ls= which window is focused
and hands that window to =h-claude-code-session-of-kitty-window=, which tries
four things, in order of how sure each one is:

1. Claude Code runs in the window itself. One of the window's foreground pids
   is then a live session's pid.
2. The window shows a tmux client, =tmux a -t NAME=. Sessions here mostly live
   in detached tmux sessions --- that is what lets them outlive a kitty
   restart --- and the kitty tab merely displays one. Claude Code's own record
   of each session, =<config home>/sessions/<pid>.json=, carries a =tmux= field
   naming the tmux session it runs in, and NAME is matched against that.
3. The window shows the agent view, =claude agents= or =claude attach=. The
   view sets the window title to the attached session's name, at times with a
   status glyph in front, and the title is matched against the live sessions'
   names. This is observed behaviour, not documented, so it has to match
   exactly one session or it is ignored.
4. The registry described below: where the session was showing the last time
   it was prompted.

The first three read only what exists at the moment of the keypress, so they
cannot go stale. The fourth can, which is why it comes last.

What counts as live comes from =claude agents --json=, the supported interface
and what the agent view itself shows. This is decided inside Claude Code's
daemon and nothing on disk reproduces it: an assigned background session and an
idle pre-forked spare share the identical argv, so filtering session records by
liveness ourselves would drop real sessions or surface spares. So the listing
stays the authority.

It is scoped to one config home, and each call costs about 180ms. Because the
homes are independent, the =live= subcommand of the =claude_session= Go binary
runs them concurrently and does the record reads and transcript derivation in
the same process, which roughly halves the wall time and removes a dozen shell
forks; =h-claude-code-session-live-list= calls it, falling back to an
identical-output shell path (=...-list-sh=) when the binary is not built. The
personal profile is asked with =CLAUDE_CONFIG_DIR= unset, since Claude Code
hashes a set value into its keychain entry name. The transcript path is
derived rather than read: the session's id under the projects directory named
after its cwd, in the same config home, with every non-alphanumeric character
of the cwd turned into =-= --- slashes, dots, spaces and underscores alike,
which is the rule Claude Code uses. The resolution takes about 300ms end to
end, most of it that one parallelised listing.

The Go probe is by =command -v=, a real PATH lookup, not by the shell's command
hash: the garden's hash is stale for a binary installed after it started, and
trusting it would send every call down the slow build-check path.

** In the background, with a band, press again to cancel

The conversion is the slow part -- =claude_session render= plus a fan-out of
pandoc processes, seconds on a large transcript -- so none of it runs in the
hotkey. The press itself only identifies the tab (kitty, about 30ms), claims
it, raises a band and returns. Everything else, the 300ms lookup included,
happens in =h-claude-code-view-job= behind that band, which names the session
once it is known and comes down when emacs has the file. Resolving *before*
claiming would leave a 300ms window in which a second press starts a second
job; this way a double-tap deterministically cancels.

The key is a toggle. A press while the tab's conversion is running cancels it:
the band turns amber and says so, the process tree goes, the temp directory
with its truncated =.org= is removed. The next press starts afresh.

The job lives in a tmux session named for the tab, =claude-view-<kitty-pid>-<window-id>=,
which is the repository's detached-job primitive and, here, also the lock, the
handle and the cancel target: =tmuxnew= kills any previous session of that
name before creating the new one, =tmux-alive-p= says whether the job still
runs (=has-session= alone does not, with =remain-on-exit= on), and
=tmux-session-processes-kill= takes the whole tree down, pandoc children
included. No marker, pid file or redis key -- the same shape as the usage
notifier. The temp directory is recorded on the session with
=tmux set-option '@ccv_tmp'= for the canceller, so the bookkeeping cannot
outlive the job. The renderer's build check runs in the foreground before the
job starts, so a cancel never has to kill a Go toolchain on a first use.

The band is hs-alert v2 under the same name as the tmux session. Re-showing an
id updates the band in place, and an unchanged message is a heartbeat, so the
job reports progress by re-showing; bands stack, so two tabs converting at once
show two. =hs-alert-dismiss= takes one down. Every alert call is wrapped in
=reval-timeout= and never fails the caller, so a Hammerspoon mid-reload cannot
hang a hotkey. On failure the band turns red with the reason and a
notification goes out too; the band would otherwise expire on its own in ten
minutes, so a crashed job cannot brand the screen.

Two ordering rules in the canceller, both learned elsewhere in the repository:
read the session's options before killing it, since the kill discards them; and
change the band before the kill, so nothing the death triggers can repaint it.
Cleanup lives in the canceller, not in an =always= block inside the job,
because a killed process is not guaranteed to run one.

On success the temp directory stays, as it always has: emacs has the file
open.

** The picker

When none of the four resolves, the hotkey does not notify and give up. It
opens a picker over every live session as a kitty overlay in that same window,
=zshlang/wrappers/claude-code-session-pick.zsh=: "which one did you mean" is a
question, not a failure. It is an overlay running its own script because fzf
needs a terminal and neither the background hotkey nor the garden's shells
have one; the script runs fzf itself and goes through the garden for the rows,
the preview and the final open. The tab's key travels into the overlay as
=CLAUDE_VIEW_TAB_KEY=, so the choice comes back through
=claude-code-view-session-bg= and gets the same band and cancel as a direct
hit.

** The registry, as insurance

The write side is =claude-code-session-register=, wired to Claude Code's
=SessionStart= and =UserPromptSubmit= hooks in
=configFiles/claude-code/settings.json=. Under
=~/.local/state/claude-code-sessions/=, in a file named
=<kitty-pid>-<kitty-window-id>=, it records the =transcript_path= the hook was
handed. kitty numbers its windows from 1 again on every restart, so the pid is
what stops a dead kitty's entries from being read as live ones.

It records the one fact a hook knows that nothing else does. When
=UserPromptSubmit= fires, Enter was just pressed, so the kitty window focused
at that instant is the one showing the session, whatever the attach mechanism.
It used to walk its own process ancestry looking for kitty instead. That finds
kitty only for a session run directly in a tab; for anything attached, the
walk ends at tmux or at Claude's pty host, and the hook silently recorded
nothing. No hook fires on attach itself, and none runs in the attaching
client, so a prompt is as close as a hook can get.

Two guards keep the record honest. If kitty has no focused window, the prompt
did not come from one --- a message from another agent, say, or the usage
auto-continue --- and nothing is written. If the focused window resolves to a
/different/ session, the prompt was injected while you sat elsewhere, and
nothing is written either. Only a window the live lookups cannot explain, or
one they agree with, is recorded. That is what makes it insurance rather than
a competing answer: it covers the attach path nobody has invented yet, and the
day the agent view stops putting the name in the title.

Nothing here needs doing for a second profile. The registry stores the
absolute transcript path, so a [[agfi:claude-work]] session records a path
under =~/.claude-work/projects/= without anything knowing that profiles exist,
and the hooks fire at all because =~/.claude-work/settings.json= symlinks to
the same tracked file.

** Exit codes and the notification

The hotkey notifies rather than printing on failure, because it runs detached
and stderr goes nowhere a person will look. It also always exits zero.
Pressing the key in a window with no session is an ordinary outcome, not an
error, and the picker or the notification has already answered --- but a
non-zero return makes BrishGarden log the command as failed and ring its
failure bell, which is a second, louder answer to a question already answered.
=h-claude-code-view-session-focused= holds the real body and the real exit
code, for anything that wants to branch on it.

Things that are easy to get wrong here:

- kitty's own =PATH= is just =/usr/bin:/bin:/usr/sbin:/sbin=, so the binding
  needs an absolute path to =brishz.dash=. It cannot use =brishz2.dash=, whose
  quoting path needs a =jq= that is not on that =PATH= either. The command is a
  bare function name, so the unquoted path is safe. The overlay picker has the
  same problem from the other side, and gets our =PATH= passed in explicitly.
- =KITTY_LISTEN_ON= is only trusted when it still points at a live socket.
  Brish's shells outlive kitty, so the garden holds whatever value was in the
  environment the day it started, which goes stale the moment kitty restarts.
  Otherwise the socket comes from [agfi:kitty-socket-get], which owns that
  knowledge for everything that talks to kitty and matches =listen_on= in
  =configFiles/kitty/kitty.conf=.
- The socket lives in =$NIGHT_SOCKETS_DIR=, =~/.local/state= by default, and
  emphatically not in =~/tmp=. It sat there once, and a stray deletion killed
  kitty's remote control outright: an unlinked socket path cannot be
  re-linked, and =listen_on= is applied only at startup, so kitty went on
  holding the bound inode while every client got ENOENT. Nothing short of
  restarting kitty brings it back, which is why
  [agfi:kitty-socket-get] says so by name instead of reporting "no socket".
  The registry moved out of =~/tmp= for the same reason; it vanished in the
  same sweep.
- Sockets left behind by a kitty that crashed are ignored rather than deleted.
  =listen_on= puts kitty's pid in the socket's name, so
  [agfi:kitty-sockets-list] can filter by whether that pid is still a live
  kitty. Deleting them used to be the strategy, and a =kitty @= that failed
  for any unrelated reason would take a working socket with it.

Remember =brishz-restart= after changing any of this: the garden keeps
persistent shells and will otherwise go on running the old code.

Variables:

- =claude_code_session_registry_dir= --- defaults to
  =$XDG_STATE_HOME/claude-code-sessions=, with =~/.local/state= standing in
  for an unset =XDG_STATE_HOME=.
- =claude_code_session_live_list_cache= --- a listing to reuse instead of
  asking =claude agents= again; set it (a =local= suffices) around several
  lookups.
- =claude_code_session_live_rows_scope= --- =windows= (default) or =all=; see
  the next section.
- =claude_code_session_kitty_socket_glob= --- defaults to
  =$NIGHT_SOCKETS_DIR/kitty-*.sock=. Passed through to
  =kitty_sockets_list_glob=, which is the same override under the name the
  shared resolver uses.

* Sessions live in a kitty window

=claude-code-session-live-fz= picks among the Claude Code sessions currently
live in a kitty window, printing =<kitty-window-id> <TAB> <transcript path>=
per choice. Each window goes through the same
=h-claude-code-session-of-kitty-window= the hotkey uses, so a session shows
up whether it runs in the tab, sits behind a tmux client, or is attached
through the agent view, and it disappears the moment its window closes. With
=claude_code_session_live_rows_scope=all= the rows cover every live session,
with =-= in the window column for one no kitty window is showing; that is what
the hotkey's overlay picker offers, via =h-claude-code-session-pick-rows=.

Each row's metadata comes from a single =claude_session list= call over every
profile's projects directory, joined back onto the live rows by transcript
path, rather than one metadata call per row. =list= walks the whole corpus in
about 45ms, while =claude_session name= alone costs about 230ms on a large
transcript — a per-row call would have made the picker's startup cost scale
with however many sessions happen to be open. The fzf preview goes further
still and skips =claude_session render= entirely: rendering a 46MB transcript
takes about eight seconds, far too slow for a preview pane that has to feel
instant. Instead =h-claude-code-session-preview= tail-scans the last few hundred
KB (=claude_code_session_preview_bytes=, 400000 by default) for fields Claude
Code already writes there in plain form, and shows, each row omitted when the
session has nothing to say for it: the name, bold, in its profile's colour; a
gray subtitle of uuid, profile and Claude Code version; =last activity=, the
newest timestamp in local time plus a relative age, =2026-09-08 17:55 (39s
ago)=; =model=, the model that answered last with =claude-= stripped and the
reasoning effort, =opus-5 · high effort=; =mode=, the permission mode and the
interaction mode, =auto · normal=; =cwd=, with =$HOME= abbreviated to =~= and
the git branch after an =@=; and the last prompt. All of it comes out of one jq
pass. Measured through the garden on a 26MB transcript it takes 127ms end to
end, most of which is the brishz round trip rather than the scan.

The name is resolved from all four sources in the Go resolver's precedence ---
=agent-name=, =custom-title=, =ai-title=, slug --- rather than from =ai-title=
alone, as it once was. =claude-code-session-import= names a fork with
=agent-name= and =custom-title= records, so the old scan showed a fork under its
pre-fork title, in exactly the workflow the resume family exists for. Checked
over all 123 local sessions, the preview's headline agrees with the
authoritative =claude_session name= on every one.

The jq expression is two groups, not one chain. The records that exist only to
say one thing --- =agent-name=, =custom-title=, =ai-title=, =last-prompt=,
=permission-mode=, =mode= --- are mutually exclusive and stay an if/elif chain.
=slug=, =cwd=, =gitBranch=, =version=, =effort=, =timestamp= and the assistant's
model ride on the ordinary message records, so a second group reads them from
every record as well as whatever the first group matched, not instead of it. The
old single chain had an ordering hazard this removes: its =.timestamp= branch
had to come last or it swallowed the title records, which carry no timestamp of
their own. The partial line a byte-tail starts on is dropped only when the tail
really is a tail; on a transcript smaller than the window that =tail -n +2= was
throwing away a whole genuine record, which for a session of one or two records
was everything there was to read.

The colour is keyed on the profile, from the =claude_code_session_profile_colors=
table: =.claude= blue, =.claude-work= orange, and an unknown profile gets no
colour rather than a wrong one. Which account a session belongs to is the thing
worth seeing at a glance, since the whole point of =claude-code-session-resume=
is that the two are otherwise interchangeable. It is deliberately not Claude
Code's own =agent-color=: that record is written once, wherever in the session
the name got settled, which is nowhere near either end of the file --- 210MB
into a 398MB transcript in one measured case --- so a tail scan cannot reach it,
and only 5 of 123 local sessions have one at all. The escapes come from the
repository's own =colorfg=, =Bold= and =resetcolor=, which gate on a tty; the
preview reaches its pane down a pipe from a non-interactive garden shell, so it
sets =isColor_override= rather than emitting escapes by hand. Because the output
carries ANSI, every caller passes fzf =--ansi=:
=h-claude-code-session-select-fz=, =claude-code-session-live-fz= and the overlay
front end =zshlang/wrappers/claude-code-session-pick.zsh=.

Two small helpers came with it. =h-claude-code-session-epoch-of= parses Claude
Code's ISO-8601 UTC stamp with =strftime -r= under =TZ=UTC=, since strptime has
no timezone field and that is how the trailing =Z= is honoured; it is its own
function because =local -x= scopes to a function, not a block, and it uses
=strftime= rather than =date= because GNU and BSD date disagree on parsing and
this runs on both. =h-claude-code-session-age= prints a duration as its single
largest unit --- =44s=, =6m=, =3h=, =2d= --- since what a preview answers is how
stale the session is.
