#+TITLE: agent_session

Renders coding-agent session transcripts into org-mode or markdown, scans a
directory of them for the fuzzy session picker, and writes the picker's preview
pane. One binary, one adapter per agent, and there are three of them now:

- Claude Code, one JSONL per session (=~/.claude*/projects/**/*.jsonl=);
- Codex, one rollout per thread
  (=~/.codex/sessions/YYYY/MM/DD/rollout-<local-timestamp>-<uuid>.jsonl=);
- Antigravity, whose conversations are *directories* rather than files
  (=~/.gemini/antigravity-cli/brain/<id>/.system_generated/logs/transcript_full.jsonl=,
  falling back to the truncated =transcript.jsonl= beside it).

The zsh side is =zshlang/auto-load/others/agent-session.zsh= for everything
agent-neutral, one =<agent>-session.zsh= per adapter, and =agents.zsh= for the
table of agents. =docs/agent-sessions.md= is the prose about that half --- the
kitty hotkey, the pickers, the window-to-session resolution order, the hook
wiring --- and this readme stays about the binary.

Standard library only, so =go build= needs no network and no module cache. It
works on a freshly bootstrapped, sudoless host.

It was =claude_session= until it grew a second agent's worth of structure. The
old name survives as a zsh =aliasfn= for =agent_session claude=, so anything
still spelling it keeps working.

* Install
#+begin_src zsh :eval never
go-install-local "${NIGHTDIR}/golang/agent_session"
#+end_src

Registered in =setup/setup_go=, so a full setup run installs it. The zsh
wrappers also install it on first use, through [[agfi:h-agent-session-dep]]
and [[agfi:ensure-dep1]], so a fresh clone works without a separate step as long
as Go is present.

* Test
#+begin_src zsh :eval never
agent-session-selftest
#+end_src

That runs =go test= plus the parity check below, once per profile root. The Go
tests alone, one package at a time:
#+begin_src zsh :eval never
cd "${NIGHTDIR}/golang/agent_session" && go test ./...
#+end_src

Each package tests what it owns: =internal/turns= the writer, fence repair,
heading levels and the diff; =internal/claude= the record model, turn merging,
name precedence and the tail scans; =internal/codex= the rollout model, the
subagent filter, the last-wins name index and the argv unwrapping;
=internal/agy= the step model, the =<USER_REQUEST>= unwrapping, an unknown step
type and the subagent inlining; =internal/session= the root labels and the
dash-guard; =internal/preview= the row primitives. The two new adapters' tests
build a whole store under =t.TempDir()=, so nothing there reads a real
transcript, and =internal/proc= has no tests of its own because its =Run= is a
variable: the two liveness tests replace it and hand back the =ps=, =lsof= and
=tmux= output they want, so nothing is shelled out to. The parity test sits at
the module root, in =parity_test.go=, because it builds the binary and runs it. It
needs real transcripts and pandoc, so it is skipped unless pointed at a corpus:
#+begin_src zsh :eval never
AGENT_SESSION_CORPUS=~/.claude/projects go test -run Parity ./...
#+end_src

=AGENT_SESSION_CORPUS_AGENT= names the agent the corpus belongs to and defaults
to =claude=; the old =CLAUDE_SESSION_CORPUS= name is still honoured.
[[agfi:agent-session-selftest]] sets the variable itself, and
=claude-session-selftest= still reaches it as an alias, as do the other old
names.

The rename and split were checked the blunt way: every subcommand run over a
synthetic fixture, byte for byte against what =claude_session= printed for the
same arguments. Nothing in the output moved.

* Layout

One module, =agent_session=, with =main.go= doing nothing but dispatch. The work
is in seven internal packages, and the seam between them is the point of the
split: an adapter translates one agent's records into a =turns.Document=, and
everything after that is shared, so a fix to the writer reaches every agent at
once.

That seam held when the second and third agents arrived, but it was not free.
Codex needed tool headlines of its own in =internal/turns= --- =shell=,
=exec_command= and =container.exec= as commands, =apply_patch= rendered as the
diff it already is (=patchFiles=), =update_plan= and =web_search= --- and
=langForKey= to pick the fence language for them. Antigravity needed a new
block type, =event=: like a =notice=, but its body is *output* rather than
prose and is not markdown, which is what an agent whose step types are an open
enum needs for the ones this code has never heard of. Both changes are in the
shared half and both are available to every adapter, which is the test of
whether a seam is in the right place.

- =internal/session= --- the contract between the CLI and the adapters. The
  =Adapter= interface, =List=, =Name=, =Meta=, =Preview=, =Live= and =Document=;
  the =Info=, =Live= and =Meta= row types, each with the TSV =Row()= the zsh side
  reads back; the option structs =ListOpts=, =PreviewOpts= and =DocOpts=;
  =ErrUnsupported=, for a subcommand an agent has no equivalent of; and the
  helpers every adapter wants --- =Fatal=, =GuardPathArgs=, =ProfileLabels=, the
  =ForEach= worker pool, and =MaxLineBytes=, the scanner buffer sized for lines
  that carry whole files inline.
- =internal/turns= --- the agent-neutral half of the renderer: the
  =Document=/=Subdoc=/=Turn=/=Block=/=TimedBlock=/=ToolResult= model,
  =Render(doc, Options)= and =RenderTurns=, =Style=, the org and markdown
  writer, fence repair, the heading tags, pandoc chunking, the unified diff, and
  the text helpers (=ShortModel=, =ModelLabel=, =ModelTag=, =ScrubText=,
  =AbbrevHome=, =Truncate= …).
  Nothing in it knows how any agent stores a session.
- =internal/preview= --- what the fzf previews of different agents are built
  from, so they line up and read alike: =Painter=, =Row=, =JoinParts=,
  =Annotate=, =HumanAge=, =VersionLabel=.
- =internal/proc= --- what the adapters need to know about the machine, each
  answer costing one command rather than one per process: =List= over a single
  =ps -axo pid=,ppid=,args==, =ByPID=, =Cwds= over a single =lsof -a -d cwd
  -Fpn=, =Holders= mapping each of several files to the pids holding it *open*
  over a single =lsof -Fpn --=, =TmuxPanes=, =TmuxOf= walking a process's
  ancestry to the pane that contains it, and =Descendants=. =Run= is a variable,
  so the tests replace it instead of running anything.
- =internal/claude= --- the code that used to be the whole program, as the first
  adapter: the record model, =conversationRecords=, =buildTurns= and
  =appendEvent=, the subagent loader, the tail scan behind =list=, the preview
  scan, and =live= over the session records in =<config-home>/sessions/=. It
  implements =session.Adapter=, and nothing outside =main.go= imports it.
- =internal/codex= --- the Codex adapter: =rollout.go= for the record model and
  the input normalising, =index.go= for the append-only name index, =list.go=,
  =preview.go=, and =live.go= over the writer locks.
- =internal/agy= --- the Antigravity adapter: =steps.go= for the step model and
  the type labels, =meta.go= for the JSON summaries mirror, =adapter.go= for
  the turns and the listing, =preview.go=, =live.go=.

The block vocabulary is the renderer's, not any agent's: =text=, =thinking=,
=tool_use=, =tool_result= (an orphan whose call is not in the document),
=notice=, =event=, =command=, =pr=, =tasks= and =file-edit=. The JSON tags on
=turns.Block= match the Anthropic content-block schema, so the Claude adapter
decodes =message.content= straight into it; another adapter fills the fields by
hand.

Adding an agent is a package under =internal/<agent>= that satisfies the
interface, plus one line each in =agentNames= and =adapters= in =main.go=. A
subcommand the agent cannot answer returns =session.ErrUnsupported=, which the
CLI turns into exit status 3.

* Commands

Every call names the agent first: =agent_session <agent> <subcommand> [flags]
args=. =agent_session agents= lists the known agents, one per line: =claude=,
=codex=, =agy=. Exit status 2 is a usage error --- no agent, an unknown agent or
subcommand --- 1 a failure, and 3 an agent that does not support the subcommand.
Nothing returns 3 today: all three adapters answer all six subcommands. It is
=session.ErrUnsupported=, and it exists so that the fourth agent can decline one
without the zsh side having to special-case it --- [agfi:h-agent-session-call]
makes the same distinction on its side, returning 2 for a verb an adapter never
defined.

The subcommands are described below with =claude= in the examples, because that
is where each one grew up. The flags mean the same thing for every agent, with
the two differences the adapter sections spell out: =-subagents= selects Codex's
child rollouts and Antigravity's spawned conversations rather than Claude's Task
transcripts, and =-cwd= is answered by each adapter's own idea of where a
session ran. A path argument beginning with a dash is guarded before flag parsing:
every relative path under a projects directory starts with one, because the
directories are named after the cwd (=-Users-evar-scripts=), and the flag
package would otherwise read it as a flag. =--= still works for anything the
guard misses.

=agent_session claude render [flags] <session.jsonl>= writes the transcript to
stdout. Flags:

- =-format md|org|org-pandoc= --- output syntax. =md= (the default) is meant to
  be piped through pandoc; =org-pandoc= does that internally and in parallel,
  and is what the zsh wrapper uses; =org= emits org directly without pandoc and
  is only a fallback, since message bodies stay markdown.
- =-max-block-lines N= --- elide code blocks longer than N lines, leaving a
  =… [N lines elided]= marker. =0=, the default, never elides.
- =-diff= --- render =Edit= tool calls as a unified diff. On by default.
- =-subagents= --- inline the transcripts of spawned subagents. On by default.
- =-jobs N= --- worker count, defaulting to the CPU count.
- =-pandoc PATH= --- the pandoc binary to use for =org-pandoc=.

Only =-subagents= reaches the adapter, as =DocOpts=; the rest are =turns.Options=
and apply to any agent's document.

=agent_session claude name <session.jsonl>= prints the session's name, or
nothing if it has none. Claude Code names a session several ways, in increasing
order of authority: a generated slug like =sharded-bouncing-clarke=, an
=ai-title= summarising the work (=fix-org-store-link-title=), a =custom-title=
the user set (=Neru=), and =agent-name=, which is the name Claude Code itself
resolved from those. Names can be revised during a session, so the last wins; a
slug never changes. 39 of 52 local sessions have a slug and 28 have a title; the
rest predate the features and fall back to their uuid.

=agent-name= is preferred when present, so a future title source is picked up
without changing this code. It cannot replace the explicit precedence, though:
only 19 of the 28 named sessions carry one. Where both exist they agree, on all
19 --- and adding it changed no name anywhere in the local corpus.

That precedence lives in one place, the =nameParts= accumulator in
=internal/claude/list.go=, and is reached three ways. =name= reads the whole
file forwards and feeds every record to it. =list= feeds it the records its
tail scan is already decoding for the timestamp, reading backwards. =preview=
feeds it the records of its own tail window, forwards. All end in the same
=resolve=, so the name in the picker's column, the headline in its preview pane
and the name a viewer writes into a filename cannot drift apart. The direction
only decides which occurrence to keep: the last one written is the last met
reading forwards and the first met reading backwards, which is what the
=keepFirst= flag of =observe= selects.

The two differ in reach. =list= widens its tail window in search of a title only
up to =nameWindow=, one MiB (the Performance section says why); the slug does not
count as having found one, since it rides on nearly every message record and so
proves nothing about how far back the scan has looked. A title written more than
a megabyte before the end of the transcript is therefore beyond the column,
which shows the slug instead. Measured over all 119 local sessions across both
profile roots, including the 26MB ones, the column and the full =name= scan agree
on every single one. The cap is a theoretical limit here, not an observed one.

The org header uses it, and so does the filename the viewers write, so a
session opens in emacs as =Neru.org= rather than a uuid:

#+begin_example
,#+TITLE: Neru
,#+SUBTITLE: Claude Code session 3e500e15-2d94-44c6-bac4-4d6634c743f6
#+end_example

=agent_session claude meta <session.jsonl>= prints =id=, name and cwd on one
tab-separated line: the id off the filename, the name by the same full scan
=name= does, and the cwd from the tail window =preview= reads, which is enough
because Claude Code writes it on every message record. It is for a caller that
wants all three of a transcript and would otherwise pay three calls for them.

=agent_session claude preview [flags] <session.jsonl>= writes the fzf preview
body for one session: what it is called, whether it is running, what it was
running as, where, when it last moved, and the last exchange of the
conversation. Each row is omitted when the session has nothing to say for it:
the name, bold, in its profile's colour, prefixed by a status emoji when the
session is live; a gray subtitle of uuid, profile and Claude Code version;
=status=, =busy= or =idle=; =last activity=, the newest timestamp in local time
plus a relative age, =2026-09-08 17:55 (39s ago)=; =model=, the model that
answered last with =claude-= stripped and the reasoning effort, =opus-5 · high
effort=; =mode=, the permission mode and the interaction mode, =auto · normal=;
=cwd=, with =$HOME= abbreviated to =~= and the git branch after an =@=; then the
=last prompt= and =last reply= blocks. A session with no name is headlined
=Claude Code session <uuid>=. Only the tail of the file is read, so the cost
does not depend on the transcript's size; the section on sessions live in a
kitty window says why this is a subcommand at all.

The two conversation blocks come out of the tail window itself rather than out
of bookkeeping. =last prompt= is the newest message the *user typed* in the
window --- a =user= record that is not =isMeta= and whose content carries no
=tool_result= block, which is the same =typed= predicate =list= dates a session
by under =-last-by user=, shared as a method on =msgRecord= so the two scans
cannot disagree about what a prompt is. Its text blocks are joined and put
through the same =snippetText= the picker's snippet column uses, so a system
reminder or =<command-name>= scaffolding is stripped and a message that is
nothing but scaffolding leaves the previous prompt standing. =last reply= is the
newest =assistant= record in the window with a non-empty =text= block: a turn
ends in a tool call more often than not, and a record holding only =tool_use= or
=thinking= has nothing a reader can use, so the walk keeps going back.

The fallback order for the prompt block is typed message, then the
=last-prompt= record, then --- under the heading =first prompt= --- the first
user message in the file. The =last-prompt= record used to be the only source,
and measured over the 77 local transcripts it is a bad one: every transcript has
such a record and in 75 of them it sits earlier than a 400KiB tail reaches, so
the block read =(none in the scanned tail)= in the common case, while a typed
message was in the tail almost always. The =first prompt= fallback covers the
remaining case, a window that is all tool traffic: what a session was started
for identifies it better than an empty block, and the heading says which of the
two you are looking at.

That head scan runs *beside* the tail read, not after it. It is started in a
goroutine before =scanPreview= and its answer is read only if the tail turns out
to hold no prompt, so in the ordinary case nothing waits on it: =main= returns
and the goroutine dies with the process. It is bounded by =headWindow= and
satisfied within the first kilobyte in practice, so running it speculatively
costs a goroutine rather than wall clock --- a 383MB transcript still previews
in about 20ms.

The status is Claude Code's own: =<config-home>/sessions/<pid>.json=, the record
=live= reads, matched on its =sessionId= against the transcript's uuid. The
config home is derived from the transcript's path the same way its profile label
is --- everything above the =projects= directory --- so a =.claude-work= session
is never matched against the personal seat's records. A session writes the
record while it runs and removes it on exit, so a transcript with no matching
record is a finished session and gets no emoji and no row; a crash leaves the
file behind, so =recordAlive= checks the pid with signal 0 first. Nothing else
is consulted: no =claude agents= subprocess (170ms per config home) and no =ps=,
because the whole point of doing this in a preview is that it costs a handful of
small reads. ⏳ is busy, 💤 is idle.

Codex and Antigravity get the =last reply= block too --- both scans already had
the text in hand --- but no status. Their live listings hardcode =running=, and
guessing busy or idle from the tail would misreport a thread killed mid-turn.

- =-bytes N= --- how much of the transcript's tail to read, in bytes. Default
  409600. A title written earlier than that falls back to the slug, the same
  trade =list= makes with =nameWindow=. 0 or less reads the whole file, which is
  the escape hatch for a title further back than the window reaches.
- =-color= --- emit ANSI colour. On by default; =-color=false= turns it off, and
  so does a =NO_COLOR= variable in the environment, whatever its value, which is
  the cross-tool convention.
- =-compact auto|true|false= --- lay the body out for a pane the ordinary two
  columns do not fit in, which in practice means a phone-sized terminal under
  Termux or a deliberately narrow preview window. The label column shrinks from
  fourteen to six and the long labels shrink with it (=last activity= becomes
  =when=, =last step= becomes =step=, through one table in =internal/preview= so
  the adapters cannot disagree); the blank lines between the blocks go; the uuid
  leaves the gray subtitle, keeping the profile or agent and the version, since
  it is the longest thing there and the row the session was picked from carried
  it anyway; the =status= row goes, since the emoji on the name line already
  says it; and the prompt and reply blocks are cut to 240 runes
  (=preview.CompactTextLen=), because a wrapped wall of text pushes everything
  above it off the top of such a pane. The ordinary layout cuts them at 600
  (=preview.WideTextLen=): generous, but not absent, because an assistant turn
  runs to thousands of characters routinely and one such answer would otherwise
  fill the pane and push the prompt it answers out of sight.

  =auto=, the default, asks the environment rather than the terminal: fzf
  exports the pane's size to the preview process as =FZF_PREVIEW_COLUMNS= and
  =FZF_PREVIEW_LINES=, and a preview run by hand has the shell's =COLUMNS= and
  =LINES= to fall back on. Under 70 columns or 15 lines is compact; a variable
  that is unset or not a positive number says nothing, and with neither
  readable the ordinary layout is what you get. No ioctl, both because this is
  a stdlib-only binary and because the preview's stdout is a pipe fzf reads, so
  measuring it would answer the wrong question.

  The zsh side bakes the decision in when the picker starts, through the knob
  =agent_session_preview_compact_p= in [[agfi:h-agent-session-preview-cmd]]:
  unset it emits nothing and =auto= applies, =y= and =n= bake =-compact=true=
  and =-compact=false=. Same reason the bytes and colour knobs are baked rather
  than exported --- fzf spawns the preview itself, and a zsh global cannot reach
  a process it did not start.

=agent_session claude list [flags] <sessions-dir>...= walks the directories for
=.jsonl= files and writes one TSV line per session, newest first: =epoch=,
absolute path, local time, the session's name, path relative to the scanned
directory, and the first user message as a snippet.

The name sits before the relative path on purpose. The relative path runs to
about fifty characters (=.claude-work/-Users-evar-scripts/87e1476d-….jsonl=),
which would push a name placed after it off the right edge of an ordinary
terminal, and seeing the name without scrolling is the whole point of the
column. A session with no name leaves the field empty; its uuid is in the
relative path either way.

More than one directory may be given, and they are merged and sorted together
rather than listed one after another. Claude Code keeps a projects directory
per config home, and [[agfi:claude-work]] runs a second one, so a single root
would leave every work session invisible.

With several roots the relative path is prefixed by a label, because it is
otherwise ambiguous --- every profile holds a =-Users-evar-scripts/=. The label
is the first path component in which the roots *differ*: =.claude= and
=.claude-work= for the profile roots, and still those two when the caller
scopes each root down to a single project, where the last component is the same
for both and the parent is =projects= for both. A single root is listed exactly
as before, with no label.

- =-cwd DIR= --- only the sessions that ran in DIR. The adapter does the
  scoping: Claude Code names each project directory after the cwd with every
  non-alphanumeric character turned into =-=, so the flag walks that one
  directory under each root, with paths relative to it, and the rows come out
  identical to handing the scoped directories in as roots. What the flag buys is
  that the caller no longer has to know how the slug is spelled, which is what
  lets the same call work for an agent that scopes a project some other way.
- =-only PATH= --- answer for these transcripts and no others, repeatable.
  Nothing is walked: =session.Under= sorts each path under whichever root
  contains it, and the adapter reads exactly those files. It is for a caller
  that already has the paths and only wants the name and the timestamp that go
  with them, which is what the pickers want; asking that way took =codex list=
  from 276ms to 6ms. A path under none of the roots is skipped rather than
  rejected, so a stale row in a cache cannot fail the call.
- =-snippet-len N= --- snippet width cap, default 120.
- =-name-len N= --- name width cap, default 40.
- =-subagents= --- also list subagent transcripts. Off by default: =render=
  inlines them into their parent, and they were a third of the list.
- =-last-by any|user= --- which record dates a row. =any=, the default, is the
  session's last record of any kind, which is what every caller got before this
  flag existed. =user= dates it by the last message the *user* typed instead.
  The difference is what an agent does on its own: a session left running writes
  tool calls and their results for as long as it works, so by =any= it keeps
  floating to the top of a picker hours after anybody spoke to it, and by =user=
  it sits where the conversation left it.

  Each adapter answers this from its own store. Claude Code's tool results come
  back as =user= records --- that is how they are sent to the model --- and the
  harness writes its own notes as =isMeta= ones, so a record counts only when it
  is neither: a =user= record whose content is a plain string, or a block list
  with no =tool_result= in it. Codex counts a =response_item= that is a =message=
  with =role: user= and text the scaffolding filter does not claim, the same
  three tests the snippet makes. Antigravity counts the newest step whose
  =source= is =USER_EXPLICIT=.

  It can cost more reading than =any=. Both tail scans widen their window until
  they find a timestamp, and under =user= the qualifying record may be a long
  way behind the end --- an hour of tool calls is a lot of bytes. The mtime
  fallback is unchanged: a transcript with no typed prompt in reach is dated by
  the file, as one with no timestamp at all always was.
- =-jobs N= --- worker count.

=agent_session claude live <sessions-dir>...= prints one TSV row per session
currently running: pid, id, name, cwd, transcript path, the tmux session it runs
in or =-=, and its status. The section on reading the session you are in says
what it is for and why it lives here.

=agent_session live-all <agent>=<sessions-dir>...= is the same thing for every
agent at once, and is the only subcommand that does not start with an agent
name. Each argument pairs an agent with one of its roots, repeated as often as
needed (=claude=~/.claude/projects claude=~/.claude-work/projects
codex=~/.codex/sessions agy=~/.gemini/antigravity-cli/brain=); the rows come out
grouped by agent, in the order the agents were first named. An adapter that
fails contributes no rows and does not fail the run, because a host with no
Codex installed should still get a picker. The next chapter says why it exists.

* One listing for every agent

Asking the three adapters in turn cost about a second before anything reached
the screen, and most of that was the same work done three times: a process
table each, an =lsof= each, three binary startups. =live-all= runs them
concurrently in one process instead, and they share the expensive reads.

=proc.ListShared= and =proc.PanesShared= do their =ps= and their =tmux
list-panes= once per process, behind a mutex, and hand every later caller the
same slice. So the three adapters in one =live-all= see one process table
between them, however they interleave. =proc.ResetShared= drops the memo; it
exists for the tests, which replace =proc.Run= with a fake and would otherwise
be answered from whatever the previous test cached.

=proc.Holders(files, pids)= narrows the question rather than the answer. Given a
pid list it passes =-a -p <pids>= to =lsof=, so the kernel is only asked about
processes that could possibly hold the file. Codex's lock probe knows its
candidates --- everything with =codex= in its command line, plus their
descendants --- and restricting the call that way took it from 238ms to 41ms.
Where the caller has no such list, =Holders= asks about the files alone, as
before.

The measured result: three sequential per-agent calls, about 950ms, became one
=live-all= at about 205ms, of which 190ms was =claude agents --json=, one call
per config home. Reading Claude Code's own session records instead of running
that CLI removed the last of it: =live-all= now measures about 105ms, and a
=ps= over some 1500 processes on its own measures about 105ms too. The shared
process table is the whole remaining cost, which is exactly what =live-all=
exists to pay once.

* Document structure

A transcript is not rendered record by record. Claude Code writes one JSONL
record per content block, so a single assistant turn arrives as a run of
records that would otherwise become a run of near-identical headings.
Consecutive records sharing a role are merged into one turn heading, which
carries the first timestamp. Sub-headings inside the turn show their own
timestamp only when it falls in a different minute, and show the full date as
well when the turn crosses midnight.

Tool results are nested under the call they answer, matching =tool_use.id=
against =tool_result.tool_use_id=. This matters because results are not really
user messages: the wire format sends them back to the model as user turns, so
rendering them literally produced a =* User= heading nobody wrote, sitting next
to --- but not under --- its call. Records containing nothing but results now
produce no heading at all. A result whose call is missing from the transcript
still renders where it sits, and a user record mixing results with typed text
keeps its heading for the text.

Together these collapse a 4.5MB session from 1182 top-level headings to 34, one
per conversational turn:

#+begin_example
,* User [2026-08-10 Mon 10:22]
,* @Opus5 Assistant [2026-08-10 Mon 10:22]
,** Thinking
,** Tool Use: Bash · Verify LaTeX delimiters
,*** Result: ok
,** Tool Use: Edit · ~/x.zsh [10:24]
,*** Result (error): Exit code 1
#+end_example

A result that is a single line of 72 characters or fewer goes on its heading
rather than into a block; an empty one reads =Result: (no output)=. A result the
adapter pretty-printed says so, and its block is =#+begin_src json= rather than
an example block --- =turns.ToolResult= carries a =Lang= for exactly that, left
empty for output whose syntax nobody can vouch for.

=Thinking= is prose, not a block. Every agent's reasoning summary is markdown:
=**Checking the CLI help**= paragraphs from Codex, the same shape from Claude
and Antigravity. Rendered verbatim it showed its own asterisks and lost its
paragraphs, so it goes through the same prose path as message text, headings
and all.

Assistant turns carry the model that produced them, as the same =@= tag a
subagent's heading uses: =@Opus5=, =@Fable5.1=, =@Haiku4.5=, and =@Synthetic=
for the messages Claude Code writes itself, such as interruption notices. The
tag leads the heading, ahead of the role and the timestamp, exactly as it does
on a subagent's --- one space after it, no separator --- so it lines up in a
column down a transcript where models alternate. Merging stops at a model
change, so a switch mid-answer starts a new heading instead of hiding inside
one --- 8 of 52 local sessions use more than one model, and 3 of 297 merged
turns would otherwise have spanned two. Annotating sub-headings instead was the
alternative, but a plain text block has no heading to annotate, so a switch
landing there would go unrecorded.

* Events

A transcript is not only messages. These record types are rendered too, each
attaching to the turn it interrupts:

- *Recap* --- the summary Claude Code writes when you step away
  (=system/away_summary=). 83 locally.
- *Notice* and *Model fallback* --- =system/informational= and
  =system/model_consent_fallback=, the latter explaining a model switch
  ("Switched to Sonnet 5 for this session · Fable 5 requires usage credits").
- *Command* --- a slash command you ran (=system/local_command=). The payload is
  the same =<command-name>= scaffolding the picker strips, so it reduces to
  =** Command: /model=.
- *Pull request* --- =pr-link=, with the number, repository and URL.
- *Edited outside the session* --- =attachment/edited_text_file=, a file you
  changed in your editor mid-conversation, with the snippet Claude was shown.
  77 locally, and they explain changes Claude did not make.
- *Context compacted* --- =system/compact_boundary=. This one stands alone
  rather than attaching to a turn, since it separates two phases of the
  conversation: =* Context compacted [2026-08-06 Thu 16:25] · manual · 476980 →
  11820 tokens=.
- =system/turn_duration= is not a section. It measures the turn before it, so it
  lands in that turn's heading as =· 4m2s=.

- *Task reminder* --- =attachment/task_reminder=, the outstanding task list.
  Rendered only when it has items. All 485 locally are empty (identical
  56-byte records with =content: []=), because the task tools go unused here,
  but a populated one is worth reading rather than dropping.

Deliberately left out, all of it bookkeeping: =mode=, =permission-mode=,
=agent-color=/=agent-setting=, =bridge-session=, =file-history-snapshot= and
=-delta=, and =last-prompt=, which only repeats the message beside it.
=system/stop_hook_summary= is dropped because it never carries content --- 0 of
225 locally. The remaining =attachment= payloads are harness internals
(=skill_listing=, =deferred_tools_delta=, =output_style=, =plan_mode=).

=agent-name= is not a section either, but it is not discarded: it feeds the
session name, above.

=queue-operation= is left out for a subtler reason. Half of what gets enqueued
is delivered and therefore already appears as an ordinary user message, so
rendering it would duplicate; the other half was withdrawn before it was ever
sent. 49 of 96 local enqueues fall in the first group.

* Subagents

Claude Code stores a subagent's transcript beside its parent, at
=<session-uuid>/subagents/agent-<id>.jsonl=, with a =.meta.json= sidecar giving
the agent type, the description it was launched with, and the id of the tool
call that spawned it. Those transcripts are inlined into a =* Subagents=
section at the top of the document, ordered by where their spawning call
appears in the parent.

Each agent's heading leads with the model it ran as, then the agent type and the
description it was launched with, so the roster says at a glance which agent was
the expensive one and which the cheap one:

#+begin_example
,** @Opus5 Explore · Find claude session name storage
,** @Fable5.1 general-purpose · Draft docs for the alt+enter binding
#+end_example

The model is the mode across the agent's own assistant records --- the most
frequent, not the first or the last. Most subagents run one model throughout,
but a switch mid-agent is possible and an interrupted one carries =<synthetic>=
records, and the mode survives both without being thrown off by a stray record.
=<synthetic>= gets no vote: it marks a message Claude Code wrote itself, an
interruption notice say, and is not a model at all. A transcript with nothing
but synthetic records has no model to report, and its heading is exactly what it
always was. Ties go to whichever model appeared first, and that is deliberate
rather than incidental: iterating a Go map is randomised, so a tie broken that
way would make the document differ run to run, and =TestPandocPathParity=
compares the parallel path against a single pandoc run byte for byte.
=modelMode= in =internal/claude/subagents.go= is the vote.

=turns.ModelTag= formats it, and every place a model stands for whoever spoke
goes through that one function: a turn heading, a Claude subagent's heading, a
Codex child rollout's. It is =@= plus =turns.ModelLabel=, which is
=ShortModel='s output with every dash-separated word capitalised and the dashes
dropped, so =claude-opus-5= is =@Opus5= and =claude-fable-5-1= is =@Fable5.1=
--- one word, scanning as a name rather than as a version string. =ShortModel=
already drops a build date, so =claude-haiku-4-5-20251001= is =@Haiku4.5=.

A word per capital, rather than only the first, is what keeps an id that does
not follow Anthropic's family-and-version shape legible: those reach the same
function, and =codex-auto-review= as =@Codexautoreview= is not a name anybody
can read, where =@CodexAutoReview= is. A short table of vendor tokens that are
acronyms rather than words keeps =gpt-5-codex= from becoming =@Gpt5Codex=; it
is =@GPT5Codex=. A version keeps the dot =ShortModel= gave it, since =Fable51=
would read as a number. The model comes out of the one read
the adapter's =subdoc= already does: it reads the agent's transcript once and
hands back a =turns.Subdoc= whose title carries the vote, so =subagentSegments=
in =internal/turns= only has to write the skeleton around it. Reading the
transcript a second time for a field already in hand would be waste. Checked
against the local corpus on a session with eleven subagents, the six whose
assistant records are mostly =claude-opus-5= render as =@Opus5= and the five
mostly =claude-fable-5-1= as =@Fable5.1=, matching a =jq= count of the raw
records exactly.

The section itself stays unfolded so the roster of agents is visible at a
glance; each agent's own heading carries =:VISIBILITY: folded= so its
transcript stays out of the way until wanted.

* How tool calls are rendered

The original jq renderer dumped every non-=Bash= tool input as compact JSON, so
a =Write= call arrived as one enormous line with every newline escaped as
=\n=. Now each input is taken apart:

- Scalars and short strings become bullets (=- **replace_all**: false=). Paths
  are abbreviated to =~=.
- =command=, =content=, =old_string=, =new_string=, =plan= and =prompt= are
  always blocks, however short. Beyond a command belonging in a source block
  anyway, org's ==verbatim== markup has no escape mechanism, so a one-line
  command inlined that way breaks apart the moment it contains an ===, which
  =echo "=== section ==="= does.
- Other multi-line or long strings become their own fenced block, tagged with a
  language guessed from the input's =file_path= extension.
- Nested arrays and objects become indented JSON.
- Anything already shown in the heading is not repeated as a bullet.

Tool-use headings carry a short summary so a folded outline stays scannable:
the path for =Read=/=Write=/=Edit= (with the line range for =Read=), the
description for =Bash= and =Agent=, the pattern for =Glob=/=Grep=, the URL for
=WebFetch=.

=Edit= calls render as a unified diff with three lines of context, produced by
a line-based LCS in the program itself --- no =diff(1)= fork, no temporary
files. The output matches =diff -U3= byte for byte. Inputs large enough to make
the quadratic LCS table wasteful fall back to printing =old_string= and
=new_string= as two separate blocks.

* Prose fields and heading levels

Message text, and the =plan= and =prompt= tool fields, are markdown rather than
code, so pandoc turns them into real org markup --- headings included. A
message's own =## Foo= must not escape the transcript's outline, so its headings
are renumbered to sit two levels under the turn they belong to, keeping their
relative depths. Two rather than one: the sub-headings a turn is made of
(=Tool Use=, =Thinking=, =Recap= …) sit one level under it, and message content
that landed on the same level would be indistinguishable from the transcript's
own structure.

Before any of that, the prose is defused: a =<= that would open markup gets a
backslash, which markdown renders as the character itself. A transcript is full
of angle brackets that are not HTML --- =<INSTRUCTIONS>= around an agent's own
instructions, a =<system-reminder>=, an XML-ish tool payload --- and pandoc
reads a line starting with one as an HTML block, which swallows everything up to
the next blank line into =#+begin_html=. That is how a whole instruction file
once arrived in a document as one unparsed lump, its markdown headings with it.
Inline the loss was quieter: a =<inline>= mid-sentence was dropped from the
output altogether.

=defuseHTML= escapes only what CommonMark would really read as markup: a
comment, or a tag that closes. A comparison (=c<d=, =a < b=) is left alone,
because the closing =>= is what CommonMark itself requires, and an autolink
(=<https://…>=) is left alone because escaping one would turn a link into text.
Fenced blocks and inline code spans are skipped entirely: their content is
already verbatim, and a backslash there would be shown rather than consumed.

The renumbering happens on the *org* side, after pandoc, not on the markdown
going in. It has to: /pandoc/ decides what a heading is, and the markdown side
cannot see everything it will call one. That was not a hypothetical. A subagent
wrote banner rules around its section titles,

#+begin_example
====================================================================
SECTION 1. Hernandez et al., …
====================================================================
#+end_example

which CommonMark reads as one lazily-continued paragraph closed by a setext
underline --- a level-1 heading, with no =#= anywhere for the markdown side to
find. Seven of them came out as =* = at column zero, siblings of the =* User=
and =* Assistant= turn headings, and re-parented the rest of the document.

So each heading this program emits carries a tag instead: two private-use runes
around a kind letter (=T= for a turn, =S= for everything else) and the heading's
true level. Markdown ignores them, pandoc passes them through untouched, and
=normalizeOrgLevels= strips them again while restoring the level each one
declares. Anything else that is a heading by then came out of a message, and is
demoted as a unit. Two things fall out of doing it this way:

- A =*= at the start of a line in pandoc's org output is /always/ a heading. The
  writer zero-width-space-escapes prose org would misread (=#+TITLE:=, a literal
  =* = line) and comma-escapes block interiors, so there are no false positives
  to sort out.
- Heading levels are no longer capped at six. Markdown stops there; org does
  not, and the tag carries the unclamped level, which matters inside a subagent
  where the transcript already starts at level three.

Three smaller rules the markdown side still enforces, all about fences:

- Headings inside fenced code blocks are skipped, because a shell snippet's
  =# comment= lines are not headings.
- A message that opens a fence and never closes it gets one appended. Otherwise
  it swallows everything after it --- the next turn's headings included --- into
  a single code block, and a chunk seam landing inside that block converts
  differently from no seam at all.
- A fence opened mid-sentence is re-cut around what was meant. A fence has to
  start its own line, so ~I want to print ```~ is not one: CommonMark reads the
  run as an inline code span, keeps the paragraph going, and then takes the
  /closing/ run --- which does start its own line --- as the opening fence. Code
  and prose come out swapped, with the rest of the sentence sealed into the
  block by the rule above.

Only a bare run closes a fence: ~```sh~ inside a ~```~ block is content, not the
end of it. Reading it as the end walks the rest of the message one block out of
step, which is how the fence-closing rule above first went wrong.

The mid-sentence shape is common because =pasteBlockified= (hyper+=,=) wraps the
clipboard in ~```~ with no leading newline, so any paste not landing at column
zero produces it --- 28 times across 18 of the local transcripts. Re-cutting is
safe because CommonMark was already going to read that text as a code block;
only the boundaries move, so a message that would otherwise have rendered
correctly cannot be broken by it. A run with no matching closer later in the
message is left alone rather than guessed at.

A body of one line was a quotation inside a sentence, and becomes an inline code
span so the sentence survives. The line after the closer is pulled up with it
unless it starts a block of its own, because a soft break there leaves pandoc a
space to strand before a leading comma. Anything longer becomes the block it
looks like. What that costs is nesting: an opener inside a list item puts the
fence at column zero, so the block and the text after it trail the list instead
of sitting in the item. Measuring list markers to keep it was not worth it.

[[agfi:org-header-rm-shared-level]] followed by [[agfi:org-header-indent]] is the
same idea, on a document that is already org.

* Bytes that are not text

Tool output is copied into the document as it was captured, and a command that
printed a binary file captures bytes that are not text. One of them, NUL, is
enough to ruin the whole file: emacs decides a file's encoding by sniffing it,
a single NUL makes it choose =no-conversion=, and in that buffer every
non-ASCII byte is displayed as an octal escape. The symptom is a document whose
heading separators read =\302\267= instead of =·=, and whose prose is mangled
wherever it was not ASCII --- for one stray byte in one tool result, possibly
thousands of lines away. Invalid UTF-8 does the same thing one step down: emacs
falls back to latin-1 and =·= reads as =Â·=.

So =turns.ScrubText= emits only what the renderer can honestly show. The C0
controls that are never text are dropped, and a byte sequence that is not valid
UTF-8 becomes U+FFFD, one per bad byte. Tab, newline and carriage return
survive because they are layout. ESC survives on purpose: dropping the
introducer alone would leave the rest of an ANSI sequence behind as literal
text, which is worse than the escape, and turning colour into org markup is a
separate job nobody has asked for yet.

It runs over each segment before pandoc rather than over the finished document,
so no chunk carries a byte pandoc would have to guess about, and the =md= and
=org= paths get the same treatment on the way out. =list= rows and the =preview=
body go through it too, since a snippet is transcript text and ends up on an
fzf line. Almost every document is clean, and the check is one pass with no
copy when it is.

The zsh side adds the second line of defence: [[agfi:h-agent-session-title]]
writes a coding cookie as the file's first line --- =# -*- coding: utf-8 -*-=
for org, an HTML comment for markdown, since =#= there would be a heading ---
which makes emacs decode as UTF-8 whatever its sniffing would have concluded.
Measured on a file with a NUL still in it, the cookie alone is enough to render
the separators correctly. On the reader's side =inhibit-null-byte-detection=
does the same thing globally, for files this renderer did not write.

* The Codex adapter

A Codex rollout is a JSONL of typed lines, and a handful of those types are all
a reader needs. The first line is =session_meta= and carries the thread id (the same
uuid the filename ends with), the cwd it was started in, and the CLI version. A
=session_meta= whose =parent_thread_id= is non-null belongs to a *subagent*, and
those are left out of =list= unless =-subagents= is given: =render= inlines them
into their parent, found by =subRollouts= grouping the day directories by
parent id, so listing them separately would show the same work twice. Then
=turn_context= lines carry the cwd, the model and the reasoning effort in force
for the turn that follows, which is where the model label on an assistant turn
comes from. Everything else is a =response_item=, whose payload type is one of
=message=, =reasoning=, =function_call=, =function_call_output=,
=custom_tool_call= and its output, or =local_shell_call=; a =compacted= line
marks a compaction and becomes its own =Context compacted= turn, as Claude's
does.

Consecutive records of one role merge into a turn, exactly as they do for
Claude, because Codex also writes the reasoning, each tool call and the final
message as separate records of the same turn.

Two filters earn their place. =normalizeInput= joins a =command= given as an
argv array into a single line and unwraps =bash -lc <script>= to the script
itself, so a shell call renders as the command a person would have typed rather
than as JSON; it also drops =workdir= when that is the only other key, since it
merely repeats the cwd.

The other is about the *first* user message, which is not one message. Codex
sends the instructions a session was launched with, and the environment it runs
in, as part of it: the whole assembled =AGENTS.md= inside =<INSTRUCTIONS>=, then
an =<environment_context>= of cwd, shell, date and sandbox policy, then whatever
the person typed. Rendered as one lump it read as though somebody had typed
their own instruction file. So =splitSections= takes the =<tag>=-wrapped
sections out --- an opening tag alone on its own line, its close found by hand
because Go's regexp has no backreference --- and the pieces go their own ways:
the launch scaffold becomes one folded turn, =Session instructions=, and the
typed remainder is the user's turn. A section that is not scaffold, an aborted
turn say, gets a turn of its own rather than being dropped. Instructions render
as prose, since they are markdown; the environment blocks stay verbatim, since
they are XML.

A folded turn is how a transcript can carry that much bulk without burying the
conversation: =Turn.Folded= puts a =:VISIBILITY: folded= drawer under the
heading, which emacs honours at startup. On the pandoc path the drawer cannot be
written inline --- a body segment's drawer would come back from pandoc as a
paragraph --- so the heading tag carries the fact across and
=normalizeOrgLevels= writes the drawer when it places the heading.

Tool results get the same treatment one layer down. Codex hands a result back in
whatever shape the tool produced: a plain string, an object with an =output=
field, or a list of content parts each with a =text= --- and a part's text is
itself often another JSON document, since MCP tools answer in JSON. Rendered raw
that is one unreadable line. =outputText= peels the layers, up to three deep,
and indents what is left when it is JSON, reporting =json= as the block's
language. A list is only taken apart when *every* element is a content part: an
ordinary JSON array is a document, and decomposing it would lose the array
itself.

Names are not in the rollout. Codex keeps them in
=$CODEX_HOME/session_index.jsonl=, which is append-only: one record per change,
so the *last* line for an id is the current name, and a record with an empty
=thread_name= is a name that was *cleared* rather than one set to the empty
string. The index is loaded once per home and kept for the process.

Liveness is the part that could have been a guess and is not. A running Codex
holds =~/.codex/thread-writer-locks/<id>.lock= *open*, so one =lsof= through
=proc.Holders= says exactly which process owns which thread --- no pairing by
cwd, no nearest start time. The holder is the native binary, which is not the
process kitty can see: the window is running the =node .../codex.js= launcher
that spawned it. So =topmostCodex= walks up the ancestry from the holder to the
outermost Codex process and reports *that* pid, which is the one the window
resolver can match. The walk is not a nicety: the ChatGPT desktop app holds
these locks too, and without following the ancestry its threads would be
reported as if they were in a terminal.

* The Antigravity adapter

Antigravity does not write a conversation, it writes *steps*. Each line of the
transcript has a =step_index=, a =source= (=USER_EXPLICIT=, =MODEL= or
=SYSTEM=), a =type=, a =status= (=DONE=, =RUNNING=, =ERROR=), a =created_at=,
and then =content=, =thinking= and =tool_calls= with a name and arguments. The
types seen so far are =USER_INPUT=, =PLANNER_RESPONSE=, =RUN_COMMAND=,
=VIEW_FILE=, =LIST_DIRECTORY=, =GREP_SEARCH=, =SEARCH_WEB=, =CODE_ACTION=,
=CONVERSATION_HISTORY=, =CHECKPOINT=, =SYSTEM_MESSAGE=, =GENERIC= and
=INVOKE_SUBAGENT= --- and that list is an *open enum*, not a schema. The next
release will add to it.

That is what the =event= block is for. A step this code has no vocabulary for
is not dropped and not rendered as JSON: =typeLabel= humanises its type
(=RUN_COMMAND= becomes "Run command", and an unheard-of =FOO_BAR= becomes "Foo
bar"), =statusNote= appends =running= or =error= when the status says something
a reader needs, and the body goes through as output. A step type nobody has
written code for still reads correctly, which is the only defence against an
enum that grows.

The mapping, in =buildTurns=: a step whose source is the user becomes a user
turn, with =userText= stripping the =<USER_REQUEST>...</USER_REQUEST>= wrapper
Antigravity puts around what was typed. A =PLANNER_RESPONSE= with content is the
agent talking, and becomes markdown text in an assistant turn; =thinking= on any
step folds in ahead of it. =CONVERSATION_HISTORY= is Antigravity's compaction and
gets a turn of its own, so the phases either side of it read as separate.
Everything else becomes an event attached to whatever turn it followed --- except
a user's, since the harness speaks for the agent and a step following a prompt
opens the agent's turn rather than being filed under the person who asked. Tool
calls become =tool_use= blocks, with =callArgs= accepting arguments as either an
object or a JSON string, and falling back to the step's own label when the call
has no name.

Whether an event's body is prose or output is a decision, not a constant. A web
search summary is markdown --- headings, bullets, links --- and reading it as a
verbatim block showed the =###= and the =*= to the reader instead of converting
them; a command's output, a file's contents or a grep's hits must be shown
exactly as they came. So =proseStep= consults a table of known kinds and, since
the enum is open, judges an unknown kind by its body: a heading or a bullet by
CommonMark's rule (=#include= is not a heading, =-fPIC= is not a list item), an
inline link, or bold. Prose becomes a =notice= block and output an =event=.

=INVOKE_SUBAGENT= steps are inlined under =-subagents=, but only where the
child is really there: which key carries the child's conversation id is not
documented, so =subConversations= takes every uuid in the step and keeps the
ones whose brain directory has a transcript. A guess that names nothing on disk
inlines nothing.

Names and cwd come from beside the transcript rather than from it.
=conversation_summaries.db= is the authority --- the zsh side reads it with
sqlite3 --- and =cache/conversation_metadata.json= is Antigravity's own mirror
of it, which is what this package reads, so a host without sqlite3 still gets a
name: =nameOf= prefers the Title and falls back to the Preview. The cwd is the
workspace from =history.jsonl=, else a =file://= WorkspaceURI from the
summaries. =list= walks =brain/*/= and skips a conversation that has written no
transcript, because there would be nothing to open.

Unlike the other two, =preview= reads the whole transcript rather than a tail of
it: these files are steps, not message bodies, and the fields the preview wants
most are in the JSON mirror anyway. The =-bytes= window is still honoured, for a
conversation that outgrows the assumption.

* Liveness, and why no adapter guesses a pid

=live= is what lets the kitty hotkey answer "which session is in this window",
and the three agents can promise very different amounts.

Claude Code publishes the answer: every running session writes
=<config-home>/sessions/<pid>.json= and removes it on exit, so the adapter
reads those files rather than asking the CLI. A crash can leave a record
behind, so each one is checked against its pid before it becomes a row.

Codex is exact but undocumented: the writer locks say which process holds
which thread, and the ancestry walk says which pid a terminal can see.
Antigravity is a pairing: a running =agy= process's cwd is looked up in
=cache/last_conversations.json=, the same map =agy= itself uses to resume in a
directory, which is right whenever a workspace hosts one conversation at a
time.

The rule all three follow is that a row names only a process that was really
traced. A session that cannot be paired to one gets no row at all rather than a
plausible pid: Claude drops an entry whose pid is 0, Codex emits rows only for
the lock holders it found, and Antigravity only for a cwd that its workspace map
answers. A session that has a pid but no tmux session carries =-= in that
column, which no window name can match.

The tmux column itself is resolved from the process tree in all three adapters:
=proc.TmuxOf= walks a session's parents up to the tmux pane containing it, over
the one =tmux list-panes -a= the whole run shares. Claude Code does record its
own location, in =<config home>/sessions/<pid>.json=, but that is the tmux
session name as it stood *at launch*, and the autoname hooks rename tmux
sessions on every prompt --- measured, five of seventeen live sessions named a
tmux session that no longer existed. So =tmuxOf= in the Claude adapter asks the
walk first and reads the record only when the walk finds nothing: a session
started outside tmux, a process the table no longer has, or a host with no tmux
running at all. The zsh side used to re-do this walk itself to repair the stale
names; it no longer has to.

That is what makes the window resolver safe. Every strategy in
[[agfi:h-agent-session-of-kitty-window]] matches a window against these rows,
so an invented pid would not produce a miss --- it would produce the wrong
transcript, opened silently. A missing row produces the picker instead, and a
question beats a wrong answer.

* Performance

pandoc dominates the conversion --- on a 4.5MB session it was 89% of the runtime
--- so =org-pandoc= splits the rendered markdown into byte-balanced chunks and
runs one pandoc per chunk concurrently. The seams always fall on record
boundaries, never inside a code block and never just after a heading, so every
chunk is a self-contained markdown document; the result is byte-identical to
converting the whole thing in one pandoc, which =TestPandocPathParity= checks
against the whole local corpus by comparing the path against itself run with
=-jobs=1=. Its reference used to be =-format=md | pandoc=, which no longer works
as one: the org-pandoc path tags its headings and rewrites their levels
afterwards, and a bare pandoc pipeline can do neither. The test exists for the
chunk seams, and still covers them. Documents below a few hundred KB use a
single process, because pandoc's ~70ms startup would eat the gain. Records also
render concurrently, since each is independent.

The no-heading rule is the newer half, and the parity test failed on one
transcript for a long time without it: the parallel output carried one blank
line a single pandoc did not. An org headline is a container, so pandoc's org
writer emits whatever follows a headline with no blank line between the two,
while the chunk join always puts one there. Probed against every block type the
renderer emits, that is the whole of the difference --- a chunk ending on a
heading, followed by a heading, paragraph, list, code block or table, all
diverge, and nothing else does. So when the byte target is reached at a part
whose markdown ends with an ATX heading, the seam moves on to the next part
instead; =endsWithMarkdownHeading= is the test, and it only has to know our own
markdown. Deciding the separator at the seam instead would mean knowing pandoc's
spacing rules, which is the trade the next paragraph refuses. The cost is
nothing measurable: only a part ending in a bodyless heading (a =### Result:=
with no content under it) can push a seam, those are rare, and in the worst case
the chunks merely come out less balanced. Parity now holds over the whole
corpus --- 112 transcripts under =~/.claude-work/projects= and 376 under
=~/.claude/projects=, 488 in all --- and the single-pandoc output is
byte-identical to what it was before the fix.

A tempting further step is to keep code blocks away from pandoc entirely ---
they are 84% of a transcript's bytes and pandoc only copies them through, and
skipping them measured ~40% less pandoc CPU. Do not. Matching pandoc's output
then means reimplementing its reader's quirks: tab expansion to 4-column stops,
CRLF folding, outright deletion of lone CRs, comma-escaping after indentation,
trailing-newline trimming. Each is a silent corruption if it drifts from
whatever pandoc does next release, and that is a bad trade for CPU on a
conversion that runs once per session view.

The fan-out assumes one conversion at a time, and the pickers broke that
assumption: =alt+enter= on ten rows meant ten renderers each spawning a CPU count
of pandocs. The zsh side now hands each conversion =-jobs= equal to the CPU count
divided by the number of live conversions, floored at one. On 8 cores that is 8
for a lone conversion, 4 each for two, 2 each for three or four, so the machine
runs about one machine's worth of pandoc whatever is started. Earlier conversions
keep the share they began with; their chunks finish in well under a second, so
the excess is transient. The count is taken by the job itself after its tmux
session exists, which is what lets two simultaneous starts both count two without
a lock; the section on the per-transcript key has the reasoning.

=list= reads only the two ends of each file: forward from the start until the
first user message, and backwards from the end over a 64KiB tail window. Both
windows widen if they come up empty. That keeps the picker's cost proportional
to the number of sessions rather than to total transcript volume --- across 52
sessions and 48MB it reads well under 1% of the bytes and runs in about 30ms,
matching a full scan exactly on every session.

The name column costs =list= nothing. The backwards walk already decodes every
line in its window, so noticing the =slug=, =aiTitle=, =customTitle= and
=agentName= fields on the records it passes is free. =scanTail= returns both the
newest timestamp and the name parts from the one buffer, decoding into a narrow
=tailRecord= that carries the type, the timestamp and those four fields and
nothing else, so no message body is copied on the way. Measured over the real
corpus --- 119 sessions across both profile roots, warm cache --- the walk took
0.03s before the column and 0.03s after.

What did change is how far the walk goes and when it stops widening. The
timestamp is settled after =tailRecords= (25) messages, since records are
written in order and the newest is always among the first few met; the name
search wants the rest of the window, so the walk now carries on past that point
and only skips the timestamp work. The two searches also widen differently. The
timestamp search is unbounded: missing it means dating the session by mtime,
which is wrong in a way worth reading a whole file to avoid. The title search
stops at =nameWindow= (1MiB): missing it only means falling back to the slug,
and a session with no title anywhere would otherwise pull a 26MB transcript
through the scan just to establish that.

=preview= reads one tail window, 400KiB by default, and decodes it into a record
as narrow as =list='s, so no message body is copied on the way. Through fzf's own
dash it measures 15.4ms, of which 10.7ms is the binary's startup and 4.3ms the
dash spawn --- so the scan itself is about 5ms, and it does not grow with the
transcript: 26MB measures 16.1ms against 2MB's 15.4ms. That is what makes it
usable as an fzf preview, which runs it on every cursor move. The zsh version it
replaced took about 600ms a keystroke; the kitty-window section has the
breakdown.

The conversation blocks and the status did not change that. The status is a
glob of =<config-home>/sessions/= and a =kill(pid, 0)=; the head scan for the
=first prompt= fallback runs in a goroutine beside the tail read and is
abandoned unread whenever the tail answered. Measured by hand, a live session's
preview is about 20ms and the largest local transcript (383MB) the same.

* Why the session time is not the file mtime

The picker used to show each file's mtime, which drifts from the conversation:
Claude Code appends bookkeeping records (for instance
={"type":"bridge-session"}=, which carries no timestamp) long after the last
message. In practice that put entries hours, and in one case two days, past the
last thing actually said. =list= therefore reports the newest timestamp among
the session's =user= and =assistant= records, and sorts by it. Files with no
timestamped message at all --- empty or truncated ones --- fall back to mtime
so they still appear in the picker rather than vanishing.

* pandoc

The org conversion runs =pandoc --from=gfm-gfm_auto_identifiers --to=org=.
Without =-gfm_auto_identifiers=, pandoc attaches a three-line
=:PROPERTIES:/:CUSTOM_ID:/:END:= drawer to every heading, which nothing in
these exports links to.

Avoid the em dash in generated headings: pandoc's org writer rewrites it as
=---=. The tool-use headings use a middle dot, which survives. Property drawers
cannot be expressed through pandoc at all --- a =:PROPERTIES:= paragraph is
collapsed onto one line, and =header_attributes= is not supported for gfm ---
which is why the Subagents skeleton is emitted directly as org and only the
message bodies are handed to pandoc. Its two headings still carry the level tags
described above, so that =normalizeOrgLevels= sees one uniform document rather
than mistaking =* Subagents= for something a message wrote.

** Two zsh hazards these helpers ran into

=path= is tied to =PATH=. It is not an ordinary array: zsh keeps the two in
sync, so =for path in ...= rewrites the shell's search path element by element
and leaves it wherever the loop ended. In a garden shell, which persists between
calls, that produced =command not found: cat= for unrelated commands minutes
later, and nothing in the traceback pointed at the loop. Any loop over paths
here uses =t=, or a hoisted =transcripts= array, and never that name. The same
applies to =cdpath=, =fpath=, =manpath= and =PROMPT=-adjacent specials.

zsh has no namerefs. =local -n= is a bash feature and zsh 5.9 answers =local:
bad option: -n=, so a helper that has to fill a caller's associative array
either builds it inline at the call site or hands values back through =REPLY=,
which is what =h-agent-session-agent-in-roots= does. Nothing in these files
takes a variable name as an argument.

Indirection is available when a caller genuinely has to name the parameter:
=${(P)name}= reads whatever =name= spells --- scalar, array or associative
array, subscripts included --- and =typeset -g "${name}=..."= or =set -A
"${name}" ...= writes it, reaching the caller's =local= without leaving a
global behind. It is not used here because the callers all want one value and
=REPLY= says so more plainly, and because =(P)= brings a trap =REPLY= does not:
if the callee happens to hold a =local= of the name it was handed, the write
lands on its own copy and the caller silently sees no change. =PE/Zsh.org= has
the pattern and the caveat.

* Reading the session you are in

Picking from a list is the wrong tool when you are already inside the session
you want to read: several sessions routinely share a project directory, so
"newest for this cwd" is not reliably the right one. =cmd+shift+o= in kitty
opens the session running in the focused window, whichever agent that is; it
works out the agent for itself, and there is one binding rather than three.

None of the three agents can do this by itself. Claude Code's
=~/.claude/keybindings.json= takes only a fixed action enum --- =chat:submit=,
=app:toggleTranscript= and the like --- with no action that runs a shell command
and no way to bind a slash command, and neither Codex nor Antigravity offers a
keybinding to a command either. So the keypress lives in kitty.

** What the window can say for itself

The hotkey is =agent-view-session-focused=, bound in
=configFiles/kitty/kitty.conf=. It asks =kitty @ ls= which window is focused
and hands that window to =h-agent-session-of-kitty-window=, which tries
five things, in order of how sure each one is:

1. The window shows a tmux client and the autoname hooks have already recorded
   who lives in that session, as the =@agent_session= user option: agent, id
   and transcript. That answers directly, for any agent, and it is tried first
   for one reason --- it is the only answer that needs no live listing, and the
   listing is what the keypress waits on. A hooked tmux window resolves in
   16ms; the same window went through the listing at 365ms before. It cannot
   contradict the two tests below either, since a window displaying a tmux
   client has none of the agent's own processes in the foreground.

   Which session to ask is the part worth writing down. It has to come from the
   client's *pid*, through one =tmux list-clients=, and not from the name in the
   window's command line: the autoname hooks rename a session after the agent
   in it, so a window still running =tmux attach -t scripts-claudework1= is
   attached to a session now called =+Claude/work claude-session-helpers-refactor=.
   The first version of this matched the spelled name, which reads perfectly and
   never once fired.
2. An agent runs in the window itself. One of the window's foreground pids is
   then a live session's pid --- which is why a session whose process was never
   traced must have no row rather than a guessed pid.
3. The window shows a tmux client, =tmux a -t NAME=, whose session the hooks
   never recorded. Sessions here mostly live in detached tmux sessions --- that
   is what lets them outlive a kitty restart --- and the kitty tab merely
   displays one. NAME is matched against the live rows' tmux column, and only a
   single hit counts, since one tmux session can host several agents in several
   panes. That column names the session the process actually sits in, found by
   walking its ancestry to a pane, so it stays right across the renames the
   autoname hooks do on every prompt. This is the path an agent takes while its
   hooks are still untrusted, and it costs the full listing: about 160ms.
4. The window shows an agent's own view, =claude agents= or =claude attach=. The
   view sets the window title to the attached session's name, at times with a
   status glyph in front, and the title is matched against the live sessions'
   names. This is observed behaviour, not documented, so it has to match
   exactly one session or it is ignored, and only when a foreground process is
   one of the agents' binaries.
5. The registry described below: where the session was showing the last time
   it was prompted.

The first four read only what exists at the moment of the keypress, so they
cannot go stale. The fifth can, which is why it comes last.

Everything the five strategies read about a window comes from one =kitty @ ls=
put through one =jq=: =h-agent-session-windows= emits a line per window with its
id, its title, its foreground pids and their command lines, the last separated
by a unit separator because no command line carries one. A =jq= per window per
field was most of what the pickers spent, twenty windows meaning forty processes
to re-read a listing already in hand. The tmux side is batched the same way: one
=tmux list-sessions= for every session's identity
(=h-agent-session-tmux-identities=) and one =tmux list-clients= for every
client's session (=h-agent-session-tmux-clients=). A caller that resolves many
windows primes =agent_session_windows_cache= and the two tables and pays for
each read once.

The live rows are every agent's =live= output concatenated, so the four
strategies above are agent-neutral: each row carries a pid and a tmux session
or the honest =-=. The rest of this section is how Claude's own row is found,
which is the most involved of the three; the Codex and Antigravity sections
above cover theirs.

What counts as live for Claude Code comes from its own session records: a
running session writes =<config-home>/sessions/<pid>.json= --- its pid, session
id, name, cwd, kind, busy/idle status and the tmux location it launched in ---
and removes the file when it exits. Compared against =claude agents --json= on
this machine the two agree exactly: the CLI's only extra entries are finished
background agents that carry no pid, which never had a row anyway.

The records are read directly, and the CLI is not run at all. That is not us
second-guessing liveness from the process table, which we still refuse to do:
an assigned background session and an idle pre-forked spare share the identical
argv, so nothing in =ps= tells them apart. It is Claude Code's own statement
that the session exists. The one case a record gets wrong is a session killed
without cleanup, which leaves the file behind, so every record is checked
against its pid --- signal 0, which asks the kernel and costs nothing --- and a
dead one is dropped.

This is what took the listing from 170ms per config home to a few file reads.
=agent_session claude live= reads every home it is given and derives the
transcript paths in the same process, which also removes a dozen shell forks;
=h-claude-session-live-list= calls it, falling back to an identical-output
shell path (=h-claude-code-session-live-list-sh=) when the binary is not built;
=h-agent-session-live-list= is what concatenates that with the other agents'
rows. The status column comes straight out of the record: =busy= or =idle=.
The transcript path is derived rather than read: the session's id under the
projects directory named after its cwd, in the same config home, with every
non-alphanumeric character of the cwd turned into =-= --- slashes, dots,
spaces and underscores alike, which is the rule Claude Code uses. What is left
of the resolution is the shared process table, not Claude Code.

The Go probe is by =command -v=, a real PATH lookup, not by the shell's command
hash: the garden's hash is stale for a binary installed after it started, and
trusting it would send every call down the slow build-check path. The zsh guard
in front of it, =h-agent-session-dep=, spells the same idea as =whence -p
agent_session=, and that spelling is load-bearing: =isdefined-cmd= reads
=$commands=, which makes zsh hash every directory in =PATH= --- 65ms in a garden
shell, which forks per call and so never has a warm hash --- while =whence -p=
stops at the first hit. Since the guard sits in front of every render, name,
listing and preview, that took it from 124ms to about 1ms.

** In the background, with a band, press again to cancel

The conversion is the slow part -- =agent_session <agent> render= plus a
fan-out of pandoc processes, seconds on a large transcript -- so none of it runs
in the hotkey. The press itself only identifies the tab (kitty, about 30ms),
claims it, raises a band and returns. Everything else, the 300ms lookup
included, happens in =h-agent-view-job= behind that band, which names the
session once it is known and comes down when emacs has the file. Resolving
*before* claiming would leave a 300ms window in which a second press starts a
second job; this way a double-tap deterministically cancels.

The key is a toggle. A press while the tab's conversion is running cancels it:
the band turns amber and says so, the process tree goes, the temp directory
with its truncated =.org= is removed. The next press starts afresh.

The job lives in a tmux session named for the tab, =agent-view-<kitty-pid>-<window-id>=,
which is the repository's detached-job primitive and, here, also the lock, the
handle and the cancel target: =tmuxnew= kills any previous session of that
name before creating the new one, =tmux-alive-p= says whether the job still
runs (=has-session= alone does not, with =remain-on-exit= on), and
=tmux-session-processes-kill= takes the whole tree down, pandoc children
included. No marker, pid file or redis key -- the same shape as the usage
notifier. The temp directory is recorded on the session with
=tmux set-option '@ccv_tmp'= for the canceller, so the bookkeeping cannot
outlive the job. The renderer's build check runs in the foreground before the
job starts, so a cancel never has to kill a Go toolchain on a first use.

The band is hs-alert v2 under the same name as the tmux session. Re-showing an
id updates the band in place, and an unchanged message is a heartbeat, so the
job reports progress by re-showing; bands stack, so two tabs converting at once
show two. =hs-alert-dismiss= takes one down. Every alert call is wrapped in
=reval-timeout= and never fails the caller, so a Hammerspoon mid-reload cannot
hang a hotkey. On failure the band turns red with the reason and a
notification goes out too; the band would otherwise expire on its own in ten
minutes, so a crashed job cannot brand the screen.

Two ordering rules in the canceller, both learned elsewhere in the repository:
read the session's options before killing it, since the kill discards them; and
change the band before the kill, so nothing the death triggers can repaint it.
Cleanup lives in the canceller, not in an =always= block inside the job,
because a killed process is not guaranteed to run one.

The same discard rule bit the launcher. =tmuxnew= replaces any session of the
name it is given, and replacing it throws away its options, =@ccv_tmp=
included --- so a relaunch orphaned the previous job's temp directory for good.
It happened two ways: a press landing between a caller's =tmux-alive-p= test and
the claim, which starts a second launch under the first one's name; and a
finished job's leftover, whose pane is dead but whose session and options survive
=remain-on-exit=. =h-agent-view-launch= now reads =@ccv_tmp= and removes
the directory before replacing the session, which also reclaims a dead
leftover's directory in passing. The other end had a window too: =tmux-alive-p=
stays true through =emc-open=, so a cancel arriving while emacs was opening the
file deleted it from under the buffer. =h-agent-view-convert= unsets
=@ccv_tmp= immediately before the handoff, so a cancel in that window reads an
empty value and =h-agent-view-rm-tmp= returns early on it. The band still
turns amber and the process tree still goes; only the file is spared.

On success the temp directory stays, as it always has: emacs has the file
open.

** A big transcript makes an org file emacs will not open

A transcript renders to an org file far bigger than itself: one 41MB transcript
produced 108MB of org. That size crossed a threshold nothing here had thought
about. =vlf-application= defaults to =ask=, which means "prompt when the file is
over =large-file-warning-threshold=", 50MB in this config. The conversion reaches
emacs through =emc-open= and =emc-eval=, which is =emacs --batch= driving
=server-eval-at=, and nobody is on that end to answer a prompt. So the open did
not fail; it blocked. One such job sat there for three hours, holding its tmux
session and its temp directory, and since a band lasts ten minutes, nothing on
screen said it was still there. From the outside it looked exactly like a hung
conversion.

=emc-nowait2= now binds =vlf-application= to =dont-ask= around the open, so a
file over the threshold goes straight to vlf, and =night-vlf.el= sets the same
default in the config. Both, because the config belongs to one machine and the
zsh is the code path: a host whose doom config predates the setting, or an emacs
started before it, must not hang. Verified on a 62MB org: =vlf-mode= on, one 1MB
chunk in the buffer against 65377804 bytes on disk.

This is a fix rather than a workaround. Plain =find-file= on 108MB of org is not
something emacs finishes either, so the prompt was never offering a usable
alternative; it was only a place to get stuck.

** From a picker, with alt+enter

In each of the three session pickers --- =h-agent-session-select-fz=,
which the viewers and the whole resume family go through,
=agent-session-live-fz=, and the kitty overlay described next ---
=alt+enter= converts the highlighted transcript to org and opens it in emacs in
the background, under the same band and cancel machinery as =cmd+shift+o=. The
picker stays open, so you can keep looking, or open several; pressing
=alt+enter= again on the same row cancels that row's conversion. The function
behind the key is =agent-view-session-toggle=.

Before this, a picker's only exit was Enter, which handed the path back to the
caller. For =agent-view-session-fz= that meant converting in the
foreground, and the terminal was blocked for seconds on a large transcript.

The job is keyed on the transcript, not on the kitty window. The hotkey's key is
=<kitty-pid>-<kitty-window-id>=, which is the right key for a press bound to one
window. A picker moves between rows, so "press again" has to mean "again on this
row": keyed on the window, =alt+enter= on a /different/ row would cancel the
running conversion instead of starting the new one, and a third press would be
needed to start it. =h-agent-view-transcript-key= derives the key from the
uuid the file is named after, sanitised to =[A-Za-z0-9-]= and refused if nothing
survives. It has to be sanitised because the key becomes a tmux session name and
tmux forbids =:= and =.=, and because a subagent transcript is
=<session>/subagents/<name>.jsonl=, whose basename is not a uuid at all.

Two things follow from that key. Several conversions can run at once and their
bands stack, which the band mechanism already supports: re-showing an id updates
in place, and distinct ids stack. And nothing on this path needs kitty, so the
binding works over ssh, under plain tmux and on Linux; only the band is
macOS-only, and it already fails soft.

The flip side is accepted: =cmd+shift+o= cannot cancel an =alt+enter=
conversion, and =alt+enter= cannot cancel one of =cmd+shift+o='s. They are
separate key namespaces on purpose, and =h-agent-view-name-of= documents
both kinds of key it receives.

=agent-view-session-bg=, which the overlay's Enter calls, is deliberately
not a toggle, although its docstring used to claim a press-again-to-cancel it
never implemented. Its one caller runs while the job that /opened/ that overlay
may still be winding down: =h-agent-view-job= launches the picker from
inside its own tmux session, dismisses the band, and only then returns. A toggle
there would sometimes answer "I picked this one" with "cancelled", silently. The
docstring was corrected instead; toggling lives in the picker's =alt+enter=.

=h-agent-session-open-cmd= builds the bind command once, in zsh, exactly
as =h-agent-session-preview-cmd= builds the preview command, and a picker
writes =--bind "alt-enter:execute-silent($(h-agent-session-open-cmd) {2})"=.
It goes through =brishzb.dash=, not =brishzq.zsh=, for a reason of the same class
as the preview's: =execute-silent= blocks fzf until the command returns, and
brishzq waits for the whole call. That measures 250ms, most of it not the garden
hop (~60ms) but =h-agent-view-launch='s own foreground work --- the
Hammerspoon band call, =gmktemp= and =tmuxnewsh2=. =brishzb.dash= posts
={ cmd } &>/dev/null &= and returns as soon as the garden forks: 20ms. Losing
stdout and the exit status costs nothing, because the work is asynchronous
either way and every failure already reports through the band and a notification
in =h-agent-view-fail=.

=brishzb.dash= splices its arguments into JSON unquoted, which =brishzq.zsh=
would not. That is safe here by construction rather than by luck: fzf
shell-quotes ={2}= with single quotes, and a transcript path cannot contain a
double quote or a backslash, whichever agent wrote it --- Claude Code names the
project directory after its cwd with every non-alphanumeric character replaced
by =-= and the file after a uuid; a Codex rollout is date directories plus
=rollout-<timestamp>-<uuid>.jsonl=; an Antigravity transcript is a uuid
directory plus a fixed =.system_generated/logs/= path. The wrapper's absolute
path comes from =$commands=, so nothing depends on whatever =PATH= fzf happens to have.

The =--bind= overrides the =alt-enter:print-query= that =FZF_DEFAULT_OPTS= sets
globally, in =bash/auto-load/configvars.bash=, and nothing is lost: in these
pickers a printed query came back as the selection and failed the =test -e= on
it, which is all it ever did. Every picker also carries a =--header= from the
shared =agent_session_fz_header=, because a binding nobody knows about
will never be pressed.

** What a per-transcript key costs, and how it is paid for

Keying conversions on the transcript let several run at once, and two things that
were bounded when the key was a kitty window stopped being bounded.

The first is leftovers. =remain-on-exit= is on, so a finished job leaves its tmux
session behind. Elsewhere that is deliberate --- it is how "did my notifier
already fire?" is answered --- but a conversion has a band and a buffer to show
for itself and needs no dead session as a receipt. Under the hotkey's per-window
keys the leftovers could not outnumber the kitty windows; under a picker's
per-transcript keys there is one for every transcript ever opened.
=agent-view-reap= removes the dead ones, and their temp directories with
them, and =h-agent-view-launch= calls it first thing, so the thing that
creates them clears them and nothing has to be scheduled. It is safe to run by
hand. It needs to find them, and it cannot do so the way
=claude-code-usage-armed-sessions= does, by regenerating a list of known names:
there is no finite set of transcript names to reconstruct. So
=agent-view-sessions= scans =tmux list-sessions= for the shared prefix
=agent_view_session_prefix= instead, the same shape as
=caffeinate-holders=.

The second is CPU. =-jobs= defaults to the CPU count and =pandocChunks= spawns
that many pandocs, which was fine at one conversion per kitty window. A picker
that stays open to invite pressing again made =alt+enter= down a list of ten mean
ten times the CPU count in pandoc processes. =h-agent-view-jobs-share=
divides the machine by the number of live conversions, so the total stays at
roughly one machine's worth however many are started, and nothing is ever
refused. Measured on 8 cores: one live conversion gets 8, two get 4 each, three
get 2, four get 2. A conversion already running keeps the larger share it was
given; its chunks are short-lived, so the overshoot drains rather than
persisting.

The count happens /inside/ the job, not at launch, and that is what makes it safe
without a lock. =tmuxnewsh2= creates the session before the body runs, so a
conversion always counts itself; two starting at once both see two and both take
half, which is the right answer rather than a race. A redis token was considered
and rejected: it would have to be released, and the main verb here is cancel,
which SIGKILLs the job --- the launcher's own note already says "no marker, pid
file or redis key". Liveness is a property of the process, so this self-heals
where a record would drift.

=h-agent-session-render= gained the =-jobs= knob this needs, read from
=agent_session_render_jobs=. Unset, the renderer keeps its own default, so
every other caller is unchanged; =h-agent-view-convert= sets it as a
=local=, which dynamic scope carries down to the renderer without exporting
anything, and an explicit setting from further out wins.

** The picker

When none of the four resolves, the hotkey does not notify and give up. It
opens a picker over every live session as a kitty overlay in that same window,
=zshlang/wrappers/agent-session-pick.zsh=: "which one did you mean" is a
question, not a failure. It is an overlay running its own script because fzf
needs a terminal and neither the background hotkey nor the garden's shells have
one; the script runs fzf itself and goes through the garden for the rows, the
preview's and =alt+enter='s command lines, the header, and the final open. The
preview itself is a binary fzf execs on every cursor move, with no garden hop.
The tab's key travels into the overlay as =AGENT_VIEW_TAB_KEY=, so the choice
comes back through =agent-view-session-bg= and gets the same band and
cancel as a direct hit.

** The registry, as insurance

The write side is =agent-session-register <agent>=, wired to every agent's
prompt hooks: Claude Code's =SessionStart= and =UserPromptSubmit= in
=configFiles/claude-code/settings.json=, the same two events in
=configFiles/codex/hooks.json=, and =PreInvocation= and =Stop= in
=configFiles/antigravity/hooks.json=. Under
=~/.local/state/agent-sessions/=, in a file named
=<kitty-pid>-<kitty-window-id>=, it records the transcript the payload named,
which the adapter's =hook-transcript= verb digs out of that agent's own field
spellings. kitty numbers its windows from 1 again on every restart, so the pid
is what stops a dead kitty's entries from being read as live ones. The old
=claude-code-sessions= directory is still read, so a record written before the
rename is not lost.

It records the one fact a hook knows that nothing else does. When
=UserPromptSubmit= fires, Enter was just pressed, so the kitty window focused
at that instant is the one showing the session, whatever the attach mechanism.
It used to walk its own process ancestry looking for kitty instead. That finds
kitty only for a session run directly in a tab; for anything attached, the
walk ends at tmux or at Claude's pty host, and the hook silently recorded
nothing. No hook fires on attach itself, and none runs in the attaching
client, so a prompt is as close as a hook can get.

Two guards keep the record honest, and a third arrived with Antigravity. If
kitty has no focused window, the prompt did not come from one --- a message
from another agent, say, or the usage auto-continue --- and nothing is written.
If the focused window resolves to a /different/ session, the prompt was
injected while you sat elsewhere, and nothing is written either. Only a window
the live lookups cannot explain, or one they agree with, is recorded. And a
window running no agent at all is not showing this session either, which the
first two guards would both have accepted: Antigravity's =PreInvocation= fires
once per model call rather than once per prompt, so by the time it runs the
focus may have moved to an ordinary shell. That is what makes it insurance rather than
a competing answer: it covers the attach path nobody has invented yet, and the
day the agent view stops putting the name in the title.

Nothing here needs doing for a second profile. The registry stores the
absolute transcript path, so a [[agfi:claude-work]] session records a path
under =~/.claude-work/projects/= without anything knowing that profiles exist,
and the hooks fire at all because =~/.claude-work/settings.json= symlinks to
the same tracked file.

** Exit codes and the notification

The hotkey notifies rather than printing on failure, because it runs detached
and stderr goes nowhere a person will look. It also always exits zero.
Pressing the key in a window with no session is an ordinary outcome, not an
error, and the picker or the notification has already answered --- but a
non-zero return makes BrishGarden log the command as failed and ring its
failure bell, which is a second, louder answer to a question already answered.
=h-agent-view-session-focused= holds the real body and the real exit
code, for anything that wants to branch on it.

Things that are easy to get wrong here:

- kitty's own =PATH= is just =/usr/bin:/bin:/usr/sbin:/sbin=, so the binding
  needs an absolute path to =brishz.dash=. It cannot use =brishz2.dash=, whose
  quoting path needs a =jq= that is not on that =PATH= either. The command is a
  bare function name, so the unquoted path is safe. The overlay picker has the
  same problem from the other side, and gets our =PATH= passed in explicitly.
- =KITTY_LISTEN_ON= is only trusted when it still points at a live socket.
  Brish's shells outlive kitty, so the garden holds whatever value was in the
  environment the day it started, which goes stale the moment kitty restarts.
  Otherwise the socket comes from [agfi:kitty-socket-get], which owns that
  knowledge for everything that talks to kitty and matches =listen_on= in
  =configFiles/kitty/kitty.conf=.
- The socket lives in =$NIGHT_SOCKETS_DIR=, =~/.local/state= by default, and
  emphatically not in =~/tmp=. It sat there once, and a stray deletion killed
  kitty's remote control outright: an unlinked socket path cannot be
  re-linked, and =listen_on= is applied only at startup, so kitty went on
  holding the bound inode while every client got ENOENT. Nothing short of
  restarting kitty brings it back, which is why
  [agfi:kitty-socket-get] says so by name instead of reporting "no socket".
  The registry moved out of =~/tmp= for the same reason; it vanished in the
  same sweep.
- Sockets left behind by a kitty that crashed are ignored rather than deleted.
  =listen_on= puts kitty's pid in the socket's name, so
  [agfi:kitty-sockets-list] can filter by whether that pid is still a live
  kitty. Deleting them used to be the strategy, and a =kitty @= that failed
  for any unrelated reason would take a working socket with it.

Remember =brishz-restart= after changing any of this: the garden keeps
persistent shells and will otherwise go on running the old code.

Variables:

- =agent_session_registry_dir= --- defaults to
  =$XDG_STATE_HOME/agent-sessions=, with =~/.local/state= standing in
  for an unset =XDG_STATE_HOME=. The old =claude-code-sessions= is still read.
- =agent_session_live_list_cache= --- a listing to reuse instead of asking
  every agent again; set it (a =local= suffices) around several lookups. It
  matters more now than it did: one lookup costs an =lsof= over the Codex
  locks and a process listing.
- =agent_session_live_rows_scope= --- =windows= (default) or =all=; see
  the next section.
- =agent_session_kitty_socket_glob= --- defaults to
  =$NIGHT_SOCKETS_DIR/kitty-*.sock=. Passed through to
  =kitty_sockets_list_glob=, which is the same override under the name the
  shared resolver uses.

* Sessions live in a kitty window

=agent-session-live-fz= picks among the agent sessions currently live in a
kitty window --- every agent at once, each row carrying its glyph --- and
prints =<kitty-window-id> <TAB> <transcript path>= per choice. The agent is
recovered from the path afterwards, which is why the row needs no column for
it. Each window goes through the same
=h-agent-session-of-kitty-window= the hotkey uses, so a session shows
up whether it runs in the tab, sits behind a tmux client, or is attached
through the agent view, and it disappears the moment its window closes.
=alt+enter= on a row converts that transcript to org and opens it in emacs in
the background, leaving the picker up; under =--multi=, fzf's ={2}= is the
highlighted row rather than the selection, which is what the binding wants,
since it acts on the one row you are looking at. With
=agent_session_live_rows_scope=all= the rows cover every live session,
with =-= in the window column for one no kitty window is showing; that is what
the hotkey's overlay picker offers, via =h-agent-session-pick-rows=.

Each row's metadata comes from one =agent_session <agent> list= call per agent
--- for Claude, over every profile's projects directory --- joined back onto the
live rows by transcript path, rather than one metadata call per row. =list=
walks the whole corpus in about 45ms, while =agent_session claude name= alone
costs about 230ms on a large transcript — a per-row call would have made the
picker's startup cost scale with however many sessions happen to be open. The
fzf preview goes further still and skips =agent_session claude render= entirely:
rendering a 46MB transcript takes about eight seconds, far too slow for a
preview pane that has to feel instant. Instead =agent_session claude preview=
tail-scans the last few hundred KB for fields Claude Code already writes there
in plain form --- the rows are listed under Commands --- and fzf execs the
binary directly, with no shell in between.

It was a zsh function first, and it cost about 600ms per cursor move, which is
unusable in a pane that repaints on every keystroke. Measured, that was roughly
380ms for the brish garden round trip, paid every keystroke because fzf reached
the function through the garden --- though that component was taken on a loaded
machine and does not reproduce: =brishzq.zsh true= measures ~60ms idle. The
600ms total and its 15ms replacement were measured the same way, so the
comparison stands even though the parts have shrunk; about 122ms for colour,
since the repository's =colorfg=, =Bold= and =resetcolor= gate on a tty through
=isColor= and =isColorTty=, which call =h-color-p-override= inside a command
substitution --- a fork per call, about 25 calls at ~5ms each; and about 155ms
for =tail -c= and =jq=, two more forks, plus a zsh loop over the several
thousand tagged lines the jq pass emitted. In the binary the whole thing is
15.4ms, most of it process startup; the Performance section has the split. That
is the criterion =PE/Zsh.org= sets for reaching for Go --- hot paths where
repeated forking dominates --- and the same reasoning that moved =list= and
=live= there. It also takes the =brishz-restart= gotcha out of the preview
entirely: there is no zsh left in the hot path to go stale.

The name is resolved from all four sources in the Go resolver's precedence ---
=agent-name=, =custom-title=, =ai-title=, slug --- rather than from =ai-title=
alone, as it once was. =claude-code-session-import= names a fork with
=agent-name= and =custom-title= records, so the old scan showed a fork under its
pre-fork title, in exactly the workflow the resume family exists for. The
precedence used to be implemented twice, once as =nameParts= and once as a jq
if/elif chain that had to be kept in step with it; now only =nameParts= exists,
and it serves =name=, =list= and =preview= alike. Checked over all 125 local
sessions, the preview's headline agrees with the authoritative =agent_session
claude name= on every one.

One accuracy improvement fell out of the move. The jq version keyed each field
on the record type that names it, so the permission mode came from
=permission-mode= events alone. The Go version decodes a narrow record with no
type field at all and takes each value from whichever record carries it, and for
=permissionMode= that is not merely equivalent: Claude Code writes it on every
ordinary =user= record as well as on its own =permission-mode= events --- 281 of
the former across the local tails --- so the newest of the two is more current
than the last change event. Everything else the preview shows already rode on
the message records and is read the same way. The partial line a byte-tail
starts on is dropped only when the tail really is a tail; on a transcript
smaller than the window there is no partial line, and a session of one or two
records would otherwise lose everything there was to read.

The colour is keyed on the profile, from =profiles.PickerColors=: =.claude=
orange, =.claude-work= violet, and an unknown profile gets no colour rather
than a wrong one. That table is generated from
=configFiles/claude-code/profiles.yaml= along with the zsh launcher's own
tables and the status line's, so the seat that is violet here is the violet one
everywhere; see =internal/profiles= and =docs/claude_code_usage.md=. Which
account a session belongs to is the
thing worth seeing at a glance, since the whole point of
=claude-code-session-resume= is that the two are otherwise interchangeable. It
is deliberately not Claude Code's own =agent-color=: that record is written
once, wherever in the session the name got settled, which is nowhere near either
end of the file --- 210MB into a 398MB transcript in one measured case --- so a
tail scan cannot reach it, and only 5 of 125 local sessions have one at all.

The table lives in Go rather than zsh because it has to: fzf spawns the preview
on its own, and a zsh global cannot reach a process it did not start. The zsh
=claude_code_session_profile_colors= array is gone for that reason, as are the
two helpers the shell version needed --- =time.Parse= reads the RFC3339 stamp
with its offset, so the =TZ=UTC= trick =h-claude-code-session-epoch-of= existed
for has nothing left to do, and =preview.HumanAge= replaces
=h-claude-code-session-age=, printing the single largest unit (=44s=, =6m=,
=3h=, =2d=) since what a preview answers is how stale the session is. The
escapes are 24-bit SGR written directly, with bold and colour in one escape for
the headline: nesting bold inside colour would end the bold at the inner reset
and leave two resets saying one thing. Because the output carries ANSI, every
caller passes fzf =--ansi=: =h-agent-session-select-fz=,
=agent-session-live-fz= and the overlay front end
=zshlang/wrappers/agent-session-pick.zsh=.

The knobs still reach it, but from the other end.
=agent_session_preview_bytes= and =agent_session_preview_color_p=
are read once, when a picker builds its =--preview= command line, and baked into
it as =-bytes= and =-color=false=. =h-agent-session-preview-cmd= does
that, printing the shell-quoted command ready to have a field placeholder
appended, so a picker writes =--preview "$(h-agent-session-preview-cmd)
{2}"=. It resolves the binary's absolute path from =$commands=, so nothing
depends on whatever =PATH= fzf happens to have.
=h-agent-session-preview= survives as a thin wrapper over the same
command, because the overlay picker reaches it by name through the garden and
because it is the convenient way to see a session's preview by hand; the
pickers themselves no longer go through it.
